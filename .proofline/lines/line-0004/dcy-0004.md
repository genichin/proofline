# Line별 implementation worktree와 공용 ProofLine tool 환경 표준화

## Problem

ProofLine 계약은 main에서 REQ를 승인한 exact commit으로 implementation branch를 만들고 그 branch에서 Micro-SPEC·구현·IQC를 수행하도록 요구한다. 그러나 implementation branch의 working directory를 정의하지 않아 main repository checkout을 implementation branch로 전환하면 직렬화된 main governance workspace가 사라지고, 다른 governance 확인이나 독립된 Line 작업과 working tree 상태가 섞일 수 있다.

또한 ProofLine이 적용된 Python project가 자체 application `.venv`를 사용할 때 ProofLine CLI를 같은 environment에 설치하면 application dependency와 governance tool dependency가 한 lock·venv에 결합된다. Project마다 ProofLine을 중복 설치하면 version과 update 상태가 달라질 수 있지만, 현재 ProofLine에는 적용 project가 공용 tool environment를 사용하는 표준이 없다.

## Evidence

- `docs/contracts/line-delivery.md:30-36`은 Line 생성·Discovery confirmation·REQ approval을 main governance에서 수행하고 implementation branch를 exact REQ approval commit에서 생성하도록 요구한다.
- 같은 문서 `line-delivery.md:38-57`은 specification 변경 시 main governance로 돌아가 REQ를 재승인한 뒤 implementation branch에 새 baseline을 반영하도록 요구한다. Main checkout과 implementation checkout을 분리하면 이 왕복 경계를 물리적으로 유지할 수 있다.
- 현재 `.gitignore`는 root `.venv/`, `temp/`, Python cache만 제외하며 `.worktrees/`는 제외하지 않는다. `git check-ignore .worktrees/line-0004`도 match를 반환하지 않았다.
- `git worktree list --porcelain` 결과 현재 main working tree `/home/genichin/work/proofline` 하나만 존재한다.
- 승인 commit을 detached worktree로 checkout하는 실측을 3회 수행했으며 Git worktree 생성은 각각 0.008초, 0.009초, 0.008초였다. 이 실측은 worktree 생성 비용만 채택 근거로 사용하며 ProofLine venv를 worktree마다 생성하는 근거로 사용하지 않는다.
- 현재 `uv tool dir`은 `/home/genichin/.local/share/uv/tools`, `uv tool dir --bin`은 `/home/genichin/.local/bin`을 반환한다. 이는 application project directory 밖의 user-level tool environment와 executable 경계를 제공한다.
- 격리된 임시 `UV_TOOL_DIR`·`UV_TOOL_BIN_DIR`에서 `uv tool install /home/genichin/work/proofline`을 실행한 결과 0.325초에 설치됐고, 생성 executable의 shebang은 별도 tool venv의 Python을 가리켰다. Checkout 밖 `/tmp`에서 해당 `proofline --help`가 성공했다.
- 현재 live `uv tool list`에는 설치된 tool이 없어 공용 ProofLine tool environment rollout은 아직 수행되지 않았다.
- `src/proofline/cli.py:9-24`의 CLI command는 `validate`와 `line init`뿐이며 Git worktree 생성이나 package update를 수행하지 않는다.
- GitHub Issue [#9](https://github.com/genichin/proofline/issues/9)는 사용자 명시적 `proofline update`의 release source, installer ownership, compatibility와 rollback을 후속 Discovery 후보로 보존한다.
- 현재 source baseline에서 `uv run pytest -q`는 45개 test를 통과하고 `uv run proofline validate`도 통과했다.

## Scope

- Main repository checkout은 `main`의 직렬화된 governance workspace로 유지한다.
- REQ approval commit에서 implementation을 시작할 때 repository root의 `.worktrees/line-NNNN/`에 해당 Line의 implementation branch를 Git worktree로 생성한다.
- Worktree branch base가 같은 Line의 exact REQ approval commit인지 생성 전후 검증한다.
- Main working tree cleanliness, 대상 worktree path·branch 충돌, 기존 worktree registration과 approval commit 존재 여부를 생성 전에 fail-closed preflight한다.
- `.worktrees/`를 repository-local derived workspace로 취급하고 Git tracking 대상에서 제외한다.
- Line worktree를 생성할 때 ProofLine 전용 `.venv`를 만들지 않는다. Main과 모든 Line worktree의 ProofLine governance 명령은 동일한 user-level `uv tool` environment와 `proofline` executable을 사용한다.
- 구현 대상 project가 source build·test를 위해 사용하는 environment는 해당 project의 개발 계약이 소유하며 ProofLine governance environment로 취급하지 않는다.
- Micro-SPEC, implementation source, test와 IQC artifact는 해당 Line worktree에서 작성하고 commit한다.
- Main integration은 기존 계약대로 검증된 candidate를 fast-forward하며, worktree 사용이 merge·delivery authority를 변경하지 않는다.
- Worktree 생성·검증·사용·정리 절차를 repository-owned Hermes workflow와 governance 문서에 기록한다. ProofLine CLI는 Git branch, worktree, commit, merge 또는 lifecycle transition을 직접 수행하지 않는다.
- ProofLine이 적용된 project는 application `.venv`에 ProofLine을 dependency로 추가하지 않고, OS user가 소유하는 하나의 공용 `uv tool` ProofLine environment와 executable을 사용한다.
- 현재 release channel이 없는 동안 공용 tool은 명시적으로 선택한 ProofLine source checkout에서 non-editable `uv tool install <proofline-checkout>` 방식으로 설치한다.
- 공용 tool 설치 후 executable이 `uv tool`의 bin directory에 존재하고 별도 tool venv Python을 사용하며, checkout 밖의 적용 project에서 `proofline validate`를 실행할 수 있는지 확인한다.
- Governance command와 project source build·test command를 구분해 문서화한다.
  - Main과 모든 Line worktree 및 적용 project의 ProofLine governance: 공용 `proofline ...`
  - 구현 대상 project의 source build·test: 해당 project가 정의한 command와 environment
- Application project의 `pyproject.toml`, lockfile와 `.venv`를 공용 ProofLine 설치·실행 과정에서 변경하지 않는다.

## Out of Scope

- GitHub Issue #9의 `proofline update` CLI 구현
- PyPI publication, Git tag·GitHub Release 또는 공식 latest release channel 정의
- ProofLine package의 자동 update, rollback 또는 version pinning 정책
- `.proofline/` schema migration 또는 canonical artifact 자동 변환
- ProofLine CLI가 Git branch, worktree, commit, merge, push 또는 lifecycle transition을 수행하는 기능
- 여러 main governance 변경의 병렬 승인이나 main 직렬화 원칙 변경
- Automatic main merge, delivery 판정 또는 worktree 강제 삭제
- Application project의 dependency·lockfile·`.venv` 변경
- 구현 대상 project의 source build·test environment 생성·공유·관리 정책
- Hosted CI, Python version matrix 또는 branch protection
- Remote branch push
- Credential, token 또는 secret 생성·저장

## Risks and Unknowns

### Risks

- User-level 공용 ProofLine environment는 모든 적용 project가 같은 installed version을 사용하게 한다. Project별 version compatibility와 update/rollback은 Issue #9의 독립 Discovery가 해결하기 전까지 수동 관리 경계로 남는다.
- `.worktrees/` 아래 nested checkout은 일반 filesystem search가 main tree와 implementation tree를 함께 탐색하게 만들 수 있다. Workflow는 명령별 working directory를 명시하고 repository search 범위를 혼동하지 않아야 한다.
- 공용 ProofLine tool environment와 구현 대상 project의 source build·test environment를 혼동하면 governance command가 project dependency 또는 worktree source를 잘못 사용할 수 있다. Workflow는 실행 executable과 environment 소유권을 명시해야 한다.
- Non-editable local-source `uv tool` 설치는 source checkout 변경을 자동 반영하지 않는다. 이 Line에서는 자동 update를 추가하지 않으며 재설치·update 정책은 Issue #9에서 결정한다.

### Assumptions

- 모든 적용 project가 동일한 user-level ProofLine tool environment를 공유한다는 운영 결정을 사용자가 채택했다.
- Main과 모든 Line worktree는 별도 ProofLine venv를 만들지 않고 동일한 user-level `uv tool` ProofLine environment를 사용한다는 운영 결정을 사용자가 채택했다.
- Git worktree directory는 clone이 아니라 main repository와 Git object database를 공유하는 linked worktree다.
