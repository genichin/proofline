# 안전한 Line initialization transaction

## Problem

`proofline line init`은 preflight에서 `.proofline`, `.proofline/lines`와 target 부재를 검사한 뒤 project root의 임시 directory를 `os.rename()`으로 target에 옮긴다. Preflight와 commit 사이에 parent가 외부 directory symlink로 교체되면 repository 밖에 Line artifact를 생성할 수 있고, 경쟁자가 빈 target directory를 먼저 만들면 POSIX rename이 이를 충돌로 거부하지 않고 교체할 수 있다. 또한 template, rendering, rendered validation, write, rename과 cleanup failure에 대해 실행 전후 tree 전체가 byte-for-byte 불변이고 ProofLine-owned 임시 artifact가 남지 않는다는 `ac-0004` 계약을 현재 tests가 완전하게 입증하지 않는다. 따라서 Line bootstrap의 no-overwrite·all-or-nothing 보장이 실제 filesystem race와 일반 failure에서 아직 충분히 고정되지 않았다.

## Evidence

- GitHub Issue [#1](https://github.com/genichin/proofline/issues/1)은 preflight 이후 `.proofline/lines` parent가 symlink로 교체되는 race, 빈 target directory의 POSIX rename 교체, stable `LineInitError`, 외부 path와 기존 tree 보존 및 실제 filesystem regression을 요구한다.
- GitHub Issue [#5](https://github.com/genichin/proofline/issues/5)는 template unavailable, unresolved variable, rendered validation, write·rename failure를 주입하고 tracked·untracked recursive tree와 file bytes, 임시 directory cleanup 및 stable diagnostic을 검증하도록 요구한다.
- `src/proofline/line_writer.py:66-90`은 `.proofline`과 `.proofline/lines`를 pathname으로 검사하고 target 부재를 확인하지만 parent directory identity를 commit까지 고정하지 않는다.
- `src/proofline/line_writer.py:181-191`은 Git root, safe path, project validation, ID history, rendering과 rendered validation을 순차 수행하고 dry-run은 이 결과를 공유한다.
- `src/proofline/line_writer.py:201-218`은 project root에 `.<line-id>-*` staging directory를 만들고 두 artifact를 쓴 뒤 target을 다시 pathname으로 검사하고 `os.rename(temp, target)`을 수행한다. `FileExistsError`만 stable `line.path.exists`로 변환하고 cleanup은 `temp.exists()`와 recursive `shutil.rmtree()`에 의존한다.
- Linux 임시 filesystem 직접 재현에서 non-empty source directory를 existing empty target directory로 `os.rename()`했을 때 `empty_target_replaced=True`였으며, 안전하다고 검사한 `lines` directory를 외부 directory symlink로 교체한 뒤 같은 pathname에 rename했을 때 `outside_write_after_parent_swap=True`였다. 이는 mocked exception이 아니라 현재 OS pathname·rename 동작이다.
- `tests/test_line_init.py:106-118`은 실행 전 존재한 non-empty target의 sentinel 보존을 확인하고, `tests/test_line_init.py:139-158`은 실행 시작 전 존재한 static `.proofline` symlink를 거부한다. 그러나 preflight 이후 parent replacement는 재현하지 않는다.
- `tests/test_line_init.py:183-197`은 `os.rename`을 monkeypatch하여 `FileExistsError`를 발생시키고 staging cleanup을 확인하지만, 실제 OS의 empty-target replacement와 external parent traversal을 검증하지 않는다.
- 현재 `tests/test_line_init.py`에는 template read, unresolved rendering variable, `_validate_rendered`, artifact write, descriptor/rename cleanup failure별 recursive snapshot regression이 없다.
- Active `ac-0004`는 write 전 fixed `.proofline` root·symlink·ID·template·collision 검사, dry-run parity, no-overwrite, 성공 시 두 artifact 모두 생성, 실패 시 byte-for-byte tree 불변과 실제 CLI recursive snapshot 검증을 이미 소유한다. `ac-0005`는 이 의미가 `ac-0004`에 통합되어 retired 상태다.
- Line 0014의 project initialization transaction은 atomic no-replace target appearance, external winner 보존, ProofLine-owned rollback과 failure diagnostics를 구현·검증했으므로 Line init에 적용할 수 있는 repository-local 선례가 있지만 두 writer의 artifact topology와 commit 단위는 서로 다르다.

## Scope

- 기존 `proofline line init line-NNNN --title TITLE [--dry-run]` interface와 canonical output인 `not_started` Line 및 `draft` Discovery 두 artifact를 유지한다.
- Preflight 이후 `.proofline` 또는 `.proofline/lines` parent가 외부 symlink나 다른 filesystem object로 교체되는 최소 race를 탐지하고 repository 밖에 artifact를 생성하지 않는다.
- Commit 경계에서 target file·symlink·directory가 먼저 나타나는 경쟁을 atomic no-replace failure로 처리하며, 경쟁 주체가 생성한 target과 기존 project tree를 수정·삭제하지 않는다. 특히 existing empty target directory도 교체하지 않는다.
- Concurrency 보장은 preflight 이후 `.proofline/lines` parent가 한 번 external symlink·다른 object로 교체되는 race와 atomic no-replace commit 경계의 target appearance 및 ProofLine-owned rollback까지 포함한다.
- 성공 시 canonical target directory에 두 artifact를 모두 생성하고, 일반 failure와 보장 대상 race에서는 실행 전 project tree를 byte-for-byte 보존하며 ProofLine invocation이 소유한 staging·partial artifact를 남기지 않는다.
- Dry-run과 actual은 Git-root, topology·symlink, target/history, package template rendering과 rendered validation preflight를 공유하되 dry-run은 project filesystem을 변경하지 않는다.
- Template missing·malformed/unresolved variable, rendered validation, staging identity, artifact write, commit, descriptor close, rollback과 cleanup failure를 typed stable diagnostic으로 반환하고 primary·secondary failure evidence를 유실하지 않는다.
- Failure tests는 tracked·untracked path, type, symlink target와 file bytes를 포함하는 recursive snapshot을 사용하고 실제 Linux filesystem에서 parent replacement와 empty-target race를 재현한다.
- Source와 exact installed candidate wheel에서 success, dry-run, collision, failure cleanup과 `proofline validate` E2E를 검증한다.
- AC admission은 active `ac-0004`의 독립·장기 동작 의미를 변경하지 않고 구현·검증 공백을 채우는 `satisfy`로 분류한다. `create`, `update`, `retire` 대상은 없으며 retired `ac-0005`는 재활성화하지 않는다.

## Out of Scope

- Issue #2의 deleted Git ref 이후 영구 Line ID 재사용 차단과 별도 identity registry·retention policy
- Issue #3의 `line-0000` 허용 여부와 Line ID syntax·numbering policy 변경
- `proofline project init` transaction, project topology schema 또는 user-level `~/.proofline/` lifecycle 변경
- Existing malformed Line이나 partial target의 자동 repair, merge 또는 overwrite
- Package release publication, version bump, tag, release checksum과 updater 실행
- Windows filesystem에서 Linux와 동일한 race primitive를 강제하는 구현; portable observable contract와 platform-specific verification 범위는 REQ에서 구분한다.
- 동일 OS 권한 actor의 private staging takeover, syscall interposition 또는 각 filesystem syscall 사이에서 path를 반복 교체하는 adversarial 공격

## Risks and Unknowns

### Risks

- Pathname을 반복 검사하는 방식만으로는 parent replacement와 commit 사이의 race를 닫을 수 없으므로 directory identity 또는 anchored filesystem operation과 실제 target filesystem의 atomicity를 근거로 설계해야 한다.
- Linux의 directory rename은 existing empty target을 교체할 수 있어 `exists()` 재검사와 `FileExistsError` 처리만으로 no-replace를 보장할 수 없다.
- Rollback·cleanup이 pathname identity를 확인하지 않으면 경쟁 주체의 target이나 staging으로 가장한 외부 data를 삭제할 수 있으므로 ProofLine-owned identity와 schema-known path만 정리해야 한다.
- Stronger no-replace primitive와 parent anchoring의 availability가 OS·filesystem별로 다를 수 있으므로 unsupported capability를 mutation 전 typed failure로 처리할지 platform support 범위를 제한할지 REQ에서 명시해야 한다.
- Fault-injection tests가 helper mocking에만 의존하면 실제 syscall semantics와 divergence가 재발할 수 있으므로 최소 race는 실제 filesystem test와 fault tests를 함께 유지해야 한다.
