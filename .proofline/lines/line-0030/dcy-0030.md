# Updater bootstrap과 v0.6.0 corrective release 전환 경계

## Problem

실제 사용 중인 배포 기준선 `v0.6.0`의 updater는 target wheel을 설치하기 전에 실행 중인 구 버전의 parser로 target `proofline_home/**`를 해석한다. Future target이 구 버전에 없던 managed root를 추가하면 official wheel과 checksum이 유효해도 target code가 실행되기 전에 update가 실패한다. `v0.6.1`과 `v0.6.2`에 current parser 수정이 포함돼 있어도 `v0.6.0` executable의 bootstrap 경계에는 도달하지 못하므로, 이를 지원되는 self-update 경로로 주장할 수 없다. 현재 `v0.6.0` 설치에서 다음 corrective release의 exact-tag installer를 사용하는 전환 경계와 그 corrective baseline 이후의 target-owned updater protocol을 분리하여 package와 managed HOME이 항상 하나의 verified target으로 수렴하도록 해야 한다.

## Evidence

- `https://github.com/genichin/proofline/issues/24`는 `v0.6.0`을 실제 배포 기준선으로 유지하고 `v0.6.1`·`v0.6.2`를 지원 기준선으로 사용하지 않으며, 기존 release object는 보존하고 현재 `v0.6.0` 설치를 다음 corrective release의 exact-tag installer로 전환한다는 제품 결정을 소유한다.
- `https://github.com/genichin/proofline/issues/22`는 official `v0.6.1` wheel의 checksum 검증은 성공했지만 `v0.6.0` updater가 `operations/legacy-nonterminal-history-migration.md`를 unknown root로 거부하여 package 설치 전에 실패했고 package·HOME·project가 무변경으로 남은 실제 재현을 기록한다. Owner comment는 compatibility bridge를 구현하지 않고 #24로 대체한다고 명시한다.
- Git tag와 GitHub Release `v0.6.0`, `v0.6.1`, `v0.6.2`는 현재 immutable public history로 존재한다.
- `git show v0.6.0:src/proofline/home_writer.py`의 `_RESOURCE_GROUPS`와 `allowed_roots`는 `contracts`, `templates`, `skills`만 허용한다. `v0.6.2`와 current source는 `operations`를 required group에 추가했지만 이 변경은 이미 실행 중인 `v0.6.0` updater의 parser를 바꾸지 않는다.
- `src/proofline/updater.py:294-302`는 current updater도 target wheel을 내려받은 뒤 현재 process의 `home_writer.payload_from_wheel()`로 target payload를 해석하고 HOME transaction을 package install 전에 준비한다. 즉 future target schema ownership은 아직 실행 중인 old code에 있다.
- `tests/test_home_update.py`의 `version_compatibility_bridge` fixture는 pre-operations `proofline_version: 0.6.0` HOME을 current code에 직접 주입해 reconciliation을 검증한다. 이는 target package code가 이미 실행된 뒤의 HOME migration을 입증하지만 actual public `v0.6.0` executable이 future target wheel을 bootstrap하는 E2E를 입증하지 않는다.
- Active `ac-0012`는 verified updater가 official wheel, package와 managed HOME을 동일 target으로 수렴시키고 실패 시 coherent previous state를 복원하는 전체 동작을 소유한다. Active `ac-0016`은 명시적 `proofline init`의 fresh HOME 초기화를 소유하므로 updater bootstrap 의미를 변경하지 않는다.
- 사용자는 Line 0030에서 이슈 #22의 original self-update bridge를 부활시키지 않고 이슈 #24의 기존 결정을 유지하도록 확정했다.

## Scope

- `v0.6.0 → v0.6.1/v0.6.2`와 `v0.6.0 → 다음 corrective release`의 기존 `proofline update`를 지원 경로로 주장하지 않는다.
- 현재 `v0.6.0` 설치 사용자가 기존 `proofline update` 대신 다음 corrective release의 exact-tag official installer와 public CLI만으로 package와 managed `~/.proofline`을 같은 target version에 수렴시키는 명시적 installer 기반 전환 경로를 제공한다.
- Installer 기반 전환은 기존 HOME의 manifest, exact managed inventory, checksum, symlink·path safety를 mutation 전에 검증한다. Valid legacy HOME은 승인된 backup 정책에 따라 보존한 뒤 target package와 HOME을 commit하고, 실패 시 mixed package/HOME 상태 없이 coherent previous state를 보존하거나 복원한다.
- Installer 기반 전환 전후 application repository의 `.proofline/`, dependency·lockfile, application environment와 Git state는 변경하지 않는다.
- 다음 corrective release를 새 updater 기준선으로 삼고, 이후 self-update는 verified target wheel을 격리 staging environment에 설치한 뒤 target wheel의 code가 target HOME inventory·schema·manifest를 생성하고 검증하는 target-owned bootstrap protocol을 사용한다.
- 실행 중인 updater는 immutable release metadata·wheel·checksum 검증, staging process 실행, protocol 결과 검증과 package/HOME transaction orchestration만 소유한다. Old updater의 hard-coded resource root allowlist로 future target HOME을 해석하지 않는다.
- Bootstrap protocol은 최소 protocol schema version, target package version, HOME manifest version, wheel SHA-256과 staged payload digest를 결속하고 unknown·incompatible·malformed 결과를 project mutation 전에 거부한다.
- Current `version_compatibility_bridge` 계열 HOME reconciliation은 target package code가 설치·실행된 이후 valid predecessor HOME을 target schema로 수렴시키는 post-install migration으로 이름과 계약을 한정한다. 이를 public `v0.6.0` executable self-update 증거로 사용하지 않는다.
- 실제 official `v0.6.0` wheel/executable 설치에서 corrective release의 exact-tag installer를 통한 isolated 전환 E2E와, 새 corrective baseline의 actual installed executable에서 future-schema candidate까지의 self-update E2E를 fixture 기반 unit/integration test와 별도로 필수 검증한다.
- AC admission은 `update: ac-0012`로 분류한다. `ac-0016`의 fresh `proofline init` 의미는 변경하지 않으며 create·retire·satisfy 대상은 없다. Corrective version·tag·asset과 public read-back은 release evidence이며 active AC로 만들지 않는다.

## Out of Scope

- 이슈 #22의 original `v0.6.0 → corrective target` self-update compatibility bridge 부활
- 기존 `v0.6.1`·`v0.6.2` tag, GitHub Release, asset 또는 issue history의 삭제·overwrite·rewrite
- PyPI publication과 mutable latest 또는 alternate artifact·source checkout fallback 지원
- Application project `.proofline/` migration이나 schema 변경
- Line·Discovery·REQ·AC lifecycle 또는 updater와 무관한 validator 변경
- Optional threat model, broad platform matrix 또는 사용자·agent actor 인증 확대
- Discovery·implementation 중 사용자 실제 HOME `/home/genichin`, 현재 user-level ProofLine tool, remote release·tag·asset 변경

## Risks and Unknowns

### Risks

- Current source parser와 fixture reconciliation이 PASS한다는 이유로 public `v0.6.0` executable bootstrap도 지원된다고 판단하면 실행 주체가 다른 결함을 다시 놓친다. Public predecessor executable subprocess E2E를 별도 gate로 유지해야 한다.
- Package install과 HOME commit의 소유권·rollback 순서가 분리되면 failure 중 mixed target이 남을 수 있다. Protocol 결과와 transaction은 하나의 selected wheel identity에 결속되고 success와 rollback 후 각각 package/HOME coherence를 read-back해야 한다.
- Installer 기반 전환의 backup 이름이나 collision 처리가 불명확하면 valid legacy HOME을 overwrite하거나 반복 실행이 임의 backup을 누적할 수 있다. Mutation 전에 deterministic policy를 확정해야 한다.
- Target staging entrypoint가 일반 installed CLI와 권한·환경을 공유하면 current user HOME이나 application cwd를 실수로 변경할 수 있다. Isolated staging HOME·tool path와 closed protocol output을 사용하고 외부 project mutation을 snapshot으로 거부해야 한다.
