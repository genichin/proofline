# Micro-SPEC 승인 전 draft 교정 chronology

## Problem

현재 계약은 후속 Line의 Micro-SPEC approval을 `A < H < S0 < S < P`로 설명하고, draft author가 clean exact `S0`에서 멈춘 뒤 correction이 필요하면 fresh exact draft와 fresh review를 요구한다. 그러나 `S0`가 최초 persisted draft인지, review blocker를 반영한 최종 approval candidate인지 명시적으로 구분하지 않는다. 이 때문에 최초 draft 뒤 substantive correction commit을 보존하면 `S0`와 status-only `S` 사이에 일반 commit이 남았다는 해석과, corrected commit 자체를 fresh `S0`로 다시 명명하면 유효하다는 해석이 동시에 가능하다.

실제 저장소에서는 승인 전 correction commit이 반복적으로 발생했고 해당 이력이 유용한 감사 근거로 남아 있다. 반면 current history validator는 `S`의 직전 commit을 암묵적으로 draft candidate로 선택할 뿐, 최초 persisted draft부터 최종 approval candidate까지의 correction chain을 lifecycle로 모델링하거나 그 구간의 허용 변경을 전수 검사하지 않는다. 따라서 현재 문서 의미와 validator의 기계적 PASS/FAIL 집합이 충분히 일치하지 않으며, 작업자가 정상 review correction을 숨기거나 branch rewrite로 제거하도록 유도할 수 있다.

승인 이후 substantive 변경을 계속 금지하면서 승인 전 교정 이력을 선형 history에 보존하려면 `S0`를 최초 persisted draft로 고정하고, 같은 Micro-SPEC만 교정하는 0개 이상의 `R` commit과 exact final review·사용자 승인·status-only `S`의 결속을 명시적인 lifecycle로 정의해야 한다.

## Evidence

- 2026-08-07T12:21:06+09:00에 확인한 GitHub Issue #25 `https://github.com/genichin/proofline/issues/25`는 현재 규칙에서 correction commit이 `S0`와 `S` 사이에 남는 문제, audit history 손실과 반복 rewrite 비용을 기록하고 `A → H → S0 → R1 → … → Rn → S → P`를 제안한다. Issue는 기존 위반의 소급 승인, 사용자 approval authority 이전과 승인 후 amendment를 명시적으로 제외한다.
- `.proofline/criteria/ac-0022.md`는 draft author가 clean exact `S0`에서 mutation을 멈추고 correction 뒤 fresh exact draft와 fresh review를 요구하지만, 최초 draft와 corrected final draft에 서로 다른 lifecycle identity를 부여하지 않는다. 같은 AC는 `S.parent=S0`, stale review 거부와 approval commit의 substantive bytes 불변을 요구한다.
- `.proofline/criteria/ac-0021.md`, `docs/contracts/micro-spec-and-iqc.md`, `docs/contracts/line-delivery.md`, `skills/proofline-approve-specification/SKILL.md`와 `skills/proofline-start-implementation/SKILL.md`는 후속 Line chronology를 `A < H < S0 < S < P < I < Q`로 설명한다. `docs/contracts/micro-spec-and-iqc.md`는 correction에 fresh `S0`가 필요하다고만 기록하여 old draft commit을 보존할지 교체할지 명확히 소유하지 않는다.
- `src/proofline/implementation_history.py`의 `_validate_specification_chronology()`는 normal approval `S`를 찾은 뒤 `draft = specification - 1`로 직전 commit만 approval candidate로 간주한다. 직전 draft와 `S`가 각각 대상 Micro-SPEC 한 path만 변경하고 `S`가 status-only인지 검사하지만, 최초 post-`H` draft를 식별하거나 그 뒤의 모든 correction commit이 같은 Micro-SPEC의 `draft/not_started` bytes만 변경했는지 검사하지 않는다.
- `tests/test_implementation_history.py`의 positive fixture는 한 번의 `S0 → S`만 만들고, `s-not-direct` negative fixture는 최종 draft와 `S` 사이에 unrelated `.proofline/review-note.md`를 삽입한다. 여러 same-path draft correction을 허용하는 positive fixture, correction 중 다른 canonical·제품·test path 변경, correction 중 status 변경, stale final review binding을 각각 독립 판정하는 matrix는 없다.
- Real-Git first-parent 조사에서 Line 0021은 `H → d7b8825(draft) → aea88e8(correction) → edbdc53(S)`, Line 0022는 `H → fee3967(draft) → 9a3f902(correction) → cc78b6c(S)` 이력을 가진다. 두 correction은 해당 Micro-SPEC 한 path만 변경했고 `spec_status: draft`, `implementation_status: not_started`를 유지했다. Line 0023과 0024는 각각 한 persisted draft 뒤 status-only approval을 기록했다.
- Line 0025 init 직전과 init commit `ae3297a` 직후 source-backed `PYTHONPATH=src proofline validate`는 exit 0으로 PASS했다. 따라서 현재 repository는 valid baseline이며 이 변경은 existing validation failure를 숨기기 위한 복구가 아니라 approval-before-correction 의미를 명시적으로 확장·강화하는 prospective governance 변경이다.

## Scope

- `ac-0022`를 `update`하여 `S0`를 exact `H` 뒤 최초로 persisted된 대상 Micro-SPEC draft로 정의하고, 0개 이상의 substantive correction commit `R1..Rn`을 거쳐 최종 draft commit을 independent review와 사용자 approval의 exact target으로 삼는 ownership choreography를 정의한다. Correction이 없으면 final target은 `S0`이고 `R*=0`이다.
- `ac-0021`을 `update`하여 후속 Line의 strict first-parent chronology를 `A < H < S0 < R* < S < P < I < Q`로 확장한다. 각 `R`은 대상 Micro-SPEC 한 path만 변경하고 `spec_status: draft`, `implementation_status: not_started`를 유지해야 하며, 다른 canonical artifact·제품 source·test·build/runtime path 또는 lifecycle start 변경이 섞이면 stable diagnostic으로 거부한다.
- Final review evidence와 user-approval evidence는 동일한 exact final draft commit과 tree에 결속하고, `S.parent`가 그 exact final draft이며 `S`가 `spec_status: draft → approved`만 포함하는지 유지한다. Old `S0` 또는 중간 `R`에 대한 stale review·approval, final target 이후 concurrent mutation, body-changing `S`와 recorder-only approval은 계속 fail-closed한다.
- `P.parent == S`와 `P`의 implementation status-only 의미, 승인 이후 substantive amendment의 기존 draft 회귀·재승인 규칙을 유지한다. 이 Line은 approval 전 correction chronology만 변경한다.
- 새 규칙의 activation boundary는 Line 0025의 updated AC approval baseline `A`로 둔다. 그 이전 REQ approval cycle은 기존 validator 의미로 보존하고 historical artifact를 rewrite하거나 새 명칭을 소급 기록하지 않는다. Line 0025와 이후 approval cycle에서는 `R*=0`인 기존 direct flow와 `R*>0` correction flow를 모두 새 규칙으로 검사한다.
- `src/proofline/implementation_history.py`, standalone approval authority audit, 관련 contract·operation·skill·template와 source/wheel packaged resource를 같은 final-target·actor-separation·chronology 의미로 동기화한다. 외부 review/user evidence JSON v1의 schema를 바꿀 필요가 없다면 그대로 유지하고 target 해석만 final draft commit으로 명확히 한다.
- Real-Git TDD에 `R*=0`, 단일 `R`, 복수 `R` positive와 off-path correction, correction 중 spec/implementation status 변경, stale intermediate review, non-direct/body-changing `S`, `P` 선행, malformed historical correction, pre-activation compatibility negative를 각각 독립 scenario로 추가한다. Source validator, isolated installed-wheel validator와 wheel-extracted packaged helper가 같은 scenario ID·diagnostic·no-mutation 결과를 제공해야 한다.
- REQ admission은 기존 AC 두 개의 observable PASS/FAIL 집합을 바꾸므로 `criteria.update = [ac-0021, ac-0022]`로 계획한다. 새 독립 장기 사양을 만들거나 기존 AC를 retire/satisfy하지 않는다.

## Out of Scope

- 기존 Line의 commit, canonical artifact, review evidence 또는 approval history rewrite와 과거 chronology 위반의 소급 승인
- 사용자 approval authority를 reviewer, 구현자, governance recorder 또는 자동화에 이전하는 변경
- `S` 이후 Micro-SPEC substantive amendment를 `R`로 취급하거나 기존 draft 회귀·재승인 절차를 우회하는 변경
- Micro-SPEC implementation, IQC, rework, main-first integration, DQC, delivery와 hosted/provider policy chronology의 재설계
- 여러 Micro-SPEC 또는 제품 변경을 하나의 correction commit에 묶는 batch approval flow
- Git branch/worktree 자동 mutation, remote push, tag, GitHub Release, package publication과 Issue #25 자동 close

## Risks and Unknowns

### Risks

- `S0` 의미를 최초 persisted draft로 바꾸면서 existing helper와 문서가 final reviewed draft를 `S0`로 부르는 표현을 일부 남기면 stale review 판정과 사람의 운영 절차가 다시 어긋날 수 있다. Contract, AC, skill, template, test scenario registry와 packaged bytes를 같은 terminology로 전수 동기화해야 한다.
- 단순히 `S.parent`만 final target에 결속하고 `H..S`의 중간 commit을 검사하지 않으면 제품 변경이나 다른 artifact mutation이 approval 전 correction으로 세탁될 수 있다. Validator는 최초 `S0`부터 final target까지의 모든 first-parent commit path와 status를 감사해야 한다.
- 새 activation boundary를 기존 `ac-0022` 최초 activation과 혼동하면 과거 valid Line을 새 의미로 소급 판정할 수 있다. Updated AC revision의 exact approval commit을 prospective boundary로 식별하고 pre-boundary compatibility fixture를 유지해야 한다.
- Micro-SPEC이 여러 개인 Line에서 각 approval chain이 겹치면 target 밖 path 변경 금지와 충돌할 수 있다. 각 Micro-SPEC의 `S0 → R* → S`를 직렬화하고 해당 chain 안에서는 그 Micro-SPEC 한 path만 변경하도록 계약과 fixture를 일치시킨다.

### Assumptions

- Review correction은 승인 전 substantive Micro-SPEC body 교정이며 REQ·AC 의미를 바꾸지 않는다. REQ·AC PASS/FAIL 또는 Discovery scope가 바뀌면 `R`이 아니라 기존 governance draft 회귀·재확인·재승인 절차를 사용한다.
- Uncommitted draft를 여러 번 고친 뒤 처음 persisted한 commit이 final candidate라면 그 commit이 `S0`이고 `R*=0`이다. `R`은 Git에 실제로 persisted된 post-`S0` correction만 의미한다.
- Existing review/user evidence v1은 exact target commit·tree와 review digest를 이미 표현하므로 schema 추가 없이 final draft target을 결속할 수 있다. 구현 조사에서 schema 변경이 불가피하면 approved scope를 확대하지 않고 specification review에서 blocker로 보고한다.
