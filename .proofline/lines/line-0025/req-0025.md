# Micro-SPEC 승인 전 draft 교정 chronology

## Objective

Micro-SPEC의 최초 persisted draft와 review correction 이력을 Git first-parent chronology에 그대로 보존하면서, 최종 approval candidate에 대한 독립 review·사용자 승인·status-only 승인 및 구현 시작 경계를 exact commit·tree·path·bytes digest로 fail-closed 검증한다.

## Scope

- `ac-0022`를 update하여 최초 persisted Micro-SPEC draft `S0`, 0개 이상의 same-target correction commit `R1..Rn`, 최종 draft를 대상으로 한 independent review와 사용자 approval, direct-child status-only approval `S`의 ownership choreography를 정의한다.
- `ac-0021`을 update하여 후속 Line의 strict first-parent chronology를 `A < H < S0 < R* < S < P < I < Q`로 확장하고, `R*=0` direct flow와 하나 이상의 correction을 보존한 flow를 모두 검증한다.
- 각 `R`은 대상 Micro-SPEC canonical path 하나만 변경하고 `spec_status: draft`, `implementation_status: not_started`를 유지해야 한다. 다른 Micro-SPEC, REQ·AC·Line·evidence, 제품 source, test, build 또는 runtime path가 섞인 correction은 거부한다.
- 여러 Micro-SPEC을 작성할 때에는 각 `S0 → R* → S → P` chain을 직렬화한다. 한 target의 approval chain 안에서 다른 target의 draft·approval·implementation lifecycle을 interleave하거나 batch approval하지 않는다.
- Post-activation independent-review와 user-approval evidence에 동일한 exact target commit·tree·canonical Micro-SPEC path·bytes SHA-256을 결속하는 closed v2 schema를 도입한다. User evidence는 exact review evidence file digest도 결속하며 v1/v2 혼합, stale intermediate target, path·digest mismatch와 actor separation 위반을 거부한다.
- `S`는 final draft의 direct non-merge child이며 target Micro-SPEC의 `spec_status: draft → approved`만 변경해야 한다. `P`는 `S`의 direct child이며 같은 Micro-SPEC의 `implementation_status: not_started → in_progress`만 변경해야 한다.
- 새 규칙은 Line 0025의 updated REQ·AC approval baseline `A`부터 prospective하게 적용한다. 그 이전 cycle은 기존 validator 의미를 보존하고, Lines 0021·0022와 동형인 기존-valid same-path correction history를 새 규칙으로 소급 거부하지 않는다.
- Contract, validator, standalone approval audit, operation skill·template와 packaged resource를 같은 chronology·authority·evidence 의미로 동기화하고 source CLI, isolated installed-wheel CLI와 wheel-extracted helper의 Real-Git parity를 검증한다.

## Constraints

- Historical canonical artifact와 Git history를 rewrite·squash·rebase하거나 corrected draft를 새 `S0`로 재명명하지 않는다.
- Post-activation `R` 구간의 허용 변경은 commit message나 timestamp가 아니라 exact first-parent diff와 canonical status bytes로 판정한다.
- Existing evidence v1은 pre-activation compatibility에만 사용하고 post-activation approval authority로 승격하지 않는다.
- Review helper와 validator는 supplied evidence를 read-only로 검사하며 review evidence, 사용자 승인 또는 Git lifecycle commit을 생성·보완하지 않는다.
- Approval 전 substantive correction과 approval 후 amendment를 혼합하지 않는다. Approval 후 의미 변경은 기존 draft 회귀·fresh review·재승인 lifecycle을 따른다.
- Repository 안에 `.venv`, `.pytest_cache`, `__pycache__` 또는 `*.pyc`를 생성·유지하지 않고 disposable repository-external 환경에서 build·installed-wheel 검증을 수행한다.

## Non-Goals

- 승인 후 Micro-SPEC amendment·rework lifecycle, implementation·IQC·DQC·integration·delivery chronology의 일반 재설계
- REQ·AC 변경, 여러 Micro-SPEC의 batch approval 또는 여러 Line의 concurrent approval chain 지원
- Historical Line·evidence migration, Git history 재작성 또는 과거 validation 결과 재판정
- Evidence actor의 암호학적 신원 인증, signature·key management 또는 외부 approval service 도입
- Release version 변경, tag·package·asset publication, remote branch mutation 또는 provider-specific CI authority 추가
