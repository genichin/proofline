# Hosted candidate harness clean-runner preflight

## Problem

ProofLine의 mandatory hosted candidate workflow는 exact integration candidate를 remote `candidate/**` ref에 push한 뒤 attempt 1에서 처음 clean runner 조건을 실행한다. Local warm cache와 checkout state가 dependency provisioning·command construction·외부 상태 의존성을 가리면 product candidate가 이미 IQC와 local integration admission을 통과한 뒤 hosted harness 자체에서 실패하며, same-candidate retry를 금지하는 현재 정책 때문에 새 `P → I → Q → V` correction cycle이 필요해진다.

현재 repository에는 empty dependency cache와 clean temporary environment에서 candidate harness의 실행 가능성을 push 전에 검사하는 executable preflight가 없다. Workflow contract tests는 YAML command 문자열과 wheel 전달 형태를 정적으로 검사하지만, clean cache에서 dependency resolution이 가능한지 또는 candidate command가 아직 존재하지 않는 public Release 같은 외부 상태에 의존하는지는 실행하지 않는다. 따라서 hosted DQC authority를 대체하지 않으면서 harness-owned 실패를 remote attempt 1 전에 좁게 탐지하는 별도 preflight가 필요하다.

## Evidence

- GitHub Issue [#19](https://github.com/genichin/proofline/issues/19)는 Line-0020 integration candidate `355842ff5951cf3f88e0c6520880a2169f4f4094`의 hosted run [`31051563486`](https://github.com/genichin/proofline/actions/runs/31051563486), attempt 1을 근거로 한다. API read-back에서 `build-candidate` job `92459666004`는 failure였고 Ubuntu job `92459720598`과 Windows job `92459720439`는 skipped였다. Exact wheel build 뒤 `uv pip install --offline <exact-wheel> pytest>=8`이 fresh runner cache에 없는 pytest를 resolve하지 못한 것이 원인이었다.
- `.github/workflows/candidate-verification.yml:28-60`은 candidate wheel을 한 번 build하고 `PROOFLINE_HOSTED_CANDIDATE_WHEEL`을 넘겨 `candidate_build_only` tests를 실행한다. `:62-112`와 `:114-170`은 Ubuntu와 Windows consumer를 구성하지만 workflow는 `candidate/**` push 뒤에만 시작하며 pre-push executable preflight entrypoint를 제공하지 않는다.
- `tests/helpers/line_0020_scenario_runner.py:124-130`의 current correction은 exact wheel path와 `pytest>=8`을 함께 설치하며 `--offline`을 제거했다. `tests/test_line_0020_scenario_registry.py:106-113`은 그 argv를 정적으로 고정하지만 empty `UV_CACHE_DIR`에서 실제 provisioning을 실행하는 repository-level preflight는 없다.
- Repository source와 `.github/` 및 candidate contract tests를 조사한 결과 tracked clean-runner preflight helper가 없고 `UV_CACHE_DIR`을 비우거나 격리하는 candidate preflight contract도 없다. 따라서 local warm cache PASS와 clean-cache PASS를 구분할 수 없다.
- Official `v0.6.0` publication 준비 중 실행된 optional candidate run [`31060280185`](https://github.com/genichin/proofline/actions/runs/31060280185), attempt 1은 exact head `a9902f5c8297af04dd57c110a56787528a61074d`에서 build job `92486538951`과 Ubuntu job `92486663372`가 PASS했지만 Windows job `92486663391`이 FAIL했다. `.github/scripts/verify-windows-candidate.ps1:227-230`이 candidate version의 public GitHub Release가 publication 전에 이미 존재한다고 가정해 `proofline update --check --version $Version`을 호출한 외부 상태 의존성이 원인이었다. 이 run은 Line DQC authority가 아닌 optional release-time execution이었지만, command의 외부 상태 전제를 push 전에 분류하지 못하는 동일한 discovery gap을 보여 준다.
- Current mandatory hosted workflow는 exact SHA checkout, single wheel build, checksum/provenance와 Ubuntu·Windows consumer evidence를 소유한다. Clean preflight가 이 remote run/job/artifact evidence를 생성하거나 DQC PASS authority를 가질 필요는 없다.

## Scope

- Clean-runner preflight의 최대 실행 범위를 dependency/cache/network policy, exact wheel identity와 checksum, Ubuntu/Windows command construction 및 외부 상태 의존성을 검사하는 contract layer로 제한한다. Native Windows candidate transaction의 실행과 판정은 mandatory hosted Windows job이 계속 소유한다.
- 새 version-independent acceptance behavior의 `create` 후보로, candidate push 전에 실행하는 non-authoritative clean-runner harness preflight와 그 executable entrypoint를 정의한다.
- Empty `UV_CACHE_DIR`, clean temporary environment와 repository-local environment 비사용을 고정해 warm-cache 의존성을 탐지한다.
- Exact candidate wheel path·filename·SHA-256을 입력으로 고정하고, harness dependency provisioning 중 source rebuild·fallback build·alternate ProofLine distribution 선택을 거부한다.
- Test-only dependency의 online/offline policy를 명시한다. Online mode는 exact ProofLine wheel identity와 별도로 harness dependency만 resolve해야 하며, offline mode는 필요한 distribution이 모두 pre-provision되지 않으면 remote push 전에 stable diagnostic으로 실패해야 한다.
- Candidate workflow와 source·packaged helper의 Ubuntu/Windows command construction, exact wheel argv, checksum 순서 및 network policy parity를 검증한다.
- Harness command가 public Release 존재, mutable latest endpoint 또는 다른 publication 상태에 의존하면 이를 explicit external-state requirement로 분류하고, 선택된 preflight 경계 안에서는 deterministic fixture 또는 contract probe로 push 전에 탐지한다.
- Preflight success/failure가 hosted run ID·job ID·artifact ID 또는 DQC result로 해석되지 않도록 outcome과 evidence schema를 분리한다.
- Preflight failure는 remote candidate ref를 생성·갱신하거나 hosted workflow를 시작하기 전에 현재 owner Line으로 반환하며 Git refs·index·worktree와 application/HOME state를 변경하지 않는다.
- Workflow/helper contract tests, empty-cache executable regression, warm-cache negative control과 no-mutation 검증을 추가한다.

## Out of Scope

- Local preflight로 mandatory hosted Ubuntu/Windows attempt 1 또는 exact run/job/artifact read-back을 대체하는 변경
- Hosted DQC authority, same-candidate retry 금지, fresh `P → I → Q → V` rework semantics 또는 candidate ref policy 변경
- Windows candidate transaction 전체를 Linux에서 재현하거나 hosted Windows runtime evidence라고 주장하는 기능
- Production updater·installer의 host allowlist, Release discovery, checksum, update transaction 또는 user-facing CLI 동작 변경
- GitHub Actions runner·service·network 전체를 로컬에서 완전히 모사하는 기능
- Remote candidate push, workflow dispatch, main integration, tag, GitHub Release, package publication 또는 public asset read-back 자동화
- Issue #17의 usage attribution과 Issue #18의 batch threat-model review contract

## Risks and Unknowns

### Risks

- Preflight가 hosted workflow와 별도로 command를 복제하면 양쪽이 drift하여 false PASS를 만들 수 있다. Shared command/resource owner와 source·packaged·workflow parity를 acceptance boundary로 둬야 한다.
- Empty-cache test가 unrestricted network availability까지 제품 요구로 바꾸면 transient index 장애를 product defect로 오분류할 수 있다. Exact wheel identity와 test-harness dependency network policy를 별도 결과로 기록해야 한다.
- Windows command construction의 정적 검증을 native Windows execution으로 과장하면 platform-specific quoting·PowerShell behavior를 놓칠 수 있다. Local preflight evidence와 hosted Windows evidence의 authority를 분리해야 한다.
- Preflight를 전체 transaction emulation으로 확대하면 attempt 1 실패 비용을 줄이려다 별도 harness 복잡도와 유지 비용을 더 크게 만들 수 있다.

### Assumptions

- `uv`의 격리된 cache/environment option으로 Linux에서 empty dependency cache와 exact local wheel provisioning을 재현할 수 있다.
- Native Windows runtime behavior는 계속 hosted Windows job이 소유하며, local preflight는 shared command construction과 external-state contract까지만 검증할 수 있다.
- Preflight는 remote write 없이 실행 가능하며 실패 시 canonical artifact, Git refs, index/worktree, project와 HOME을 변경하지 않아야 한다.
