# DQC를 Line-level 위험과 exact binding 중심으로 간소화

## Problem

ProofLine의 DQC 계약은 integration candidate를 Line 전체 관점에서 검증하도록 정의하지만 IQC와 DQC가 각각 소유하는 검사와 DQC 재실행 조건을 구분하지 않는다. 실제 운영에서는 Micro-SPEC IQC에서 이미 exact implementation commit을 대상으로 통과한 focused test, package·skill 형식, compile 또는 lock 검사를 DQC가 다시 수행해 왔다. 이 중복은 Line-level 회귀·coverage·candidate binding·통합 가능성이라는 DQC의 핵심 신호를 흐리고 ProofLine 절차를 필요 이상으로 무겁게 만든다.

## Evidence

- GitHub Issue [#8](https://github.com/genichin/proofline/issues/8)은 Line 0002 DQC가 IQC에서 수행한 wheel resource, skill 형식, compile과 lockfile 검사를 반복한 문제와 DQC 간소화 완료 조건을 기록한다.
- `docs/contracts/line-delivery.md:97-117`은 DQC가 모든 Micro-SPEC이 합쳐진 exact candidate를 검증하고 AC 배정, IQC PASS, Micro-SPEC 간 충돌·회귀, 전체 test와 REQ 범위를 확인한다고 정의하지만 IQC evidence 재사용과 조건부 재실행 기준은 정의하지 않는다.
- 같은 계약 `line-delivery.md:176-196`은 main integration에 필요한 lifecycle state, canonical validation, placeholder, IQC·DQC exact commit binding을 이미 별도 gate로 정의한다.
- `.proofline/lines/line-0002/micro-specs/iqc-0002-001.md:17-25`는 focused CLI·safety·wheel test, canonical validation과 wheel resource를 implementation commit에서 검증했다.
- `.proofline/lines/line-0002/dqc-0002.md:25-45`는 전체 test와 canonical validation에 더해 compile, lockfile, wheel build·resource와 skill 형식을 다시 검사했다.
- `.proofline/lines/line-0005/micro-specs/iqc-0005-001.md:17-27`은 focused tests, transition audit, skill validation, canonical validation과 diff check를 수행했다.
- `.proofline/lines/line-0005/dqc-0005.md:22-34`는 전체 test, candidate binding과 fast-forward에 더해 canonical validation, compile, lock, diff와 skill validation을 다시 수행했다.
- `templates/schema-v1/artifacts/dqc.md`의 Checks 표는 Line 전체 검사 기록 형식만 제공하며 필수 DQC 신호, IQC evidence 재사용과 조건부 검사 기준을 구분하지 않는다.
- 사용자는 현재 ProofLine이 너무 많은 제약을 걸지 않도록 유지하고 새 hard gate보다 중복 절차를 줄이는 방향을 우선하도록 결정했다.

## Scope

- IQC는 Micro-SPEC의 exact implementation commit에서 focused behavior, component-specific safety, package·skill 형식과 구현별 정적 검사를 소유한다.
- DQC의 기본 필수 검사를 다음 Line-level 신호로 한정한다.
  1. 모든 non-withdrawn Micro-SPEC의 approved·implemented 상태와 대응 IQC `passed`
  2. REQ→AC→Micro-SPEC→IQC coverage와 exact commit binding
  3. 모든 구현이 합쳐진 candidate의 전체 regression test
  4. Candidate canonical `proofline validate`
  5. Micro-SPEC 간 충돌, 통합 위험과 Line 전체 REQ 범위
  6. Main ancestor·fast-forward 가능성과 DQC candidate 이후 제품 source 불변
- DQC는 exact binding이 유효한 passed IQC evidence를 인용할 수 있으며 동일 focused test, package·wheel, skill metadata, compile, lock 또는 설치 환경 검사를 기본적으로 반복하지 않는다.
- 다음 경우에만 관련 검사를 DQC에서 조건부로 재실행한다.
  - IQC implementation commit 이후 candidate에서 해당 component source가 변경됨
  - 여러 Micro-SPEC의 결합이 focused IQC로 판정할 수 없는 integration risk를 만듦
  - IQC evidence가 누락·stale·failed·blocked이거나 exact binding을 확인할 수 없음
  - REQ 또는 AC가 해당 검사를 명시적인 Line-level verification으로 요구함
- 조건부 검사가 적용되지 않는다는 사실은 DQC 실패가 아니며, DQC artifact는 재실행하지 않은 이유와 사용한 IQC binding을 기록한다.
- `docs/contracts/line-delivery.md`, canonical DQC template과 repository-owned DQC workflow/checklist를 필수·조건부 책임 분리에 맞춘다.
- Temporary repository와 representative Line fixtures에서 필수 DQC 검사 누락은 발견하되 관련 없는 IQC 검사를 반복하도록 강제하지 않는지 검증한다.
- `proofline validate`는 현재 canonical tree의 schema·reference validation 역할을 유지하며 DQC command 실행 목록이나 Git history를 새 hard gate로 검사하지 않는다.

## Out of Scope

- 전체 regression test, canonical validation, coverage, exact binding, fast-forward와 source immutability gate 제거
- DQC 자동 통과 또는 IQC 결과의 무검증 신뢰
- 모든 Line에 compile, lock, wheel, package, skill 또는 설치 검사를 다시 강제
- GitHub Actions, hosted CI, Python version matrix 또는 remote status check 추가
- ProofLine CLI가 test, Git commit, merge, push 또는 lifecycle transition을 실행하는 기능
- IQC·DQC artifact schema의 새로운 mandatory metadata field
- 기존 Line 0002·0005 DQC history rewrite
- `proofline update`, release source와 package distribution 정책

## Risks and Unknowns

### Risks

- Passed IQC 이후 candidate에서 관련 source가 바뀌었는데 binding만 보고 재사용하면 stale evidence가 될 수 있다. DQC는 implementation commit 이후 candidate diff와 결합 위험을 확인해 조건부 재실행 여부를 판단해야 한다.
- 조건부 기준이 추상적이면 담당자마다 검사량이 달라질 수 있다. Contract와 workflow는 대표 trigger와 기록 방법을 제공하되 모든 component type을 중앙 allowlist로 고정하지 않아야 한다.
- 검사 수 감소를 품질 기준 약화로 오해할 수 있다. 전체 regression, canonical validation, coverage, exact binding과 integration readiness는 항상 필수임을 template과 example에서 분명히 해야 한다.

### Assumptions

- IQC artifact의 passed result와 exact Micro-SPEC·implementation commit binding은 DQC가 재사용할 수 있는 canonical evidence이다.
- 전체 regression test는 여러 Micro-SPEC 결합으로 발생하는 일반적인 회귀를 검출하는 DQC의 기본 실행 검사로 유지된다.
- Component-specific 검사 재실행 필요성은 candidate diff, IQC coverage와 REQ·AC verification으로 판단하며 새로운 global validator gate가 필요하지 않다.
