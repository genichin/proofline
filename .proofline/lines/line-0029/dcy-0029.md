# Specification 승인 절차 간소화

## Problem

ProofLine의 REQ·AC 승인 workflow는 사용자의 명시적 approval과 현재 canonical validation만으로 승인 여부를 결정할 수 있는데도, 별도 status-only commit을 권장하고 immediate parent를 검사하는 optional Git transition audit를 함께 유지한다. 이 audit는 사용자 approval authority를 인증하지 않고 `recorded`와 `not recorded`를 모두 유효하게 처리하므로 승인 판정에 영향을 주지 않지만, skill·contract·helper와 전용 test surface를 늘리고 두 승인 경로를 설명하게 만든다. Specification 승인을 사용자 결정과 현재 canonical state에 기반한 하나의 절차로 단순화해야 한다.

## Evidence

- `skills/proofline-approve-specification/SKILL.md`는 status-only approval commit과 direct approval을 별도 경로로 설명하고 `audit_transition.py` 실행 및 `recorded`/`not recorded` 해석을 포함한다.
- `skills/proofline-approve-specification/scripts/audit_transition.py`는 378줄의 standalone Git helper로 approval commit과 immediate parent의 REQ·AC status transition 모양을 검사하지만, 스스로 approval authority가 아니라고 정의한다.
- `tests/test_approve_specification_skill.py`는 두 경로, helper의 Git process 격리·timeout·output limit·object replacement·artifact mode와 transition 결과를 위한 전용 fixture 및 회귀 검사를 유지한다.
- `docs/contracts/requirements-and-criteria.md`는 status-only 별도 commit을 권장 감사 경로로, prior draft가 없는 direct approval을 별도 유효 경로로 정의하면서 validator가 그 chronology를 보증하지 않는다고 명시한다.
- Retired `ac-0007`과 `ac-0009`, historical `req-0005`는 prior transition audit 의미를 보존하지만 현재 active specification은 아니다.
- 사용자는 Line 0028 이후 작업으로 optional Git transition audit와 특별한 승인 commit 절차를 제거하고, 사용자 승인 뒤 상태 변경과 `proofline validate`만 수행하는 간소화를 지시했다.

## Scope

- Repository-owned `proofline-approve-specification` skill을 `exact REQ·AC 제시 → 사용자 명시적 approval → 계약상 status 변경 → current canonical validation → 결과 보고`의 단일 흐름으로 축소한다.
- 별도 status-only approval commit을 권장하거나 direct approval과 구분하는 절차, exact approval commit을 transition evidence로 보고하는 절차를 제거한다.
- `audit_transition.py`와 그 전용 package resource 및 테스트를 제거한다.
- `docs/contracts/requirements-and-criteria.md`에서 권장 감사 경로와 direct approval 이중 경로를 제거하고, 사용자만 approval authority를 가지며 current canonical approved REQ·AC가 specification baseline을 형성한다는 계약만 유지한다.
- Installed wheel과 HOME resource가 source skill 및 제거된 helper 상태와 일치하도록 package 검증을 갱신한다.
- AC admission은 `create`로 분류한다. Retired AC를 재활성화하지 않고, 사용자 명시적 approval과 current canonical validation에 기반한 단일 specification 승인 절차를 독립 판정할 새 AC 하나를 만든다. `update`, `retire`, `satisfy` 대상은 없다.

## Out of Scope

- Discovery confirmation과 REQ·AC의 `draft`, `approved`, `withdrawn`, `active`, `retired` lifecycle 자체의 제거
- 사용자를 대신한 approval 결정, approval 자동화 또는 사용자 identity의 암호학적 인증
- 일반 Git commit 사용, 승인된 specification revision의 Git 보존 또는 기존 history 재작성
- Retired AC와 historical REQ의 기존 bytes 수정
- Micro-SPEC 독립검토·승인, 구현·IQC·DQC·delivery·release 절차
- Line 0028의 allocator 및 `line init`·`requirement init` 구현 변경

## Risks and Unknowns

### Risks

- Source skill에서만 helper를 제거하고 wheel 또는 HOME resource에 잔존시키면 설치 형태에 따라 이전 audit 절차가 다시 노출될 수 있다. Source·wheel·fresh HOME의 resource parity와 제거된 경로 부재를 함께 검증해야 한다.
- Transition audit 제거를 사용자 approval gate 제거로 오해하면 agent가 승인 authority를 행사할 수 있다. Skill과 active AC는 명시적 사용자 approval 전 status 변경 금지를 계속 요구해야 한다.
- Historical Line·REQ·retired AC의 transition 표현까지 일괄 수정하면 승인 당시 evidence를 훼손한다. 현재 contract·skill·helper·test surface만 변경하고 historical canonical artifacts는 보존해야 한다.
