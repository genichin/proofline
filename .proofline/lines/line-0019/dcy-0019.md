# DQC 전 exact hosted candidate 검증

## Problem

Line 0018은 local IQC·DQC, main fast-forward, delivery와 remote main push까지 완료한 뒤에야 자동 실행된 hosted candidate workflow의 Ubuntu·Windows 실패가 확인됐다. 해당 workflow는 Line 0018의 DQC admission에 mandatory evidence로 연결되지 않았다. Local source/isolated-wheel parity만으로는 shallow checkout과 native Windows subprocess 차이를 검출하지 못했으며, 현재 DQC 계약은 configured hosted gate의 exact remote evidence를 필수 Line-level 신호로 요구하지 않아 remote-environment 결함이 delivery 이후 발견될 수 있다.

## Evidence

- GitHub issue `#15`는 incident와 재발 방지 요구를 보존한다: https://github.com/genichin/proofline/issues/15
- GitHub Actions run `30955946035`는 exact delivered head `5ce7bd8022692ac3921f5baa7eb20487a9a72fe3`에서 build job `92148873959`는 PASS했지만 Ubuntu job `92148937051`과 Windows job `92148936992`는 FAIL했다. Artifact `8911008843`은 같은 run에 결속됐다: https://github.com/genichin/proofline/actions/runs/30955946035
- Ubuntu log에서 checkout의 shallow history 때문에 Line 0001부터 0018까지 `history.unavailable`이 발생했다. `.github/workflows/line-0017-candidate.yml`의 세 `actions/checkout@v4` step에는 `fetch-depth: 0`이 없고, workflow는 특정 Line 이름을 유지한 채 모든 push·pull request·manual dispatch에 실행된다.
- Windows log에서 installed wheel의 `proofline validate`가 `src/proofline/implementation_history.py:148`의 `os.set_blocking(stream.fileno(), False)`에서 `AttributeError`로 종료됐다. `_git()`은 `selectors.DefaultSelector`, nonblocking pipe와 `os.read`를 결합하지만 Windows subprocess pipe는 이 POSIX 경로와 호환되지 않으므로 호출 guard나 예외 변환만으로 기능을 복구할 수 없다.
- `tests/test_line_0017_ci.py`는 workflow job·same artifact·Windows gate와 POSIX `fcntl` import 부재를 검사하지만 full-history checkout, `os.set_blocking` 부재 또는 native Windows policy-bearing history validation success를 독립적으로 보장하지 않는다. `.github/scripts/verify-windows-candidate.ps1`이 source에서 실행하는 focused test는 HOME init이며 installed candidate validation fixture도 policy-bearing multi-commit chronology를 구성하지 않는다.
- `ac-0021`은 shallow/missing history를 fail-closed하고 source/installed-wheel parity를 요구한다. 따라서 shallow checkout acceptance가 아니라 CI에 full history를 제공하고 Windows에서 동일 의미를 구현해야 한다.
- `ac-0010`은 coverage·IQC binding, full regression, canonical validation, integration scope, main fast-forward와 source immutability를 DQC 필수 신호로 정의하지만 configured hosted candidate run의 exact SHA·job·artifact·digest read-back을 필수 신호로 정의하지 않는다.

## Scope

- AC admission은 `update: ac-0010`, `satisfy: ac-0021`, `create: []`, `retire: []`로 분류한다.
- `ac-0010`을 갱신하여 repository가 mandatory hosted candidate gate를 구성한 경우 exact candidate SHA의 hosted PASS, 동일 wheel artifact의 platform별 검증, run·job·artifact·digest read-back과 post-evidence source immutability를 DQC 필수 Line-level evidence로 요구한다. 누락·실패·ref drift·artifact mismatch·stale evidence에서는 DQC PASS를 차단한다.
- `ac-0021`의 의미는 변경하지 않고 stdout·stderr를 동시 drain하는 Windows-compatible bounded Git subprocess pump를 구현한다. Per-command/session timeout·aggregate output cap·nonzero exit·bounded terminate/kill/reap·pipe cleanup과 Git environment hardening을 유지한다. Missing/shallow/unresolved history는 계속 `history.unavailable`로 fail-closed하며 read-only contract를 유지한다. 같은 비이식적 pipe pump를 가진 standalone start-implementation preflight도 shared helper 또는 동일한 portable contract로 동기화한다.
- `.github/workflows/line-0017-candidate.yml`을 Line identity에 종속되지 않는 exact candidate workflow로 전환하고 `candidate/**` remote branch push만 canonical trigger로 허용한다. Workflow는 event의 immutable full SHA를 requested candidate로 고정하고 각 job의 checked-out HEAD와 일치시킨다. History-aware checkout은 full first-parent history를 제공하고, exact candidate에서 wheel을 한 번 build한 뒤 Ubuntu와 Windows가 동일 artifact와 SHA-256을 검증한다.
- Hosted run의 checked-out HEAD, artifact provenance와 digest를 machine-readable evidence로 남기고 DQC가 기록할 exact candidate binding을 제공한다. GitHub artifact ZIP digest를 wheel SHA-256의 대체물로 사용하지 않고 artifact를 내려받아 strict 단일 checksum record와 exact wheel 하나를 독립 검증한다. Local simulated parity는 hosted Windows PASS를 대신하지 않는다.
- Native Windows 또는 Windows-compatible regression에서 `os.set_blocking` 부재, stdout·stderr 동시 drain, timeout, aggregate output cap, nonzero exit와 bounded terminate/kill/reap 경계를 검증한다. Ubuntu에서는 full-history source validation과 전체 regression을 유지한다.
- Hosted gate의 candidate-controlled failure 또는 candidate defect/source 변경은 main integration·delivery를 금지하고 `verifying → in_progress` 뒤 fresh rework `P → I → Q → V`와 새 hosted evidence를 요구한다. Candidate bytes가 불변이고 GitHub platform `startup_failure`·`stale`처럼 candidate-controlled step 시작 전의 외부 중단이나 governance authority가 기록한 외부 취소·공식 service incident가 exact run/attempt·step·timestamp evidence로 입증된 경우에만 같은 `V`의 새 run/attempt를 허용한다. 원인 불명, timeout, candidate-controlled step 시작 후 failure 또는 external evidence가 불완전하면 transient로 인정하지 않고 DQC를 blocked로 유지한다.

## Out of Scope

- `ac-0021`의 first-parent chronology, prospective legacy cutoff 또는 stable diagnostic 의미 변경
- Windows installer·HOME transaction 동작의 신규 기능 또는 controlled Windows 11 사용자 환경 인증
- GitHub branch protection·repository rule 설정 변경, 자동 DQC authority 행사 또는 자동 main merge
- `workflow_dispatch` exact SHA 또는 pull request synthetic merge SHA를 DQC candidate trigger로 사용하는 경로
- Release, tag, package publication, public asset read-back과 version 변경
- GitHub Actions 외 CI provider를 위한 일반 추상화
- Line 0018 history rewrite, `delivered` 취소 또는 기존 IQC·DQC evidence 변경

## Risks and Unknowns

### Risks

- Candidate ref가 run 중 이동하거나 workflow checkout과 artifact build source가 다르면 잘못된 SHA에 PASS evidence가 결속될 수 있다. Workflow는 checked-out HEAD를 requested candidate와 비교하고 run head SHA·artifact digest를 read-back해야 한다.
- `candidate/**` ref는 hosted evidence read-back과 delivery 완료 전까지 보존하고 이후에만 명시적 remote cleanup 대상으로 삼아야 한다. Workflow가 ref를 자동 삭제하지 않는다.
- Windows pipe handling을 단순 `communicate()`로 교체하면 per-command/session output cap, timeout 또는 bounded child ownership이 약화될 수 있다. Correction은 기존 resource·cleanup invariants를 동일하게 검증해야 한다.
- Full-history checkout은 runtime과 network cost를 늘리지만 history-aware canonical validation에 필수이며 shallow fallback은 허용하지 않는다.
- DQC artifact는 hosted candidate `V` 이후 작성되므로 hosted evidence는 `V`에 결속하고, DQC commit까지 제품 source·test·build/runtime configuration이 불변인지 별도로 검사해야 한다.
- Same-`V` retry는 failed run을 지우거나 무시하는 우회로가 될 수 있다. DQC는 이전 run/attempt, failed step, GitHub platform conclusion과 external incident/cancellation evidence를 보존하고 narrow transient predicate를 입증해야 하며 ambiguous failure는 fail-closed해야 한다.
