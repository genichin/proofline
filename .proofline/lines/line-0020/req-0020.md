# Main-owned Line handoff와 concurrent integration spine

## Objective

Lead/orchestrator가 approved REQ·AC baseline을 main에서 status-only Line handoff commit으로 영속화하고 exact handoff worktree를 구현 에이전트에게 인계하며, 구현 에이전트가 main을 변경하지 않은 채 Micro-SPEC lifecycle과 구현 evidence를 Line first-parent spine에 기록하도록 한다. Main이 다른 governance를 계속 진행해도 latest main과 exact Line head를 canonical manifest로 결속한 main-first integration candidate를 hosted CI·DQC에서 검증하고 main first-parent history와 Line evidence를 모두 보존한다.

## Scope

- REQ 승인 전 Micro-SPEC exact coverage를 강제하는 current reference validation을 변경하여 Line handoff와 Micro-SPEC drafting 동안 zero/partial coverage를 허용하고, 최초 Micro-SPEC implementation transition 전에는 REQ 전체 exact coverage와 대상 Micro-SPEC approval을 fail-closed하게 요구한다.
- Exact approved specification baseline `A`의 direct first-parent child로 Line 한 파일의 `not_started → in_progress`만 포함한 main-owned handoff commit `H`를 만들고 exact `H`에서 dedicated linked worktree를 생성·검증·복구하는 workflow를 제공한다.
- Micro-SPEC draft authoring, independent read-only review, user/governance approval, status-only approval commit과 implementation agent handback을 exclusive ownership phase로 분리한다.
- Line worktree의 `H → S → P → I → Q` strict first-parent implementation spine과 latest main `M`을 two-parent integration candidate `V`에 결속한다. Candidate-contained canonical integration manifest가 Line identity, `M`과 `Q`를 소유하며 parent order·merge tree·staleness를 검증한다.
- Candidate/DQC 전 mutable main·Line ref equality와 통합 후 immutable Git object chronology를 구분한다. Main drift에는 same-`Q` fresh candidate와 fresh hosted/DQC evidence를 요구하고, delivery 이후에는 branch 존재를 historical invariant로 요구하지 않는다.
- Existing exact candidate DQC, hosted Ubuntu·Windows PASS, artifact/provenance/checksum read-back, full regression, canonical validation, integration scope와 fast-forward gate를 main-first merge candidate에 그대로 적용한다.
- Contract, templates, validator, standalone worktree workflow, implementation-history validation, DQC workflow와 source/installed-wheel Real-Git tests를 같은 authority·ancestry·diagnostic 의미로 동기화한다.
- Current validator를 변경하는 Line 0020에 한해 main에서 REQ·AC와 `ms-0020-001` bootstrap specification을 함께 draft·approve한다. 후속 Line은 Micro-SPEC 없이도 approved REQ·AC 뒤 `H`와 worktree를 만들고 Micro-SPEC을 worktree에서 작성한다.

## Constraints

- Main checkout과 main ref의 Discovery·REQ·AC·Line handoff는 lead/orchestrator가 소유하며 구현 에이전트는 Line worktree만 변경한다.
- Git commit, branch, worktree, merge, push와 lifecycle authority는 ProofLine CLI가 자동 행사하지 않고 repository-owned Hermes workflow와 사용자 approval gate가 소유한다.
- Integration candidate는 exactly two parents를 가지며 parent 0은 latest main, parent 1은 exact single-Line verification head다. Manifest 외 merge-only 제품 변경이나 conflict resolution은 허용하지 않는다.
- Existing linear delivered Line 0018·0019의 canonical artifacts와 history를 rewrite하지 않고 source와 installed-wheel validation compatibility를 유지한다.
- Validator와 supporting workflow는 Git/index/worktree/ref/object를 read-only로 검사하고 실패 시 stable diagnostic과 no-mutation evidence를 제공한다.

## Non-Goals

- 구현 에이전트의 main 수정·commit, Micro-SPEC 자기 승인 또는 reviewer mutation
- 여러 Line 제품 변경의 conflict 자동 해결, octopus merge 또는 multi-Line integration candidate
- Main history reset/rewrite, `in_progress → not_started` rollback, rebase·squash·cherry-pick integration
- Line 0020 bootstrap exception의 후속 Line 재사용 또는 main에서 제품 source·test·runtime 구현
- Existing delivered Line의 migration rewrite, release·tag·package publication 또는 public asset 변경
