# Worktree 생성 gate와 Micro-SPEC 구현 착수 gate 분리

## Problem

ProofLine은 linked worktree 생성과 특정 Micro-SPEC의 source·test·document 구현 착수를 서로 다른 lifecycle action으로 운용하지만, repository contract와 `proofline-start-implementation` skill은 두 행동을 모두 “implementation 시작”으로 표현한다. 이 표현은 agent나 runbook이 Micro-SPEC `approved`를 worktree 생성의 선행 조건으로 잘못 추가하거나, 반대로 worktree가 존재한다는 이유로 draft 또는 미작성 Micro-SPEC의 구현을 시작하도록 해석하게 만든다.

Executable worktree preflight는 confirmed Discovery, approved REQ, not-started Line, clean main과 Git path·branch·registration 충돌 부재만 검사하며 Micro-SPEC 존재 여부나 `spec_status`를 읽지 않는다. 반면 Micro-SPEC contract와 first-parent implementation handoff는 해당 Micro-SPEC이 `approved`이고 별도 `in_progress` transition이 persisted된 뒤에만 제품 구현을 시작하도록 요구한다. 현재 동작은 이 경계를 암묵적으로 따르지만 action별 gate 표와 직접적인 no-Micro-SPEC/draft-Micro-SPEC regression이 없어 해석에 따라 lifecycle gate가 확장되거나 약화될 수 있다.

## Evidence

- GitHub Issue [#16](https://github.com/genichin/proofline/issues/16)은 worktree creation과 Micro-SPEC implementation-start gate의 분리, executable preflight source of truth, Real-Git no-mutation matrix와 source/installed-wheel parity를 요구한다.
- Exact baseline `44adb5a854f29e0d3e1c7dcdb0bb5d2f7e45577f`의 `skills/proofline-start-implementation/scripts/create_worktree.py:377-459`는 exact approval commit에서 Discovery `confirmed`, REQ `approved`, Line `not_started`, history preflight, ignored target, path·branch·registration collision을 검사한 뒤 `git worktree add`를 수행한다. Micro-SPEC path 또는 `spec_status` 검사는 없다.
- `skills/proofline-start-implementation/SKILL.md:17-30`은 worktree workflow 자체를 “implementation 시작”으로 소개하지만, 같은 문서 `117-128`은 제품 변경 전에 approved Micro-SPEC 뒤의 별도 `in_progress` commit이 필요하다고 규정한다. Worktree 생성과 제품 구현 착수의 허용 상태를 한 표로 분리하지 않는다.
- `docs/contracts/line-delivery.md:38-50`은 exact REQ approval commit에서 linked worktree를 만들고 이후 Micro-SPEC·implementation·IQC를 worktree에서 작성한다고 규정한다. `docs/contracts/micro-spec-and-iqc.md:20-38,60-65`는 Micro-SPEC `approved`를 구현 시작 조건으로, `in_progress`를 code·test·document 구현 중 상태로 정의한다.
- Active `ac-0007`은 exact approved REQ baseline, stable Line identity, isolated branch/worktree와 no-mutation failure를 durable criterion으로 소유한다. Micro-SPEC 승인 전 worktree 생성 허용은 이 criterion의 의미를 바꾸지 않고 기존 worktree behavior를 명시적으로 검증하는 `satisfy`에 해당한다.
- `tests/test_start_implementation_skill.py:37-65`의 `make_approved_repo` fixture는 Micro-SPEC을 만들지 않으며, `test_worktree_script_accepts_direct_approval_without_draft_parent`가 그 fixture에서 worktree 생성 성공을 확인한다. 즉 no-Micro-SPEC success는 간접적으로 실행되지만 test 이름과 contract가 해당 boundary를 직접 소유하지 않는다. Draft Micro-SPEC success case는 현재 해당 test module에 없다.
- 2026-08-05에 repository 밖 `UV_PROJECT_ENVIRONMENT=/tmp/proofline-line0020-discovery-uv`로 no-Micro-SPEC success, dirty-main no-mutation failure, draft-REQ failure의 focused 3 tests를 실행해 모두 PASS했다. Repository worktree에는 `.venv`가 생성되지 않았다.
- `tests/test_wheel_package.py:832-846`은 worktree skill, script와 관련 contracts가 wheel resource bytes와 일치함을 검사한다. 그러나 installed wheel에서 추출한 standalone script가 no-Micro-SPEC과 draft-Micro-SPEC에 동일한 executable semantics를 보이는지 직접 실행하는 matrix는 없다.
- Relevant history에서 `8dadb46`이 fail-closed worktree creation workflow를 도입했고, Line 0018·0019의 후속 history validation과 Windows portability 변경은 implementation chronology를 강화했지만 worktree creation과 Micro-SPEC approval gate를 하나의 action으로 합치지는 않았다.

## Scope

- AC admission은 active `ac-0007`의 `satisfy`로 한다. Existing exact approval baseline과 no-mutation worktree behavior의 PASS/FAIL 의미를 바꾸지 않고, worktree 생성 gate와 Micro-SPEC 구현 착수 gate를 명시·검증한다.
- Canonical contracts와 `proofline-start-implementation` skill에 lifecycle action-to-gate 표를 추가한다.
  - Linked worktree 생성: Discovery `confirmed`, REQ `approved`, Line `not_started`; approved Micro-SPEC은 요구하지 않는다.
  - Micro-SPEC draft 작성·수정: approved REQ/AC 범위의 Line worktree에서 가능하며 구현 착수로 간주하지 않는다.
  - 특정 Micro-SPEC의 source·test·document 구현 착수: 해당 Micro-SPEC `approved`와 별도 persisted `in_progress` transition이 필요하다.
  - IQC, DQC, main integration과 delivery: 각각의 후속 contract gate를 유지한다.
- `create_worktree.py` preflight를 linked-worktree creation eligibility의 executable source of truth로 명시한다. Agent와 runbook은 repository-owned preflight에 없는 Micro-SPEC lifecycle 조건을 worktree 생성 gate에 임의 추가하지 않는다.
- Temporary Real-Git fixture에서 다음 matrix를 직접 고정한다.
  - Micro-SPEC이 없는 confirmed/approved/not-started baseline은 worktree 생성 PASS.
  - Draft Micro-SPEC이 있는 동일 baseline도 worktree 생성 PASS.
  - Draft Discovery, draft REQ 또는 started Line은 worktree 생성 FAIL.
  - Dirty main과 path·branch·worktree registration collision은 FAIL.
  - 모든 preflight failure는 ref, worktree registration과 target path를 변경하지 않는다.
- Source checkout script와 exact packaged/isolated wheel resource에서 같은 preflight semantics를 실행해 artifact parity뿐 아니라 executable behavior parity를 검증한다.
- Contract/skill/tests가 같은 action names, required states와 authority boundary를 사용하도록 동기화한다. Substantive skill change에는 version bump를 포함한다.

## Out of Scope

- Micro-SPEC 승인 없이 해당 Micro-SPEC의 source·test·document 구현을 허용하는 변경
- Worktree 생성 시 Micro-SPEC 생성·승인, Line/Micro-SPEC `in_progress` 전환 또는 Git commit 자동화
- `create_worktree.py`가 현재 허용하거나 거부하는 worktree eligibility 집합의 확대·축소
- `ac-0007` criterion 또는 verification 의미 변경, 신규 AC 생성
- Line 0018·0019와 기존 delivered artifact/history 수정
- IQC/DQC admission, hosted candidate CI, main integration, delivery, release·tag·publication 변경

## Risks and Unknowns

### Risks

- Current no-Micro-SPEC success test는 `proofline.yaml` 없는 축약 fixture를 사용하므로 real project의 standalone validator preflight와 결합된 behavior를 완전히 입증하지 못한다. 실제 schema-v1 Git fixture와 installed resource 실행으로 보완한다.
- “Implementation worktree”와 “implementation 시작”이라는 기존 명칭을 그대로 두면 표를 추가해도 agent가 두 action을 재혼합할 수 있다. Contract와 skill에서 `create linked worktree`와 `start Micro-SPEC implementation`을 일관된 독립 용어로 사용한다.
- Installed-wheel parity를 resource byte equality로만 판정하면 packaged standalone script의 runtime 차이를 놓칠 수 있다. Checkout 밖 temporary project에서 extracted packaged script를 실제 실행하되 application repository와 user harness를 변경하지 않는다.

### Assumptions

- Issue #16과 사용자의 Line 0020 진행 지시는 “Micro-SPEC 없음 또는 draft 상태에서도 worktree 생성은 허용하지만 제품 구현은 approved Micro-SPEC 전까지 금지한다”는 scope를 채택한다.
- Current executable acceptance set은 의도된 baseline이다. Implementation 중 현재 behavior와 contract가 실제로 충돌하는 증거가 발견되면 사양 의미를 임의 수정하지 않고 Discovery를 draft 상태에서 재검토한다.
