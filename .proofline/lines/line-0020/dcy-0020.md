# Worktree 생성 gate와 Micro-SPEC 구현 착수 gate 분리

## Problem

ProofLine의 main checkout은 lead/orchestrator가 Discovery·REQ·AC approval과 Line handoff를 직렬화하는 governance workspace이고, Line worktree는 별도 구현 에이전트가 Micro-SPEC·source·test·IQC를 작성하는 격리 workspace여야 한다. 그러나 현재 contract와 `proofline-start-implementation` workflow는 worktree를 exact REQ approval commit에서 생성한 뒤 구현 에이전트가 worktree에서 Line과 Micro-SPEC을 함께 `in_progress`로 전환하도록 안내한다. 이 구조는 main이 소유해야 할 Line handoff transition을 구현 에이전트에게 넘기고, worktree 생성과 Micro-SPEC implementation-start를 하나의 “implementation 시작”으로 혼합한다.

현재 validator는 모든 non-withdrawn REQ criteria가 즉시 non-withdrawn Micro-SPEC 합집합으로 exact coverage되어야 한다고 요구한다. 실제 schema-v1 project의 worktree preflight는 전체 `proofline validate`를 실행하므로, approved REQ·AC 뒤 worktree에서 Micro-SPEC을 처음 작성하려는 lifecycle은 `criteria.uncovered`로 차단된다. `proofline.yaml` 없는 축약 fixture만 Micro-SPEC 부재 상태의 worktree 생성을 통과하므로 current test success는 canonical project behavior를 대표하지 않는다.

Main은 한 Line을 구현 worktree로 넘긴 뒤 다른 Line/Discovery governance를 계속할 수 있다. 따라서 handoff boundary, branch ancestry, latest-main synchronization과 DQC candidate 재고정 규칙이 없으면 서로 다른 Line의 commit이 잘못된 checkout에 기록되거나 exact IQC/DQC binding을 유지한 fast-forward integration이 불가능해질 수 있다.

Issue의 최초 “Micro-SPEC 없음 PASS” 제안은 current schema-v1 coverage validator와 함께 실행할 수 없다는 review blocker가 확인됐다.

- Exact baseline `44adb5a854f29e0d3e1c7dcdb0bb5d2f7e45577f`의 `docs/contracts/line-delivery.md:194-219`는 `not_started`를 implementation branch 미시작, `in_progress`를 Micro-SPEC 작성 또는 구현 중으로 정의하고 branch 생성 시 `not_started → in_progress`를 요구한다. 이는 채택된 main-owned handoff 의미와 일치한다.

## Scope

- AC admission은 다음과 같이 한다.
  - `update`: `ac-0003` — Micro-SPEC coverage enforcement boundary를 approved REQ 시점에서 Micro-SPEC implementation-start gate로 변경한다.
  - `update`: `ac-0007` — exact worktree base와 ownership choreography를 approval commit 직접 분기에서 main-owned handoff commit 분기로 변경한다.
  - `satisfy`: `ac-0021` — 각 Micro-SPEC의 approved specification, persisted `in_progress`, implementation, implemented/IQC first-parent chronology를 그대로 검증한다.
- Canonical handoff 순서를 다음과 같이 고정한다.
  1. Lead/orchestrator가 main에서 Discovery를 confirm하고 REQ·대상 AC를 approve한다. 이를 exact approval baseline `A`로 고정한다.
  2. 모든 worktree/path/branch/validator preflight를 mutation 전에 수행한다.
  3. Lead/orchestrator가 main에서 해당 Line 한 파일의 `not_started → in_progress`만 포함한 status-only handoff commit `H`를 만든다. `H`는 `A`의 direct first-parent child이며 다른 Line, Discovery, REQ, AC, Micro-SPEC, source 또는 test 변경을 포함하지 않는다.
  4. Exact `H`에서 dedicated Line branch와 `.worktrees/line-NNNN/` linked worktree를 생성하고 branch/HEAD/main cleanliness를 read-back한다.
  5. 검증된 worktree만 구현 에이전트에게 인계한다. 구현 에이전트는 main checkout, main Discovery·REQ·AC와 main ref를 변경하지 않는다.
- Line `in_progress`는 worktree handoff 이후 Micro-SPEC drafting 또는 구현이 진행 중임을 의미한다. Line handoff 자체는 특정 Micro-SPEC의 implementation start가 아니다.
- Worktree에서는 zero, partial 또는 complete Micro-SPEC coverage 상태로 draft를 작성할 수 있다. 어떤 Micro-SPEC도 `implementation_status: in_progress` 또는 `implemented`가 되지 않은 동안 uncovered REQ criteria를 허용한다.
- 특정 Micro-SPEC의 implementation-start commit 전에 다음을 fail-closed하게 요구한다.
  - REQ 전체 target이 non-withdrawn Micro-SPEC 합집합으로 exact coverage됨
  - 구현 대상 Micro-SPEC이 `spec_status: approved`
  - 대상 Micro-SPEC의 별도 persisted `not_started → in_progress` transition
  - Line은 이미 main handoff commit에서 `in_progress`
- Source·test·document 변경은 위 Micro-SPEC implementation-start commit의 strict first-parent descendant에서만 수행한다. Worktree 생성, Micro-SPEC drafting 또는 approval을 implementation commit으로 bind하지 않는다.
- REQ criteria와 대상 AC approval 상태는 exact approval baseline `A`에서 직접 검증한다. Current main tree의 상태를 과거 `A`의 대체 evidence로 사용하지 않는다. Worktree base `H`가 exact `A`의 approved artifacts와 status-only handoff를 포함하는지 검증한다.
- Main은 `H` 이후 다른 Line/Discovery governance를 진행할 수 있다. DQC 전에 implementation branch에서 latest main을 non-rewriting merge로 반영하고 canonical validation, integration checks와 candidate를 다시 고정한다. Rebase·squash·cherry-pick으로 Micro-SPEC/IQC exact commit identity를 다시 쓰지 않는다.
- Hosted candidate `V` 이후 main이 다시 진행해 fast-forward가 불가능하면 latest main을 Line branch에 반영하고 fresh candidate를 고정하며 영향받은 verification과 hosted DQC evidence를 다시 수행한다.
- Contract, `proofline-start-implementation` skill, executable supporting script와 tests가 같은 ownership, `A → H → worktree → Micro-SPEC approval → P → I → Q → V` 순서와 stable diagnostics를 사용하도록 동기화한다. Substantive skill change에는 version bump를 포함한다.
- Temporary Real-Git source 및 exact packaged/isolated-wheel script matrix에서 다음을 검증한다.
  - Approved REQ·AC, no-Micro-SPEC, Line `not_started` baseline에서 clean preflight 후 status-only `H`와 exact-H worktree handoff PASS
  - Worktree에서 no/partial/draft Micro-SPEC 상태의 canonical validation PASS
  - First Micro-SPEC `in_progress` 전에 exact coverage 누락 또는 target Micro-SPEC non-approved이면 FAIL
  - Exact coverage와 target approval 뒤 separate Micro-SPEC `in_progress`와 implementation chronology PASS
  - Draft Discovery/REQ, inactive·draft·missing target AC, started Line의 재-handoff, dirty main, path·branch·registration collision은 mutation 전 FAIL
  - 실패 전후 refs, worktree registration, main index/worktree와 target path 불변; handoff commit 이후 failure는 아래 recovery policy를 따른다.

## Out of Scope

- 구현 에이전트가 main Discovery·REQ·AC를 직접 수정·승인하거나 main에 commit하는 동작
- Micro-SPEC 자기 승인, source/test/document 변경과 lifecycle transition의 같은 commit 혼합
- ProofLine CLI가 Git commit, branch, worktree, merge, push 또는 lifecycle authority를 자동 소유하도록 확장하는 변경
- DQC 이후 squash, cherry-pick, rebase 또는 exact IQC/DQC binding을 다시 쓰는 integration
- 여러 Line의 제품 implementation을 conflict 없이 자동 병합하는 scheduler
- Line 0018·0019 및 기존 delivered artifact/history 수정
- Release, tag, package publication 또는 public asset read-back

## Risks and Unknowns

### Risks

- Main handoff commit `H`가 성공한 뒤 external filesystem/Git failure로 worktree 생성이 실패하면 Line은 `in_progress`지만 usable worktree가 없는 상태가 된다. Historical handoff commit을 reset/rewrite하거나 `in_progress → not_started`를 임의 도입하지 않는 recovery policy가 필요하다.
- Current validator는 path 종류만으로 제품 구현 시작을 판정하지 않는다. Micro-SPEC lifecycle gate는 canonical transition과 history를 기계적으로 검사하지만, 구현 에이전트가 transition 없이 source를 변경하는 행위는 workflow ownership과 review에서 추가로 차단해야 한다.
- Concurrent main의 governance-only merge는 product evidence를 stale하게 하지 않을 수 있지만 다른 Line의 product source가 포함되면 integration risk와 IQC/DQC 재실행 범위가 달라진다. Candidate 고정 전에 exact changed-path와 trigger를 fail-closed하게 분류해야 한다.
- Approval baseline `A`, handoff `H`, Micro-SPEC approval, implementation commit과 latest-main merge를 서로 다른 authority가 기록하므로 commit identity와 first-parent/second-parent 방향을 잘못 선택하면 history validation 또는 fast-forward integration이 실패할 수 있다.

### Assumptions

- Main의 lead/orchestrator는 Discovery confirmation, REQ·AC approval, Line handoff commit과 worktree 생성 authority를 소유한다.
- Worktree 구현 에이전트는 Micro-SPEC draft와 구현 evidence를 작성하지만 Micro-SPEC approval, DQC, main integration과 delivery authority를 자동으로 갖지 않는다.
- Main의 다른 Line/Discovery 진행은 허용하되 exact candidate가 latest main을 포함하고 main에서 fast-forward 가능해야 한다는 기존 DQC gate는 유지한다.
