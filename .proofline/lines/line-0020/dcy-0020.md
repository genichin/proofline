# Worktree 생성 gate와 Micro-SPEC 구현 착수 gate 분리

## Problem

ProofLine의 main checkout은 lead/orchestrator가 Discovery·REQ·AC approval과 Line handoff를 직렬화하는 governance workspace이고, Line worktree는 별도 구현 에이전트가 Micro-SPEC·source·test·IQC를 작성하는 격리 workspace여야 한다. 그러나 현재 contract와 `proofline-start-implementation` workflow는 worktree를 exact REQ approval commit에서 생성한 뒤 구현 에이전트가 worktree에서 Line과 Micro-SPEC을 함께 `in_progress`로 전환하도록 안내한다. 이 구조는 main이 소유해야 할 Line handoff transition을 구현 에이전트에게 넘기고, worktree 생성과 Micro-SPEC implementation-start를 하나의 “implementation 시작”으로 혼합한다.

현재 validator는 모든 non-withdrawn REQ criteria가 즉시 non-withdrawn Micro-SPEC 합집합으로 exact coverage되어야 한다고 요구한다. 실제 schema-v1 project의 worktree preflight는 전체 `proofline validate`를 실행하므로, approved REQ·AC 뒤 worktree에서 Micro-SPEC을 처음 작성하려는 lifecycle은 `criteria.uncovered`로 차단된다. `proofline.yaml` 없는 축약 fixture만 Micro-SPEC 부재 상태의 worktree 생성을 통과하므로 current test success는 canonical project behavior를 대표하지 않는다.

Main은 한 Line을 구현 worktree로 넘긴 뒤 다른 Line/Discovery governance를 계속할 수 있다. 따라서 handoff boundary, branch ancestry, latest-main synchronization과 DQC candidate 재고정 규칙이 없으면 서로 다른 Line의 commit이 잘못된 checkout에 기록되거나 exact IQC/DQC binding을 유지한 fast-forward integration이 불가능해질 수 있다.

Current history validation은 candidate의 단일 global first-parent chain에서 lifecycle evidence를 찾고 second-parent-only marker·implementation을 거부한다. Diverged main과 Line branch를 merge하면 어느 parent를 먼저 선택하더라도 다른 한쪽 history는 second parent가 되므로, concurrent main과 current global-first-parent 판정을 동시에 만족할 수 없다. Main governance spine과 Line implementation spine을 명시적으로 분리하고 integration candidate의 parent 역할을 고정해야 한다.

## Scope

- AC admission은 다음과 같이 한다.
  - `update`: `ac-0003` — Micro-SPEC coverage enforcement boundary를 approved REQ 시점에서 Micro-SPEC implementation-start gate로 변경한다.
  - `update`: `ac-0007` — exact worktree base와 ownership choreography를 approval commit 직접 분기에서 main-owned handoff commit 분기로 변경한다.
  - `update`: `ac-0021` — candidate global first-parent 판정을 explicit main governance spine과 designated Line implementation spine 판정으로 변경한다.
  - `satisfy`: `ac-0010` — main-first merge result를 exact integration candidate로 고정하고 mandatory local·hosted DQC 신호를 그대로 검증한다.
- Line 0020은 current validator를 변경하는 self-hosting migration이므로 다음 one-time bootstrap을 사용한다.
  1. Main governance에서 `req-0020`, update 대상 AC draft와 모든 REQ target을 coverage하는 `ms-0020-001` draft를 함께 작성해 current canonical validation을 계속 PASS시킨다.
  2. Independent specification reviewer는 exact REQ·AC·bootstrap Micro-SPEC draft bytes를 read-only로 함께 검토한다.
  3. 사용자 승인 뒤 governance lead가 main에서 REQ `draft → approved`, update AC `draft → active`, bootstrap Micro-SPEC `draft → approved`의 status-only specification approval commit `A`를 기록한다. Substantive body, source, test 또는 runtime 변경을 섞지 않는다.
  4. Main에서 status-only Line handoff commit `H`를 `A`의 direct first-parent child로 기록하고 exact `H` worktree를 구현 에이전트에게 인계한다.
  5. 구현 에이전트는 bootstrap Micro-SPEC을 다시 작성하거나 승인하지 않고 exact approved specification을 인계받아 별도 `implementation_status: in_progress` commit `P` 뒤 구현한다.
  6. 이 bootstrap은 Line 0020에만 적용한다. Updated validator와 workflow가 delivery된 뒤 시작하는 후속 Line은 approved REQ·AC, zero/partial Micro-SPEC coverage 상태에서 `H`와 worktree를 만들고 Micro-SPEC을 worktree에서 작성하는 canonical flow를 사용한다.
- Canonical handoff 순서를 다음과 같이 고정한다.
  1. Lead/orchestrator가 main에서 Discovery를 confirm하고 REQ·대상 AC를 approve한다. 이를 exact approval baseline `A`로 고정한다.
  2. 모든 worktree/path/branch/validator preflight를 mutation 전에 수행한다.
  3. Lead/orchestrator가 main에서 해당 Line 한 파일의 `not_started → in_progress`만 포함한 status-only handoff commit `H`를 만든다. `H`는 `A`의 direct first-parent child이며 다른 Line, Discovery, REQ, AC, Micro-SPEC, source 또는 test 변경을 포함하지 않는다.
  4. Exact `H`에서 dedicated Line branch와 `.worktrees/line-NNNN/` linked worktree를 생성하고 branch/HEAD/main cleanliness를 read-back한다.
  5. 검증된 worktree만 구현 에이전트에게 인계한다. 구현 에이전트는 main checkout, main Discovery·REQ·AC와 main ref를 변경하지 않는다.
  6. Status-only handoff commit `H`가 persisted된 뒤 worktree 생성이 실패하면 Line은 `in_progress`와 exact `H`를 유지한다. 원인을 제거한 뒤 새 lifecycle commit 없이 같은 `H`에서 idempotent preflight와 worktree 생성을 재시도한다. Recovery가 불가능하고 Line을 종료해야 하면 정상 `in_progress → cancelled` transition을 사용한다.
- Micro-SPEC drafting과 approval은 exclusive ownership phase로 분리한다.
  1. 구현 에이전트는 Line worktree에서 Micro-SPEC draft를 작성하고 clean exact draft commit `S0`를 만든 뒤 mutation을 중지한다.
  2. 독립 specification reviewer는 exact `S0`의 Micro-SPEC bytes, REQ·AC 범위와 coverage를 read-only로 검토하며 worktree, index, ref 또는 artifact를 변경하지 않는다.
  3. Review가 correction을 요구하면 approval하지 않고 구현 에이전트에게 반환한다. 수정된 draft는 fresh exact commit과 fresh independent review가 필요하다.
  4. Review PASS 뒤 사용자 또는 governance lead가 exact `S0` approval authority를 행사한다.
  5. Governance lead는 구현 에이전트가 중지되고 Line worktree가 clean하며 branch HEAD가 exact `S0`인지 확인한 뒤, 같은 Line worktree에서 해당 Micro-SPEC의 `spec_status: draft → approved`만 포함한 approval commit `S`를 기록한다. Main checkout, main ref와 Discovery·REQ·AC는 변경하지 않는다.
  6. Approval commit의 parent가 exact `S0`이고 substantive Micro-SPEC body가 review bytes와 동일하며 status transition 외 변경이 없는지 read-back한 뒤 구현 에이전트에게 exact `S` worktree를 다시 인계한다.
- Line `in_progress`는 worktree handoff 이후 Micro-SPEC drafting 또는 구현이 진행 중임을 의미한다. Line handoff 자체는 특정 Micro-SPEC의 implementation start가 아니다.
- Worktree에서는 zero, partial 또는 complete Micro-SPEC coverage 상태로 draft를 작성할 수 있다. 어떤 Micro-SPEC도 `implementation_status: in_progress` 또는 `implemented`가 되지 않은 동안 uncovered REQ criteria를 허용한다.
- 특정 Micro-SPEC의 implementation-start commit 전에 다음을 fail-closed하게 요구한다.
  - REQ 전체 target이 non-withdrawn Micro-SPEC 합집합으로 exact coverage됨
  - 구현 대상 Micro-SPEC이 `spec_status: approved`
  - 대상 Micro-SPEC의 별도 persisted `not_started → in_progress` transition
  - Line은 이미 main handoff commit에서 `in_progress`
- Source·test·document 변경은 위 Micro-SPEC implementation-start commit의 strict first-parent descendant에서만 수행한다. Worktree 생성, Micro-SPEC drafting 또는 approval을 implementation commit으로 bind하지 않는다.
- REQ criteria와 대상 AC approval 상태는 exact approval baseline `A`에서 직접 검증한다. Current main tree의 상태를 과거 `A`의 대체 evidence로 사용하지 않는다. Worktree base `H`가 exact `A`의 approved artifacts와 status-only handoff를 포함하는지 검증한다.
- Main은 `H` 이후 다른 Line/Discovery governance를 진행할 수 있다. Line worktree는 main을 merge/rebase하지 않고 `H → Micro-SPEC approval → P → I → Q` exact first-parent implementation spine을 유지한다. `Q`는 모든 대상 implementation, passed IQC와 Line `verifying` transition을 포함한 exact Line verification head다.
- DQC lead는 latest main `M`에서 별도 integration candidate branch/worktree를 만들고 exact `Q`를 `--no-ff` merge하여 two-parent candidate `V`를 만든다. `V.parent[0]`은 exact latest main `M`, `V.parent[1]`은 exact Line head `Q`여야 한다. Octopus merge, parent reversal, 둘 이상의 Line head, stale `M`·`Q` 또는 conflict 미해소 candidate는 거부한다.
- Merge commit `V`는 `.proofline/lines/line-NNNN/integration-NNNN.md` canonical integration manifest를 새로 포함한다. Manifest frontmatter는 `id`, `line_id`, `main_parent`, `line_head`를 exact 값으로 기록하며 `candidate_commit` self-reference는 기록하지 않는다. Manifest를 포함한 commit 자체가 `V`이고 DQC가 이후 `candidate_commit: V`를 결속한다.
- Candidate admission은 manifest path·`line_id`가 exact target Line 하나와 일치하고, `main_parent == V.parent[0] == M`, `line_head == V.parent[1] == Q`이며, `Q`의 canonical Line identity·verifying state·IQC binding이 같은 `line_id`에 속하는지 검사한다. Manifest 0개·복수, path/ID mismatch, parent mismatch, arbitrary second parent, 둘 이상의 Line identity 또는 merge conflict 결과를 fail-closed하게 거부한다.
- `V`의 merge tree는 deterministic merge result와 exact integration manifest addition만 포함해야 한다. Manifest 이외의 merge-only source·test·build/runtime 수정이나 conflict resolution이 필요하면 candidate를 생성하지 않고 해당 owner Line으로 반환한다.
- Validator는 main governance spine을 `V.parent[0]`의 first-parent로, Line implementation spine을 `V.parent[1]`에서 `H`까지의 first-parent로 독립 검증한다. Line spine 내부의 approved Micro-SPEC, `P → I → Q`와 IQC exact binding은 계속 strict first-parent여야 하며 임의 second-parent evidence는 허용하지 않는다. Existing linear delivered Line은 현재 first-parent mode로 계속 PASS해야 하고 Line 0018·0019 history를 rewrite하지 않는다.
- Hosted CI와 DQC는 exact merge candidate `V`를 검증한다. DQC draft/PASS artifact commit은 `V`의 first-parent descendant이며 제품 source·test·build/runtime configuration을 변경하지 않는다. Main은 DQC PASS commit으로 fast-forward한 뒤 별도 delivery transition을 기록한다.
- Candidate 생성, hosted evidence admission, DQC PASS와 main fast-forward 직전까지는 `refs/heads/main == M`을 요구한다. Main이 old `V`를 포함하지 않은 채 `M'`로 진행하면 old `V`는 stale이며 merge/rebase/retry하지 않는다. New latest main에서 동일 exact `Q`를 designated second parent로 하는 fresh integration candidate와 manifest를 만들고 canonical/integration/full regression, fresh hosted evidence와 DQC를 다시 수행한다. `Q`와 기존 IQC SHA는 rewrite하지 않는다.
- Pre-integration에는 canonical Line branch/worktree의 clean exact head가 `Q`와 일치해야 한다. `Q` 이후 Line source·test·build/runtime 또는 governance evidence가 변경되면 old `V`는 stale이며 fresh Line verification head와 fresh `V`가 필요하다. Integration과 clean worktree cleanup 이후 historical validation은 mutable Line branch/ref의 존재나 equality를 요구하지 않는다.
- Main이 DQC PASS descendant로 fast-forward된 뒤에는 current main과 `M` equality를 요구하지 않는다. Historical/post-integration validation은 DQC의 exact `candidate_commit: V`, `V` 내 manifest, actual two parents, main first-parent상의 연속된 `M → V → DQC PASS → delivery`와 designated Line spine을 검사한다. 후속 main commit이 추가돼도 이 historical binding은 계속 PASS한다.
- Contract, `proofline-start-implementation` skill, DQC workflow, executable supporting scripts와 tests가 같은 ownership, `A → H → worktree → Micro-SPEC approval → P → I → Q`, `M + Q → V → DQC → fast-forward delivery` 순서와 stable diagnostics를 사용하도록 동기화한다. Substantive skill change에는 version bump를 포함한다.
- Temporary Real-Git source 및 exact packaged/isolated-wheel script matrix에서 다음을 검증한다.
  - Approved REQ·AC, no-Micro-SPEC, Line `not_started` baseline에서 clean preflight 후 status-only `H`와 exact-H worktree handoff PASS
  - Worktree에서 no/partial/draft Micro-SPEC 상태의 canonical validation PASS
  - First Micro-SPEC `in_progress` 전에 exact coverage 누락 또는 target Micro-SPEC non-approved이면 FAIL
  - Exact draft `S0`의 independent read-only review, user/governance approval과 status-only `S` chronology PASS; self-approval, reviewer mutation, stale draft approval, approval과 substantive body 변경 혼합은 FAIL
  - Exact coverage와 target approval 뒤 separate Micro-SPEC `in_progress`와 implementation chronology PASS
  - Draft Discovery/REQ, inactive·draft·missing target AC, started Line의 재-handoff, dirty main, path·branch·registration collision은 mutation 전 FAIL
  - 실패 전후 refs, worktree registration, main index/worktree와 target path 불변; handoff commit 이후 failure는 아래 recovery policy를 따른다.
  - Diverged main `M`과 exact Line head `Q`의 `parent[0]=M`, `parent[1]=Q` integration candidate 및 각 spine의 exact first-parent chronology PASS
  - Exact manifest path/ID/`M`/`Q` binding과 deterministic merge tree PASS; manifest missing·duplicate·mismatch, parent reversal, branch-first main merge, octopus/multiple-Line merge, stale parent, Line spine의 second-parent-only `P`·`I`·`Q`, ambiguous binding은 FAIL
  - Pre-DQC main drift와 Line-head drift는 FAIL; DQC PASS descendant fast-forward 직후 및 후속 unrelated main commit 뒤 historical validation은 PASS
  - Existing linear Line 0018·0019 fixtures와 exact installed-wheel validator behavior는 regression 없이 PASS

## Out of Scope

- 구현 에이전트가 main Discovery·REQ·AC를 직접 수정·승인하거나 main에 commit하는 동작
- Micro-SPEC 자기 승인, source/test/document 변경과 lifecycle transition의 같은 commit 혼합
- Independent reviewer의 artifact mutation 또는 governance lead의 approval commit에 substantive Micro-SPEC 수정 혼합
- ProofLine CLI가 Git commit, branch, worktree, merge, push 또는 lifecycle authority를 자동 소유하도록 확장하는 변경
- Line branch를 latest main에 merge/rebase하거나 squash·cherry-pick으로 exact Micro-SPEC/IQC binding을 다시 쓰는 integration
- 여러 Line의 제품 implementation을 conflict 없이 자동 병합하는 scheduler
- Integration merge에서 manifest 이외의 source·test·build/runtime conflict resolution 또는 merge-only 제품 수정
- Handoff 실패 시 main history reset/rewrite 또는 `in_progress → not_started` lifecycle rollback
- Line 0020 bootstrap exception을 후속 Line에 재사용하거나 main에서 제품 source·test·runtime implementation을 수행하는 동작
- Line 0018·0019 및 기존 delivered artifact/history 수정
- Release, tag, package publication 또는 public asset read-back

## Risks and Unknowns

### Risks

- Main handoff commit `H`가 성공한 뒤 external filesystem/Git failure로 worktree 생성이 실패하면 Line은 일시적으로 `in_progress`지만 usable worktree가 없을 수 있다. Stable diagnostic과 exact-H retry identity를 기록하고, retry가 branch/path/registration의 partial mutation을 그대로 수용하지 않도록 idempotent preflight를 적용한다.
- Current validator는 path 종류만으로 제품 구현 시작을 판정하지 않는다. Micro-SPEC lifecycle gate는 canonical transition과 history를 기계적으로 검사하지만, 구현 에이전트가 transition 없이 source를 변경하는 행위는 workflow ownership과 review에서 추가로 차단해야 한다.
- Concurrent main에 다른 Line의 product source가 포함되면 merge candidate가 새로운 integration risk를 만든다. Exact changed-path와 trigger를 fail-closed하게 분류하고 integration/full regression과 hosted DQC를 candidate `V`에서 수행해야 한다.
- Approval baseline `A`, handoff `H`, Line head `Q`, latest main `M`, merge candidate `V`를 서로 다른 authority가 기록하므로 parent identity/order를 잘못 선택하면 history validation 또는 fast-forward integration이 실패할 수 있다. Candidate provenance와 DQC는 `M`, `Q`, `V`를 모두 exact SHA로 기록한다.
- Per-Line spine 판정이 arbitrary second-parent evidence를 일반 허용하면 기존 history hardening을 무력화한다. 오직 exact two-parent integration candidate의 designated `parent[1]`과 그 내부 strict first-parent chain만 Line evidence root로 허용한다.
- Candidate manifest는 `V`를 self-reference할 수 없으므로 containing commit identity와 exact parent binding을 함께 사용해야 한다. DQC의 후속 `candidate_commit: V`와 manifest parent values 중 하나라도 불일치하면 historical evidence를 거부한다.
- Mutable main/Line refs를 historical invariant로 사용하면 정상 delivery 또는 worktree cleanup 뒤 validation이 실패한다. Ref equality는 pre-integration operational gate에만 사용하고 post-integration은 immutable Git object와 canonical binding만 사용한다.
- Line 0020이 목표 workflow를 자기 specification drafting에 직접 사용하지 못하므로 bootstrap fixture만 PASS하고 future no-Micro-SPEC flow가 깨질 위험이 있다. Real-Git source/installed-wheel tests는 후속 Line을 모사한 zero/partial coverage handoff를 반드시 실행하고 legacy bootstrap을 일반 성공 경로로 취급하지 않는다.

### Assumptions

- Main의 lead/orchestrator는 Discovery confirmation, REQ·AC approval, Line handoff commit과 worktree 생성 authority를 소유한다.
- Worktree 구현 에이전트는 Micro-SPEC draft와 구현 evidence를 작성하지만 Micro-SPEC approval, DQC, main integration과 delivery authority를 자동으로 갖지 않는다. Draft review·approval phase에는 mutation을 중지한다.
- Independent specification reviewer는 exact draft에 대한 read-only PASS/FAIL recommendation만 소유한다. 사용자 또는 governance lead가 approval authority를 소유하고, governance lead는 clean exact draft 위 status-only approval commit을 Line worktree에 기록한다.
- Main의 다른 Line/Discovery 진행은 허용하되 exact merge candidate의 first parent가 latest main이고 main에서 DQC PASS descendant로 fast-forward 가능해야 한다는 기존 DQC gate는 유지한다.
