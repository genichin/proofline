# Project Design Documents and Maintenance Skill

## Problem

ProofLine은 Discovery, REQ와 AC를 통해 변경 이유와 승인할 제품 동작을 정의하지만, 승인된 동작을 구현 가능한 기술 설계로 연결하는 project-level 문서 형식과 authoring workflow를 제공하지 않는다. 적용 프로젝트는 interface signature와 오류 경계, data structure와 invariant, component 간 runtime 순서와 failure propagation을 각자 임의 형식으로 기록하거나 구현 코드에서 다시 추론해야 한다.

이 공백 때문에 여러 구현 agent와 후속 Line이 같은 REQ/AC를 사용하더라도 API, data ownership, 상태 전이와 호출 순서를 서로 다르게 해석할 수 있다. 반대로 이러한 기술 설계를 AC 본문에 누적하면 version-independent observable behavior와 implementation-facing design detail의 소유권이 섞인다. ProofLine은 canonical specification을 확장하지 않으면서 project `docs/`의 기술 설계 문서를 일관되게 만들고, 현재 REQ/AC와 직접 source evidence에 따라 필요한 문서만 안전하게 갱신하는 agent workflow가 필요하다.

## Evidence

- `docs/contracts/storage-and-retention.md:13-24`는 적용 프로젝트의 사용자용 파생 문서를 `docs/requirements.md` 하나로 제한한다. 이 문서는 active AC를 펼친 비정본 view이며 기술 설계 문서가 아니다.
- `templates/README.md:7-17,31-36`과 `templates/schema-v1/` inventory에는 네 canonical artifact template과 derived requirements template만 있다. `interface contract`, `data model`, `runtime flow` template은 없다.
- `src/proofline/project_schema.py:3-20`과 `src/proofline/project_writer.py:97-104`에 따르면 `proofline project init`은 `proofline.yaml`, identity allocator와 두 `.gitkeep`만 소유하며 project `docs/`를 생성하지 않는다.
- `skills/proofline-start-requirement/SKILL.md:41-49`는 confirmed Discovery에서 REQ/AC 본문을 작성하도록 안내하지만 별도 기술 설계 문서의 영향 분석이나 갱신 절차를 제공하지 않는다.
- `skills/proofline-approve-specification/SKILL.md:31-49`는 exact REQ/AC만 사용자에게 제시하여 승인 baseline을 형성하고 Line 외 작업·검증·배포 artifact 승인을 범위에서 제외한다. 기술 설계 문서가 구현 기준일 때의 review 경계는 현재 정의되지 않았다.
- 2026-08-10에 repository의 Markdown filename과 `docs/`, `skills/` 내용을 검색한 결과 interface contract, data model 및 runtime flow template이나 이를 유지하는 skill은 발견되지 않았다.
- Scaffold 직전 `main`은 `9c74a9206a988fc22212278d7ce62d341ce8c752`에서 clean이었고, `proofline line init --title "Project Design Documents and Maintenance Skill" --dry-run`은 다음 identity `line-0034`와 두 canonical path를 충돌 없이 계획했다.

## Scope

- ProofLine package가 제공하는 project design-document template family를 추가한다. Template은 적용 프로젝트의 `.proofline/` 밖 `docs/interfaces/<name>.md`, `docs/data-model/<name>.md`, `docs/runtime-flows/<name>.md`에 사람이 관리하는 문서를 작성하도록 안내하되 package resource 자체와 적용 프로젝트 문서를 구분한다.
- Interface Contract template은 purpose와 boundary, caller/callee, input/output, precondition/postcondition, 오류·호환성 및 관련 REQ/AC를 표현한다.
- Data Model template은 entity/struct/schema, field와 type, invariant, ownership/lifetime, serialization·ABI 또는 migration boundary 및 producer/consumer를 표현한다.
- Runtime Flow template은 trigger와 participants, 정상 순서, 상태 전이, timeout/retry/cancellation, failure propagation, recovery와 외부 side-effect 경계를 표현한다.
- Repository-owned `proofline-maintain-design-docs` agent skill을 제공한다. Skill은 현재 confirmed Discovery, 대상 REQ/AC, 기존 design docs, source, test와 config를 직접 조사한 뒤 interface/data model/runtime-flow 영향 여부를 분류하고, 이미 같은 사실을 소유한 기존 문서를 우선 갱신하며 실제로 독립적인 owner가 필요할 때만 새 문서를 제안한다.
- Skill은 explicit 요청에만 project `docs/`를 작성한다. Existing path, symlink, 예상 밖 file type 또는 owner가 불명확한 문서를 덮어쓰거나 자동 변환하지 않고, 변경 전 대상과 planned update를 제시한다. Product·policy·compatibility·scope 결정을 근거 없이 확정하지 않는다.
- AC는 지속적인 observable product behavior를 계속 소유하고 design docs는 그 behavior를 구현하는 기술 계약을 소유하도록 중복을 피한다. Design 문서가 REQ/AC의 PASS/FAIL 의미나 scope를 바꾸는 경우 문서 수정만으로 우회하지 않고 ProofLine specification governance로 되돌린다.
- REQ는 구현 기준인 design docs의 exact project-relative path를 `Scope` 또는 `Constraints`에 열거한다. Specification 승인 시 approval skill은 해당 Interface Contract, Data Model과 Runtime Flow의 exact 내용을 REQ/AC와 함께 사용자에게 제시하며, 사용자 승인이 이 전체 집합을 normative technical baseline으로 확정한다. Design docs에는 별도 status나 approval metadata를 추가하지 않는다.
- 승인된 REQ가 참조하는 design docs의 기술 의미를 바꾸려면 REQ와 영향받는 AC를 계약에 따라 draft로 되돌려 변경 문서와 함께 재검토·재승인한다. 오탈자처럼 기술 의미와 구현 판정이 변하지 않는 수정은 새로운 product scope로 확대하지 않는다.
- Design-document template과 skill source를 official wheel 및 agent-skill installation payload에서 사용할 수 있도록 source/package byte parity와 skill structure를 검증한다.
- AC admission은 template family와 evidence-grounded, ownership-safe maintenance workflow를 하나의 새 version-independent AC로 `create`하고, exact referenced design docs를 Specification 승인 baseline에 포함하는 경계를 소유하도록 `ac-0025`를 `update`하는 방향으로 분류한다.

## Out of Scope

- Line, Discovery, REQ와 AC 외 새로운 `.proofline/` canonical artifact family, identity allocator 또는 lifecycle status 추가
- `proofline project init`에서 `docs/` 자동 생성, 기존 문서 overwrite 또는 project-wide design document migration
- 첫 delivery에서 design-document 생성·갱신을 소유하는 새 ProofLine CLI command나 embedded LLM runtime 구현
- Source code, schema, OpenAPI, database 또는 diagram에서 design docs를 자동 생성하거나 자연어와 구현의 semantic parity를 validator가 판정하는 기능
- ADR, 사용자 설명서, 운영 runbook, test plan, release/publication/deployment record를 포괄하는 범용 문서 관리 체계
- Design docs만으로 Discovery confirmation, REQ/AC approval, 구현 완료, 검증 또는 배포 authority를 행사하는 기능
- 기존 project 문서의 일괄 재작성, 이름 변경 또는 directory topology 강제 migration

## Risks and Unknowns

### Risks

- Design docs가 REQ/AC와 같은 제품 동작을 중복 서술하면 두 source of truth가 drift할 수 있다. Template과 skill은 AC의 observable behavior를 복제하기보다 관련 ID를 참조하고 기술 계약만 소유하도록 제한해야 한다.
- `docs/`는 project/user-owned 공유 영역이므로 고정 scaffold가 기존 문서를 침범할 수 있다. Initial workflow는 explicit target, no-overwrite와 기존 owner 우선 원칙을 적용하고 `project init` 또는 validator-owned topology로 승격하지 않아야 한다.
- 지나치게 고정된 template은 언어·framework별 실제 설계를 수용하지 못하고, 지나치게 자유로운 template은 agent 간 일관성을 만들지 못한다. 공통 의미 section만 고정하고 language-specific detail은 section 내부에서 표현할 수 있어야 한다.
- Skill이 source 구현을 현재 사양보다 authoritative하게 해석하면 기존 defect를 설계 계약으로 굳힐 수 있다. 승인된 REQ/AC와 확인된 사용자 결정이 제품 의미를 우선하고 source는 현재 상태 evidence로만 사용해야 한다.
