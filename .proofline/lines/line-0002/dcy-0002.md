# Hermes 기반 Discovery 작성 workflow와 안전한 Line bootstrap

## Problem

ProofLine은 schema v1 template과 최소 validator를 제공하지만 새 Line과 Discovery를 시작하는 canonical writer가 없다. 현재는 agent나 사용자가 template을 직접 복사하고 ID·제목을 치환해야 하므로 경로 불일치, ID 재사용, template variable 잔존, 기존 파일 덮어쓰기 및 부분 생성 위험이 있다.

결정론적 CLI만으로는 repository의 실제 문제, evidence, scope와 사용자 결정을 판단해 의미 있는 Discovery 내용을 작성할 수 없다. 반대로 CLI가 LLM provider와 credential, repository 탐색 및 대화 상태까지 직접 소유하면 ProofLine의 결정론적 validation 경계와 agent의 추론·조사 역할이 혼합된다. 따라서 안전한 scaffold 생성과 evidence 기반 Discovery 작성을 분리하되 하나의 재현 가능한 workflow로 연결해야 한다.

## Evidence

- `line-0001`은 `proofline validate` validator MVP를 전달했으며 `dcy-0001.md`와 `req-0001.md`는 artifact writer, 자동 ID 할당 및 Hermes Agent skill을 명시적으로 범위에서 제외했다.
- `src/proofline/cli.py`의 현재 CLI는 `validate` command만 제공한다.
- `templates/schema-v1/artifacts/line.md`와 `discovery.md`는 Line 및 Discovery draft의 canonical 생성 입력을 제공한다.
- 현재 저장소에는 `SKILL.md` 또는 repository-owned Hermes skill source가 없다.
- `pyproject.toml`의 runtime dependency는 `PyYAML`뿐이며 LLM provider 또는 agent runtime dependency가 없다.
- 2026-08-01 현재 `uv run pytest`는 28개 test를 모두 통과하고 `uv run proofline validate`는 진단 없이 종료 코드 0을 반환한다.

## Scope

- 사용자가 명시한 `line-NNNN` ID와 제목으로 `line-NNNN.md`와 `dcy-NNNN.md` draft를 canonical path에 함께 생성하는 deterministic CLI scaffold를 제공한다.
- CLI는 `proofline.yaml`, 고정 `.proofline` root, Line ID 문법, 현재 tree 및 Git history의 ID 재사용, symlink, template 존재와 대상 path 충돌을 어떤 write보다 먼저 검사한다.
- 기존 파일을 덮어쓰지 않으며 성공하면 두 artifact를 모두 생성하고 실패하면 어떤 파일도 남기지 않는 all-or-nothing write를 제공한다.
- Dry-run은 동일한 preflight와 in-memory rendering·validation을 수행하되 directory, 파일, Git branch 또는 commit을 만들지 않는다.
- 생성 결과에서 일반 template variable을 모두 실제 값으로 치환하고 canonical frontmatter에는 placeholder를 남기지 않는다. Discovery 본문에는 schema v1이 허용한 draft governance placeholder만 남길 수 있다.
- Repository-owned Hermes workflow는 CLI scaffold를 사용한 뒤 현재 repository의 직접 근거를 조사하여 Discovery의 Problem, Evidence, Scope, Out of Scope 및 필요한 Risks and Unknowns를 작성한다.
- Hermes workflow는 근거로 해소할 수 없는 product·policy·scope 결정을 구조화된 Open Question으로 남기며 Discovery를 스스로 `confirmed`로 전환하지 않는다.
- CLI와 Hermes workflow의 역할 경계, 실패 시 무변경 보장 및 생성 결과 validation을 fixture와 자동화 test로 검증한다.

## Out of Scope

- CLI 내부의 LLM 호출, model/provider 선택, API credential 관리 및 대화형 agent runtime
- REQ, AC, Micro-SPEC, IQC 또는 DQC writer
- 자동 Line ID 할당
- Discovery confirmation, REQ approval 및 기타 lifecycle transition command
- Git branch 생성, commit, merge, push 또는 원격 side effect
- Line 1에서 제외한 참조 의미·집합 불변식·Git commit ancestry의 validator 확장
- `docs/requirements.md` generator
- Live Hermes profile에 skill을 설치하거나 배포하는 rollout
- Agent가 사용자 대신 product·policy·priority·scope 결정을 내리거나 approval authority를 행사하는 기능

## Risks and Unknowns

### Risks

- 이 Line을 시작하는 시점에는 bootstrap writer가 없으므로 `line-0002`와 `dcy-0002` 자체는 template 계약에 따라 수동 생성해야 한다. 이 bootstrap 예외는 Line 2의 구현 기능으로 일반화하지 않는다.
- CLI scaffold와 Hermes workflow를 한 Line에 포함하면 범위가 커질 수 있다. CLI는 두 artifact의 안전한 생성만, Hermes workflow는 Discovery draft 작성만 담당하도록 경계를 유지한다.
- Hermes 환경마다 사용 가능한 repository 도구가 다를 수 있다. Workflow는 특정 model provider에 결합하지 않고 읽기 가능한 직접 evidence와 ProofLine CLI contract를 기준으로 작성한다.
- Git history의 ID 재사용 검사는 current tree 검사보다 비용이 크지만 보존·폐기 계약상 필요하다. 구현은 repository-local read-only Git 조회로 제한한다.

### Assumptions

- Repository-owned Hermes workflow source는 이 저장소에서 version control하며 live profile 설치는 별도 rollout으로 취급한다.
- Line ID는 사용자가 명시하며 자동 번호 할당은 후속 Line에서 별도로 결정한다.
- CLI scaffold가 생성한 Discovery는 항상 `status: draft`이며 내용 작성과 review 이후에도 별도 governance 절차 없이는 `confirmed`가 되지 않는다.
