# AC admission과 maintenance 경계 정의

## Problem

ProofLine은 Discovery와 REQ가 다루는 변경을 새 AC 생성, 기존 AC 변경, retirement 또는 사양 변경 없는 maintenance 중 무엇으로 분류해야 하는지 결정하는 admission 절차가 없다. 현재 REQ schema와 template은 `criteria.create ∪ update ∪ retire` 합집합에 최소 하나의 AC를 요구하므로, bug fix·test 보강·문서 정합화·workflow 개선·release evidence처럼 제품 사양을 변경하지 않는 작업도 불필요한 AC 생성이나 의미가 바뀌지 않은 기존 AC update로 표현될 수 있다.

이 문제는 AC를 프로젝트가 지속적으로 만족해야 하는 최소 사양이 아니라 Issue 또는 Line별 작업 추적 ID로 팽창시킨다. 기대 상태는 REQ 작성 전에 변경의 사양 가치를 분류하고, 신규 AC는 독립적이고 version-independent한 제품 동작 또는 제약일 때만 허용하며, 사양 변경 없는 maintenance에는 AC lifecycle을 왜곡하지 않는 명시적 추적 경로를 제공하는 것이다.

## Evidence

- GitHub Issue #11 `새 AC 생성 전에 사양 가치와 기존 AC 소유권을 판정한다`는 `Issue → Line → REQ → 새 AC`의 기계적 변환, AC admission 부재와 maintenance 분류 경로 부재를 근본 원인으로 기록한다: `https://github.com/genichin/proofline/issues/11`.
- `.proofline/lines/line-0005/dcy-0005.md`는 기존 active AC update를 범위 밖으로 두고 신규 create AC 경로를 먼저 완결한다는 전제를 사용했으며, 그 결과 기존 `ac-0007`의 경계 조건이 별도 `ac-0009`로 생성됐다.
- `templates/README.md`는 REQ의 `criteria.create`, `update`, `retire` 합집합에 최소 하나의 AC를 요구한다.
- `docs/contracts/requirements-and-criteria.md`는 같은 사양 축의 값이나 조건 변경은 stable AC를 update하고, active AC는 version-independent product behavior 또는 constraint여야 한다고 규정하지만 이 판단을 수행하는 절차와 필수 근거를 정의하지 않는다.
- `src/proofline/validator.py`는 artifact field, 상태값, path, heading, placeholder와 직접 reference를 검사하지만 신규 AC의 의미적 독립성, 기존 AC 소유권 또는 장기 사양 가치를 판정하지 않는다.
- Line 0012는 `ac-0005`, `ac-0009`, `ac-0017`, `ac-0018`, `ac-0019`를 survivor AC에 통합·retire하여 active AC를 11개로 정리했지만, `.proofline/lines/line-0012/dcy-0012.md`는 Issue #11의 admission template·skill·validator 개선을 명시적으로 제외했다.
- 이미 retired된 `ac-0011`, `ac-0013`, `ac-0015`는 특정 release version과 delivery evidence를 active AC로 모델링했던 별도 사례이며, 사양·구현·검증·release evidence 분류 실패가 한 번의 예외가 아니었음을 보여준다.

## Scope

- 새 AC admission 기준을 정의한다: 기존 active AC가 소유하지 않는 새로운 사양 축, 지속적인 version-independent 제품 동작 또는 제약, 독립 PASS/FAIL 가능성, 고객 또는 시스템 운영자가 관찰 가능한 결과와 장기 유지 가치.
- Discovery에서 REQ 작성 전에 변경을 `create`, `update`, `retire`, 기존 AC 위반 bug fix, test·IQC·DQC 보강, contract·문서·workflow 정합화, release evidence 또는 사양 변경 없는 maintenance로 분류하는 decision flow를 정의한다.
- `criteria.create` 선택 시 가장 가까운 기존 active AC, 기존 AC update로 처리할 수 없는 이유, 구현 방법·검증 절차·release evidence가 아닌 이유와 장기 active 가치에 대한 근거를 요구한다.
- `create`와 `update` 또는 사양 변경 여부가 불명확하면 Discovery Open Question으로 남기고 confirmation 전에 해소하도록 한다.
- 기존 active AC의 의미를 바꾸지 않는 bug fix·regression test·verification 보강은 신규 non-mutating `criteria.satisfy` binding으로 Line·REQ·Micro-SPEC·IQC·DQC에 연결한다.
- 제품 acceptance condition과 직접 관계없는 오탈자·내부 링크·formatting·개발 도구 설정·release 실행·housekeeping은 Line/REQ 밖의 issue와 일반 Git workflow로 처리한다.
- 사용자 관찰 동작, PASS/FAIL, 지원 범위, 호환성 또는 실패·안전 조건이 달라지면 maintenance나 `satisfy`로 우회하지 않고 기존 규칙에 따라 `criteria.create` 또는 `criteria.update`를 사용한다.
- REQ criteria schema에 `satisfy`를 추가하고, `satisfy` 대상은 의미가 변경되지 않은 기존 active AC여야 하며 `create`, `update`, `retire`와 같은 REQ에서 중복 분류할 수 없도록 한다.
- REQ의 최소 1개 AC invariant는 `create ∪ update ∪ retire ∪ satisfy` 합집합을 기준으로 유지한다. 순수 housekeeping은 이 invariant를 완화하지 않고 Line 밖으로 분리한다.
- AC admission의 semantic 규칙과 변경 분류는 governance contract와 repository-owned workflow가 소유하며 admission만을 위한 신규 AC는 만들지 않는다.
- Repository-owned Discovery·REQ 작성 workflow와 schema v1 template에 admission 및 변경 분류 checklist를 반영한다. Template과 skill은 가장 가까운 기존 AC, 독립 사양 축, 장기 active 가치와 release evidence 여부를 검토한다.
- Validator는 `satisfy` declaration, active AC direct reference, 변경 종류 간 중복, coverage와 unresolved Open Question 같은 결정론적 구조를 검사한다. 기존 AC 중 가장 적합한 `ac-0002`와 `ac-0003`의 PASS/FAIL 의미를 이에 맞게 update한다.
- 신규 AC의 의미적 독립성, 기존 AC와의 중복 및 maintenance 적합성에 대한 최종 판단과 승인 권한은 사용자가 소유한다.
- Version·tag·checksum 등 release-specific 문구는 일반 hard error로 만들지 않고 representative review fixture와 workflow warning으로 다룬다.
- 특정 release를 active AC로 생성하는 사례와 기존 AC 경계 조건을 신규 AC로 중복 생성하는 사례를 representative fixture 또는 workflow test로 검증한다.
- Line 0013의 REQ 변경 집합은 현재 schema로 `create: []`, `update: [ac-0002, ac-0003]`, `retire: []`로 확정한다. Prospective `satisfy` field는 이를 도입하는 승인 baseline 자체의 권한 근거로 사용하지 않는다.

## Out of Scope

- 현재 active 또는 retired AC의 추가 병합·retire·재활성화
- Issue #10의 한국어 template 문구와 authored-content 언어 gate 구현
- 기존 제품 기능, installer, updater, home writer 또는 Line writer 동작 변경
- LLM이 AC 의미를 자동 판정하거나 사용자 confirmation을 대체하는 기능
- 특정 외부 issue tracker 또는 project management system과의 통합
- 기존 Line·REQ·AC·Micro-SPEC·IQC·DQC history rewrite
- AC admission 규칙만을 위한 신규 AC identity 생성

## Risks and Unknowns

### Risks

- Maintenance 경로를 지나치게 넓게 허용하면 실제 사양 변경이 AC review와 approval을 우회할 수 있으므로 분류 조건과 escalation gate가 필요하다.
- 빈 AC 변경 집합을 허용하면 현재 REQ→AC→Micro-SPEC coverage invariant와 IQC/DQC 의미가 약해질 수 있다.
- 모든 maintenance를 기존 AC에 연결하면 의미가 바뀌지 않은 AC를 update로 오표기하거나 unrelated AC를 추적 anchor로 사용할 수 있다.
- 모든 작업을 Line 밖으로 보내면 repository-local evidence와 exact commit binding이 손실될 수 있다.
- Admission 규칙 자체를 검토 없이 새 AC로 만들면 이 Line이 해결하려는 과잉 생성 문제를 반복할 수 있다.
- Validator는 authored criterion의 의미를 완전하게 판정할 수 없으므로 자동 검사를 과도하게 확대하면 false positive 또는 형식적인 근거 문구만 증가할 수 있다.

### Assumptions

- AC admission의 최종 semantic 판단과 신규 사양 승인 권한은 사용자에게 있으며 validator나 에이전트가 이를 대신하지 않는다.
- 현재 active AC 11개와 Line 0012의 retirement 결과는 이 Discovery의 baseline이며 재분류 대상으로 확대하지 않는다.
- Issue #11의 목적은 모든 작업에 추가 artifact를 요구하는 것이 아니라 불필요한 AC 생성을 막는 최소한의 분류·확인 경계를 만드는 것이다.
