# REQ·AC draft→approval 감사 추적

## Problem

ProofLine 계약은 신규 REQ와 AC를 검토 중인 `draft`로 기록하고, main governance의 별도 approval commit에서 REQ `draft→approved`와 대상 AC `draft→active` transition을 남긴 뒤 그 exact commit을 implementation baseline으로 사용하도록 정의한다. 그러나 현재 실제 workflow는 REQ와 AC를 첫 commit부터 `approved`·`active`로 추가할 수 있고 validator와 worktree preflight도 approval commit의 현재 상태만 확인한다. 이 경우 사용자가 검토한 draft bytes, 명시적 승인 경계와 implementation baseline의 관계를 Git history에서 감사할 수 없다.

## Evidence

- GitHub Issue [#6](https://github.com/genichin/proofline/issues/6)은 Line 0002에서 REQ·AC가 첫 commit부터 `approved`·`active`로 추가되어 draft review transition이 남지 않은 문제와 완료 조건을 기록한다.
- `docs/contracts/requirements-and-criteria.md:140-159`는 REQ `draft→approved` transition을 기록한 main governance commit이 specification baseline이며 implementation branch는 그 exact commit에서만 생성할 수 있다고 정의한다.
- 같은 계약 `requirements-and-criteria.md:173-203`은 신규 AC의 허용 transition을 `draft→active`로 정의하고, REQ가 승인될 때 create/update 대상 draft AC가 active가 된다고 규정한다.
- 같은 계약의 REQ·AC schema 예시는 각각 `status: draft`를 초기 상태로 사용한다.
- Commit `d59a99fc00dfb98086e2dbd9472fcf0eb0b96a1a`은 Line 0002 REQ와 `ac-0004`~`ac-0006`을 처음 추가하면서 바로 `approved`·`active`로 기록했다.
- Commit `a33928860b9079fb15ec4497b0c4f753e90e6afb`도 Line 0004 `req-0004`, `ac-0007`, `ac-0008`을 처음 추가하면서 바로 `approved`·`active`로 기록했으며, 그 parent에는 `req-0004.md`가 존재하지 않는다.
- `src/proofline/validator.py`는 REQ `draft|approved|withdrawn`과 AC `draft|active|retired` vocabulary 및 현재 artifact reference를 검증하지만 approval commit parent의 draft bytes나 transition diff를 검사하지 않는다.
- `skills/proofline-start-implementation/scripts/create_worktree.py:113-138`은 지정된 approval commit에서 Discovery `confirmed`, REQ `approved`, Line `not_started`를 확인하지만 그 parent의 REQ·AC draft 상태는 확인하지 않는다.
- 사용자는 신규 approval 시 draft가 없으면 no-mutation으로 중단하고, 과거 Line history를 rewrite하지 않으며, 절차 증가는 draft review gate와 별도 approval commit 하나로 제한하는 방향을 승인했다.

## Scope

- 신규 REQ와 REQ의 `criteria.create`에 포함되는 신규 AC를 처음 기록할 때 각각 `status: draft`로 작성하고 main에 draft specification commit으로 보존한다.
- Draft commit 후 REQ objective·scope·non-goals, 대상 AC criterion·verification과 변경 집합을 사용자에게 요약하여 명시적 approval을 받는다.
- Approval은 clean `main`에서 수행하며 current HEAD에 같은 Line의 draft REQ와 모든 create 대상 draft AC가 존재하지 않으면 artifact, working tree, Git ref를 변경하지 않고 중단한다.
- Approval 전에 draft 본문 수정이 필요하면 `draft` 상태에서 수정·검증·commit한 뒤 다시 review한다.
- 명시적 approval 후 별도 main governance commit에서 REQ `draft→approved`와 create 대상 AC `draft→active`만 전환한다.
- Approval commit의 immediate parent가 검토된 draft bytes를 소유하고, approval commit diff에서 허용된 lifecycle status 외 REQ·AC 의미가 바뀌지 않았는지 검증한다.
- Approval commit과 그 parent의 exact relation, REQ·AC identity·상태·본문 불변성을 temporary Git fixture test로 검증한다.
- Repository-owned Hermes specification approval workflow와 checklist를 제공하되, agent는 사용자 대신 approval 결정을 내리지 않는다.
- Line 0004에서 제공한 worktree creation preflight가 신규 Line의 approval commit parent에 draft REQ·AC가 존재하고 허용된 status-only transition인지 확인하도록 보강한다.
- Transition 검사는 specification approval과 implementation 시작 경계에서 수행하며 일반 `proofline validate` 실행마다 전체 Git history를 재검사하지 않는다.
- Line 0002와 Line 0004의 기존 history는 rewrite하지 않고 이 Discovery와 Issue #6의 retrospective evidence로 보존한다.

## Out of Scope

- 사용자 승인 없는 자동 approval 또는 lifecycle transition
- ProofLine CLI가 Git commit, branch, worktree, merge 또는 push를 수행하는 기능
- Line 0002·0004와 기존 commit의 rewrite, squash 또는 synthetic draft commit 삽입
- 기존 active AC의 update·재승인과 AC retirement workflow 일반화
- REQ·AC 본문을 자동 생성하거나 product 의미를 자동 판단하는 기능
- 모든 `proofline validate` 실행에서 full Git history를 scan하는 gate
- 별도 approval database, 서명 infrastructure 또는 remote review service
- Main governance 직렬화 원칙, DQC·IQC 또는 fast-forward integration 계약 변경
- `proofline update`, release source, version pinning 또는 rollback

## Risks and Unknowns

### Risks

- Draft review gate와 approval commit 분리로 신규 Line마다 사용자 확인 한 번과 commit 하나가 추가된다. Workflow는 기존 contract를 반복 설명하거나 별도 상태 저장소를 만들지 않고 summary·status-only transition·검증만 제공해야 한다.
- Approval 직전에 formatting이나 본문까지 함께 수정하면 status-only audit boundary가 깨진다. 이 경우 approval을 중단하고 변경을 draft commit으로 먼저 보존해야 한다.
- Worktree preflight의 parent-transition 검사는 Line 0002·0004처럼 이미 delivered된 legacy baseline을 소급 무효화해서는 안 된다. 신규 implementation 시작 경계에 적용하고 과거 history는 retrospective evidence로만 유지한다.

### Assumptions

- Main governance는 직렬화되어 approval commit의 immediate parent가 승인 직전 draft state를 소유할 수 있다.
- 사용자의 명시적 approval message가 lifecycle decision authority이며 Hermes workflow는 그 결정 후 deterministic status transition과 검증만 수행한다.
- 이번 Line은 신규 REQ와 신규 create AC 경로를 먼저 완결하며 update·retire lifecycle은 독립된 필요가 확인될 때 별도 Line으로 다룬다.
