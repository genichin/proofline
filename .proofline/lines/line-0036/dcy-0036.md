# schema-v1: line 아티팩트에 status 및 세션/작업 로그 연계 추가

## Problem

현재 Line artifact는 `id`만 가지므로 사람이 각 Line의 대략적인 진행 단계와 최근 활동을 한눈에 확인하기 어렵다. 또한 에이전트가 구현할 때 세운 계획과 TODO, 진행 상황, blocker, 검증 결과 및 다음 행동을 사용자가 나중에 참고할 수 있는 Line별 영속 기록이 없다. Issue #28이 요구하는 상태와 세션·작업 로그 연계는 운영 가시성을 위한 표시 정보이며, 구현 완료·검증 통과·delivery를 판정하거나 보증하기 위한 근거가 아니다. 현재 계약은 이 표시 정보까지 제거했기 때문에 사용자가 개별 세션이나 외부 시스템을 찾아야 한다.

## Evidence

- `E-001` 2026-09-02 12:38 KST에 확인한 [GitHub Issue #28](https://github.com/genichin/proofline/issues/28)은 `line` frontmatter의 상태 필드, 별도 append형 세션·작업 로그, 상태 전이 이벤트와 로그 연동, 기존 Line 마이그레이션을 제안한다. Issue는 2026-08-25에 생성된 open enhancement이며 댓글로 보완된 결정은 없다.
- `E-002` 현재 기준 revision `f59faab909819adb4d8e6ebd4e8f64088cc8c410`의 `docs/contracts/line-delivery.md`는 Line이 작업·검증·통합·delivery 상태를 소유하지 않고 `id`만 가진 frontmatter-only 문서라고 규정한다.
- `E-003` `docs/contracts/document-format.md`는 Line에 status가 없고 Git 또는 외부 시스템 소유 metadata와 정의되지 않은 frontmatter key를 금지한다. `templates/schema-v1/artifacts/line.md`도 `id`만 생성한다.
- `E-004` `src/proofline/validator.py`의 `ARTIFACT_FIELDS`는 Line의 current field를 `id` 하나로 제한하고, 과거 `execution_status`와 `implementation_history`만 값을 해석하지 않는 deprecated metadata로 허용한다.
- `E-005` Line 0027의 confirmed Discovery와 approved REQ는 보증과 연결되지 않은 Line execution lifecycle을 제거하고 프로젝트별 운영 상태를 ProofLine canonical schema 밖에 두었다. 이때 상태를 검증 authority와 분리된 단순 표시 정보로 유지하는 요구가 반영되지 않았으며, active `ac-0004`는 Line bootstrap 결과를 id-only Line과 draft Discovery로 규정한다.
- `E-006` `docs/contracts/storage-and-retention.md`는 canonical tree에 원시 대화·debug log를 저장하지 않으며, `evidence/`에는 사람이 선별한 Markdown 참고 문서만 허용하고 이를 canonical 상태나 완료 근거로 사용하지 않도록 규정한다.
- `E-007` 사용자는 2026-09-02에 Line 상태는 진행 상황을 표시하기 위한 정보일 뿐이며, 현재 단계에서는 이를 검증이나 완료 판정에 사용할 필요가 없다고 명확히 했다.
- `E-008` 사용자는 에이전트가 구현할 때 계획과 TODO, 진행 상황 등을 기록하고 사용자가 참고할 수 있는 Line별 로그가 필요하다고 명확히 했다.

## Scope

- `S-001` Line에 사람이 현재 진행 단계를 빠르게 파악할 수 있는 단일 `status` 표시를 추가하고 `phase`처럼 의미가 중복되는 별도 field는 두지 않는다. 초안 권장 값은 `discovery`, `specification`, `implementation`, `verification`, `release`, `retired`이다.
- `S-002` 일반적인 표시 순서는 `discovery → specification → implementation → verification → release → retired`로 문서화하되, 필요하면 실제 작업 흐름에 맞게 앞 단계로 돌아갈 수 있다. 기록된 상태를 구현 완료·검증 통과·통합·delivery의 증거 또는 gate로 해석하지 않는다.
- `S-003` `status`는 선택 field로 둔다. Validator는 Line에 `status`가 있는지만 확인하고, 없으면 validation을 실패시키지 않는 warning만 출력한다. 값은 권장 vocabulary를 안내하되 enum으로 제한하거나 전이, 실제 작업 상태, Git chronology를 검증하지 않는다.
- `S-004` 에이전트는 구현 작업을 시작하고 진행하거나 중단·검증·인계할 때 계획, TODO 상태, 완료한 작업, 현재 진행 상황, blocker, 주요 결정, 검증 결과와 다음 행동을 사용자가 읽을 수 있는 간결한 Line 활동 로그에 기록한다.
- `S-005` 활동 로그의 권장 위치는 `.proofline/lines/line-NNNN/evidence/activity-log.md`이며 canonical 상태나 완료 증거가 아닌 비정본 참고 문서로 유지한다. 각 의미 있는 갱신은 시각, 작성 주체 또는 세션 식별, 구분, 요약과 다음 행동을 포함한 새 항목으로 append하고 기존 chronology를 임의로 다시 쓰지 않는다.
- `S-006` Line에는 사용자가 활동 로그를 쉽게 찾을 수 있도록 최근 활동 요약과 상대 링크를 표시한다. 로그가 없거나 오래됐다는 사실은 validation 실패, 구현 중단 또는 delivery 차단 조건이 아니다.
- `S-007` 로그에는 원시 transcript나 내부 추론을 복사하지 않고 사용자가 작업 상태를 이해하고 이어받는 데 필요한 결과 중심 정보만 기록한다. 동시 append 충돌, 보존 한계 및 credential·개인정보 제외 경계를 정의한다.
- `S-008` 기존 Line은 소급 변경을 강제하지 않고 `status`가 없으면 warning만 허용하며, 활동 로그가 없는 것은 별도로 경고하거나 실패시키지 않는다. 현재 `execution_status`와 `implementation_history`는 opaque metadata로 보존하고 신규 상태 표시와의 호환 규칙을 명시한다.
- `S-009` AC admission은 id-only bootstrap을 변경하므로 active `ac-0004`를 `update`하고, 검증 authority가 없는 상태·활동 표시 동작은 독립적인 장기 product behavior로 `create`하는 방향으로 분류한다.

## Out of Scope

- `OS-001` 상태 값만으로 구현·검증·통합·delivery 완료를 판정하거나 보증하는 기능
- `OS-002` 기존 Line artifact와 Git history의 일괄 재작성 또는 삭제
- `OS-003` 원시 대화, 내부 chain-of-thought, 전체 에이전트 transcript, debug log, credential 또는 개인정보를 `.proofline/`에 저장하는 기능
- `OS-004` GitHub Issues, Kanban, CI 또는 에이전트 세션 관리 시스템 자체를 ProofLine으로 대체하는 기능

## Risks and Unknowns

### Risks

- `R-001` Line status가 GitHub Issue, 작업 보드 또는 CI 상태와 다를 수 있다. 이를 표시 정보로 명시하고 검증·완료 판정에 사용하지 않아 의미 확대를 방지해야 한다.
- `R-002` append형 로그를 Git 추적 artifact로 만들면 동시 작업의 충돌, 무제한 증가, secret 유입과 보존 정책 문제가 생길 수 있다.
- `R-003` 과거에 제거한 field와 이름 또는 값이 겹치면 기존 Line의 의미를 잘못 해석할 수 있으므로 신규 표시 schema와 legacy metadata의 호환 경계를 명확히 해야 한다.
