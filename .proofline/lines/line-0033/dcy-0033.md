# Agent Skill Installation Management

## Problem

ProofLine 패키지는 기준이 되는 에이전트 스킬 파일을 포함하지만, 사용자가 실제 Hermes·Codex 에이전트에서 사용할 수 있도록 각 에이전트의 스킬 탐색 위치에 설치하고 이후 ProofLine 버전과 함께 안전하게 갱신·진단·제거하는 제품 경계가 없다. 현재 `proofline init`과 업데이터는 패키지 자원을 별도의 관리 대상 `~/.proofline/` 트리로 펼치고 그 안의 스킬을 사용자 실행 환경으로 취급한다. 그러나 에이전트는 이 중간 트리를 직접 사용하지 않으며, 사용자가 실제 에이전트 대상에 다시 연결하거나 복사해야 한다. 패키지 자원과 에이전트 대상 사이에 영속적인 `~/.proofline` 복사본을 유지하면 패키지·사용자 홈·여러 에이전트 복사본이 서로 다른 버전으로 남을 수 있고, 홈 매니페스트·일치화·초기 구동 규약이라는 별도 생명주기가 필요하다.

사용자는 `~/.proofline/`을 더 이상 사용하지 않고 `proofline init` 명령과 전체 사용자 홈 생명주기를 제거하기로 결정했다. 기준 원본은 설치된 패키지 또는 업데이트 대상으로 검증된 휠 자체여야 하며, 영속적인 복사본은 에이전트가 실제 탐색하는 등록 대상에만 있어야 한다.

에이전트별 스킬 디렉터리에 ProofLine 매니페스트를 두면 개별 설치는 자체 설명이 가능하다. 그러나 `proofline update`가 사용자 지정 Hermes 프로필을 포함한 모든 등록 대상을 찾기 위해 에이전트별 경로를 추측·탐색해야 하고, 에이전트가 관리 정보를 스킬로 오인할 수 있다. 반대로 모든 설치 기록을 변경 가능한 매니페스트 파일 하나에 합치면 설치·제거 하나에도 전체 레지스트리를 다시 써야 하며, 동시 실행·부분 손상·복구의 영향 범위가 모든 에이전트 설치로 확대된다. 따라서 ProofLine이 소유하는 중앙 운영체제 기본 사용자 상태 디렉터리 아래에 설치별 매니페스트를 두고 그 파일 집합 자체를 레지스트리로 사용해야 한다. 실제 에이전트 대상에는 검증된 패키지 또는 휠의 스킬 파일만 복사하는 생명주기가 필요하다.

## Scope

- `proofline init` 공개 명령과 업데이트 후 암묵적인 홈 일치화를 제거한다. ProofLine은 `~/.proofline/`을 생성·읽기·검증·갱신·백업·삭제하지 않으며, 사용자 홈 환경을 기준 자원 위치나 실행 선행조건으로 사용하지 않는다.
- 기존 `~/.proofline/`은 새 ProofLine 실행의 소유 범위 밖에 둔다. 업데이트·설치·제거·상태·진단은 이름이나 과거 매니페스트만으로 기존 트리를 자동 삭제·이동·재사용하지 않고 그대로 보존한다. 기존 트리 정리는 이 Line의 자동 이전 범위가 아니다.
- 사용자 실행 환경 생성을 소유하는 `home_writer`, 대상 홈 생성·검증을 소유하는 `home_protocol`, 홈 매니페스트·일치화 연결부와 패키지·홈 트랜잭션 코드를 실제 제품 경로에서 제거한다. 패키지에 필요한 기준 계약·템플릿·작업 절차·스킬은 빌드 입력과 가져올 수 있는 패키지 자원으로 유지할 수 있지만, 영속적인 사용자 홈 복제본과 초기화된 홈 일치를 제품 계약으로 주장하지 않는다.
- 저장소 소스와 빌드된 휠은 에이전트 설치·업데이트에 필요한 완전한 `proofline-*` 스킬 목록과 보조 파일을 같은 상대 경로와 바이트로 제공해야 한다. 패키지 자원의 내부 이름은 구현 세부사항일 수 있으나 공개 파일시스템의 `~/.proofline`을 요구해서는 안 된다.
- `proofline agent-skill setup`, `proofline agent-skill remove`, `proofline agent-skill status`, `proofline agent-skill doctor`를 명시적인 에이전트 연동 생명주기로 도입한다.
- 초기 지원 어댑터는 Hermes와 Codex로 한정한다. 각 어댑터는 에이전트 실행 파일·설정과 사용자가 선택한 프로필 또는 범위를 읽기 전용으로 조사하여 실제 대상 루트와 배치 구조를 확정한다. 변경 명령은 이 결과를 변경 전에 다시 확인한다. 알 수 없는 에이전트, 존재하지 않는 프로필, 모호한 대상, 지원하지 않는 구조는 추측하지 않고 중단한다.
- 설치는 **복사 전용**으로 고정한다. 심볼릭 링크, 하드 링크, Windows 정션, Hermes `skills.external_dirs` 수정, 에이전트 설정 다시 쓰기를 사용하지 않는다.
- `agent-skill setup`의 기준 원본은 **현재 실행 중인 설치된 ProofLine 패키지의 검증된 내장 스킬 자원**이다. 별도의 영속 원본 디렉터리에 먼저 복사하지 않으며 인접 source checkout을 대체 원본으로 사용하지 않는다. 패키지 버전·배포 출처·스킬 목록·경로 형식·바이트를 대상 준비 전에 검증하고, 설치 패키지로 입증할 수 없거나 원본이 불완전·안전하지 않거나 식별자가 맞지 않으면 에이전트 대상을 변경하지 않는다.
- `proofline update`의 기준 대상 원본은 체크섬과 출처를 검증한 정확한 대상 휠이다. 업데이터는 대상 휠의 스킬 파일을 격리된 임시 준비 위치로 직접 추출·검증하여 등록 대상용 파일을 준비하고, 성공 또는 복구 후 준비 위치를 삭제한다. 임시 준비 위치는 영속적인 기준 복사본이나 사용자 실행 환경이 아니다.
- Hermes 어댑터는 확인된 프로필 스킬 루트 아래 `proofline/` 묶음 디렉터리에 `proofline-*` 스킬 디렉터리를 복사한다. Codex 사용자 어댑터는 확인된 `$HOME/.agents/skills/` 아래 `proofline-*` 스킬 디렉터리를 직접 복사한다. 어댑터별 대상 경로는 논리적 범위에서 계산하되 사용자 홈·환경·에이전트 설정을 운영체제 기본 경로로 해석하고, 매니페스트에는 정규화된 절대 대상을 기록한다.
- 중앙 변경 상태 루트는 응용 프로젝트와 에이전트 대상 밖의 운영체제 기본 사용자 상태 위치에 둔다. Linux에서는 `${XDG_STATE_HOME:-~/.local/state}/proofline/agent-skills/`, Windows에서는 `%LOCALAPPDATA%\ProofLine\State\agent-skills\`에 대응하는 경로를 사용한다. 경로는 하나의 운영체제 추상화 계층에서 결정하며 `~/.proofline`, 임의의 현재 작업 디렉터리, 저장소 내부 대체 경로를 사용하지 않는다.
- 중앙 상태 루트 아래 설치 단위별 매니페스트를 저장하고 그 파일 집합 자체를 레지스트리로 사용한다. 예시는 `hermes/default.yaml`, `hermes/<profile>.yaml`, `codex/user.yaml`이며 별도의 전역 `registry.yaml`은 두지 않는다. 에이전트·프로필 또는 범위의 논리적 식별자를 안전하고 충돌 없이 파일 경로에 대응시키고, 예약 이름·경로 구분자·대소문자 무시 충돌·상위 경로 이탈을 변경 전에 거부한다.
- 각 설치 매니페스트는 스키마 버전별 닫힌 필드 집합으로 소유자, 에이전트, 논리적 프로필 또는 범위, 배치 구조, 확인된 대상 루트, 설치된 ProofLine 버전, 원본 휠 또는 패키지 식별자, 전체 파일 해시, 각 관리 대상 상대 경로의 형식·SHA-256과 ProofLine이 생성한 묶음 디렉터리의 소유권을 기록한다. 절대 원본 경로 자체를 파일 식별자로 사용하지 않으며 대상 밖 경로·중복 경로·알 수 없는 스키마 버전·정의되지 않은 추가 필드·잘못된 해시를 거부한다.
- 대상 스킬 디렉터리에는 ProofLine 연동 매니페스트를 복사하지 않는다. 중앙 매니페스트가 유효하고 저장 대상의 관리 경로 집합·형식·바이트가 현재 설치된 ProofLine 패키지의 동일 스킬 버전과 정확히 일치할 때만 ProofLine 소유 설치를 `healthy`로 판정한다. 현재 에이전트 프로필의 재해석 결과와 실제 세션의 스킬 로드·사용 이력은 `healthy` 판정에 포함하지 않는다.
- `setup`은 패키지 원본·어댑터·대상·기존 중앙 기록을 모두 사전 점검하고, 대상 밖 같은 파일시스템의 인접 준비 위치에 파일을 완전히 복사해 다시 읽은 뒤 교체한다. 동일한 논리 설치와 동일한 파일은 아무 변경 없이 성공한다. 기존 중앙 매니페스트 없이 대상에 같은 이름의 디렉터리나 파일이 있거나 기록된 바이트와 대상 바이트가 다르면 각각 관리되지 않은 충돌 또는 변형으로 판정하고 자동 덮어쓰지 않는다.
- 초기 버전에는 광범위한 `--force`를 제공하지 않는다. `proofline agent-skill setup --adopt-existing`은 현재 어댑터가 대상 경로를 명확하게 다시 확인하고 기존 대상의 관리 경로 집합·형식·바이트가 현재 패키지의 검증된 기준 스킬과 정확히 일치할 때만 대상 바이트를 변경하지 않고 중앙 매니페스트를 생성한다. 심볼릭 링크·하드 링크·재분석 지점, 대상 밖 경로, 예상하지 않은 관리 파일 또는 한 바이트라도 다른 파일이 있으면 충돌로 거부한다. 기존 Hermes 묶음 디렉터리처럼 ProofLine이 생성하지 않은 디렉터리는 ProofLine 소유로 기록하지 않으며, 명시적 선택 없이 기존 대상을 자동 등록하지 않는다.
- `remove`는 중앙 매니페스트가 소유하고 대상 재확인 결과가 기록된 경로 집합·형식·SHA-256과 일치하는 설치만 제거한다. 변형, 잘못된 매니페스트, 대상 루트 불일치, 대상 밖 경로 해석이 있으면 삭제하지 않는다. 관리 대상 말단과 매니페스트가 생성 소유권을 기록한 빈 묶음 디렉터리만 정리하며, 에이전트 루트와 관련 없는 사용자 스킬은 보존한다. 대상 삭제를 확인한 뒤 해당 설치 매니페스트를 원자적으로 제거한다.
- `proofline agent-skill repair`는 명시적으로 선택한 등록 설치의 유효한 매니페스트가 대상 루트와 관리 경로의 ProofLine 소유권을 계속 입증하고 현재 어댑터의 대상 재확인이 일치할 때만 `drifted`·`missing` 관리 파일을 현재 설치된 패키지의 검증된 동일 스킬 바이트로 트랜잭션 방식 복구한다. 관리 경로 밖 파일은 변경하지 않으며, 소유권 핵심 필드가 잘못되거나 대상이 모호한 `invalid-manifest`에는 대상 복구를 수행하지 않는다. 복구 후 대상과 매니페스트를 현재 패키지 식별자로 다시 기록·검증하고 `healthy`가 아니면 성공을 반환하지 않는다.
- `proofline agent-skill unregister`는 명시적으로 선택한 설치의 중앙 매니페스트만 원자적으로 제거하고 대상 파일·디렉터리는 읽기 확인 외에 변경하지 않는다. 잘못된 매니페스트도 안전하게 식별된 에이전트·프로필 또는 범위의 중앙 등록 파일 자체만 해제할 수 있으며, 대상은 관리되지 않는 기존 파일로 남는다는 경고를 출력한다. `repair`와 `unregister`는 새 변경 전에 중단된 journal 복구와 대상·등록 잠금을 수행하며, `status`와 `doctor`가 암묵적으로 호출하지 않는다.
- `doctor`는 설치된 패키지 원본과 전체 또는 선택한 설치의 매니페스트·대상을 읽기 전용으로 검사하여 최소 `healthy`, `outdated`, `drifted`, `missing`, `conflict`, `invalid-manifest`, `unsupported` 상태와 안정적인 진단을 반환한다. 기본 진단은 복구·등록·복사·삭제를 수행하지 않는다.
- `proofline agent-skill status`는 중앙 상태 루트에 등록된 전체 설치 또는 명시적으로 선택한 에이전트·프로필·범위의 상태를 한눈에 보는 읽기 전용 요약 인터페이스다. 기본 사람이 읽는 출력은 에이전트, 논리적 프로필 또는 범위, 확인된 대상, 설치된 ProofLine 버전, 상태를 결정론적으로 정렬한 표와 `registered`·`healthy`·`outdated`·`blocked` 개수를 제공한다. `--json`은 같은 의미의 버전이 지정된 안정 스키마를 제공한다. 매니페스트 하나가 잘못되어도 해당 기록을 `invalid-manifest`로 표시하고 안전하게 식별할 수 있는 나머지 설치를 계속 나열한다.
- `agent-skill status`는 현재 설치된 패키지 파일과 각 매니페스트·저장 대상의 로컬 경로 집합·형식·SHA-256만 공통 상태 검사로 비교한다. 현재 에이전트 프로필을 다시 해석하거나 세션 사용 이력을 조회하지 않으며, 네트워크·릴리스 검색·복구·등록·복사·삭제를 수행하지 않는다. 등록 설치가 없으면 빈 레지스트리를 정상으로 보고한다. 하나 이상 `drifted`, `missing`, `conflict`, `invalid-manifest`, `unsupported`이면 요약을 끝까지 출력한 뒤 0이 아닌 종료 코드를 반환한다. `outdated`는 대상이 설치된 패키지보다 이전 파일임을 뜻하며 기본 업데이트로 일치시킬 수 있는 상태로 구분한다.
- `proofline status`는 현재 실행 중인 설치 패키지, 현재 작업 디렉터리의 ProofLine 프로젝트 존재 여부와 로컬 검증 결과, 중앙 레지스트리의 에이전트 스킬 요약을 하나의 읽기 전용 로컬 상태로 집계한다. 패키지 구역은 설치 버전과 로컬에서 입증 가능한 설치 출처를, 프로젝트 구역은 `not-detected` 또는 발견된 프로젝트 루트·검증 상태를, 에이전트 스킬 구역은 `agent-skill status`와 같은 개수·최악 상태를 표시한다. 현재 디렉터리에 프로젝트가 없는 것은 오류가 아니며 임의의 상위·인접 저장소를 탐색하거나 생성하지 않는다.
- `proofline status`는 암묵적인 네트워크 요청이나 업데이트 확인을 수행하지 않는다. 최신 공식 릴리스 조회는 기존 `proofline update --check`의 책임으로 유지한다. 사람이 읽는 출력과 `--json` 스키마는 패키지·프로젝트·에이전트 스킬 구역을 항상 구분한다. 일부 구역이 유효하지 않아도 안전하게 계산 가능한 다른 구역을 계속 출력한 뒤 전체 결과에 맞는 0이 아닌 종료 코드를 반환한다.
- `proofline agent-skill doctor`는 상태 요약에서 발견한 특정 설치의 매니페스트 필드, 예상·실제 경로·형식·해시와 복구를 막는 원인을 자세히 보여 주는 읽기 전용 진단 인터페이스로 유지한다. `status`와 `doctor`는 같은 내부 검사 결과와 상태 용어를 사용하여 같은 대상을 서로 다르게 판정하지 않아야 한다.
- 기본 `proofline update`는 패키지와 중앙 매니페스트에 이미 등록된 모든 에이전트 스킬 설치를 같은 선택 대상 휠 식별자로 갱신한다. 새 Hermes 프로필이나 Codex 범위를 발견·등록하지 않으며 등록 설치가 0개이면 패키지만 업데이트한다.
- `proofline update --no-sync-agent-skills`는 명시적으로 패키지만 업데이트하는 제외 선택지다. 중단된 이전 트랜잭션이 있으면 OQ-004에서 정한 필수 복구와 재확인을 먼저 수행하지만, 그 이후에는 에이전트 대상과 매니페스트를 변경하지 않는다. 중앙 레지스트리는 읽기 전용으로 가능한 범위까지 검사하며 `drifted`·`missing`·`conflict`·`invalid-manifest`·`unsupported` 설치가 있어도 패키지 휠·출처·설치 대상의 사전 점검이 통과하면 패키지 업데이트를 허용한다. 패키지 설치가 성공하면 명령은 성공을 반환하되 사람이 읽는 경고와 기계 판독 결과에 에이전트 동기화가 문제 상태로 건너뛰어졌음을 `skipped-with-issues`로 표시한다. 별도의 `--sync-agent-skills` 선택 방식은 도입하지 않는다.
- `proofline update --check`는 패키지 출처·버전과 등록된 에이전트 설치 전체를 변경 없이 함께 검사하고 종합 상태를 반환한다. 변형·충돌·잘못된 매니페스트가 있으면 기본 업데이트가 차단됨을 표시하고, 패키지만 업데이트하는 선택지가 있음을 알리되 자동 선택하지 않는다.
- 기본 업데이트는 대상 휠, 패키지 설치, 중앙 레지스트리와 모든 등록 대상을 먼저 사전 점검하고 준비한다. 하나라도 변형·충돌·잘못된 상태이면 전체 변경 전에 중단한다. 모든 대상 준비와 재확인이 성공한 뒤 패키지와 에이전트 대상을 순서대로 반영한다. 실패하면 이번 실행이 변경한 패키지·대상·매니페스트를 검증된 이전 상태로 복구하여 서로 다른 선택 휠 식별자가 섞인 상태를 성공으로 보고하지 않는다.
- 여러 파일시스템에 걸친 완전한 운영체제 수준 원자성을 주장하지 않는다. 실행 단위 트랜잭션은 중앙 상태 루트의 durable journal, 검증된 백업, 소유권을 고려한 복구와 최종 재확인으로 패키지·각 등록 대상·매니페스트의 선택 휠 식별자를 확인한다. 정상 프로세스 오류뿐 아니라 강제 종료와 전원 손실로 중단된 트랜잭션도 journal로 감지한다. `status`·`doctor`·`update --check`는 이를 변경 없이 보고하고, 다음 `setup`·`remove`·`update`는 새 변경 전에 이전 트랜잭션을 자동 복구하고 재확인한다. 파일시스템 또는 하드웨어 자체 손상과 복구 실패는 성공으로 보고하지 않고 안정적인 0이 아닌 진단으로 명시한다.
- Windows의 기본 업데이트는 교체 대상 패키지 밖의 검증된 detached helper에 준비된 트랜잭션을 인계하고, 패키지를 불러온 현재 작업 프로세스가 종료된 뒤 helper가 해당 프로세스의 종료를 확인하여 패키지·등록 스킬·매니페스트 교체와 복구를 수행한다. 사용자에게 보이는 업데이트 호출은 helper가 선택 휠 식별자와 최종 상태를 재검증하기 전에 성공으로 완료되지 않으며, helper 시작·인계·실행·복구·결과 회수 중 하나라도 실패하면 성공을 반환하지 않는다.
- 홈 폐기 대상으로 진입하는 이전 실행 파일이 대상 홈 규약을 요구하므로 해당 자체 업데이트를 지원한다고 주장하지 않는다. HOME 폐기 첫 릴리스의 변경 불가능한 exact-tag `install.sh --force` 또는 `install.ps1 -Force`를 공식 패키지 전용 전환 경로로 사용한다. 설치 프로그램은 해당 태그의 휠과 `SHA256SUMS`를 엄격하게 검증하고 격리된 위치에서 대상 패키지의 설치·import 가능성을 사전 점검한 뒤 `uv tool install --force --no-config`로 교체하며, Unix와 Windows 모두 실행 버전과 설치된 distribution provenance를 다시 확인하기 전에는 성공을 반환하지 않는다. 이 전환은 기존 `~/.proofline`, 프로젝트 `.proofline/`, 중앙 에이전트 레지스트리와 에이전트 대상을 읽기·변경·백업·삭제하지 않는다. 공식 전환 검증 범위는 공개 `v0.7.0` wheel에서 HOME 폐기 첫 릴리스로의 진입이며, 이전 릴리스는 각 릴리스에 이미 정해진 기준 전환 체인을 통해 먼저 `v0.7.0`에 도달한다. 일반 `--force`가 다른 설치를 기술적으로 교체할 수 있다는 사실을 추가 지원 전환으로 주장하지 않는다. 이후 기준 버전의 업데이터에는 홈 규약을 다시 포함하지 않는다.
- 설치·제거·업데이트는 대상마다 같은 파일시스템에서 준비·백업·교체가 가능한지 변경 전에 확인한다. 대상과 매니페스트 양쪽의 심볼릭 링크·재분석 지점·일반 파일이 아닌 항목·경로 이탈·대소문자 충돌을 보수적으로 거부한다. 지원되는 Windows·Unix 파일시스템의 원자성 차이는 어댑터가 숨기지 않고 복구와 재확인으로 검증한다.
- 동시에 실행된 설치·제거·업데이트가 같은 상태 루트나 대상을 변경하지 못하도록 프로세스 단위 잠금과 오래된 잠금 복구 규칙을 둔다. 설치별 매니페스트는 임시 파일 쓰기, 가능한 범위의 `fsync`, 원자적 교체와 재확인을 사용하여 부분 YAML을 기준 상태로 남기지 않는다.
- 계약, 산출물 구조, 작업 절차, 저장소 소유 스킬, 패키지 자료와 테스트에서 `~/.proofline`, `proofline init`, 초기화된 홈 일치, 홈 규약을 현재 생명주기로 주장하는 내용을 제거하거나 과거 전환으로 명시한다. 현재 공개 문서는 프로젝트 `.proofline/`, 설치된 패키지 자원, 중앙 에이전트 상태, 에이전트 대상을 일관되게 구분해야 한다.
- 소스와 휠에서 같은 스킬 목록과 어댑터 정책이 재현되는지 검증한다. 테스트는 격리된 도구 디렉터리, 임시 사용자 홈·상태·에이전트 대상만 사용한다. 실제 `/home/genichin`, 기존 `~/.proofline`, 실제 Hermes·Codex 설정·스킬 디렉터리와 원격 자원을 변경하지 않는다.
- AC 반영 분류는 다음과 같다. `update` 대상은 `ac-0012`, `ac-0025`, `ac-0026`, `ac-0027`이다. `ac-0012`는 패키지·홈 일치와 대상 홈 규약을 폐기하고 검증된 패키지 출처·패키지 복구·등록 에이전트 설치의 동일 휠 일치화를 소유한다. `ac-0025`·`ac-0026`·`ac-0027`은 각각 승인 절차, 한국어 작성 지침, guided-worktree 동작의 제품 의미를 유지하면서 source·휠·HOME 배포 일치를 source·휠 및 등록 설치가 있을 때의 에이전트 대상 일치로 변경한다. `retire` 대상은 `proofline init`과 관리 대상 사용자 실행 환경 전체를 소유한 `ac-0016`이다. `create` 대상은 에이전트 대상·프로필 해석, 설치별 중앙 등록 정보, 설치와 명시적 기존 파일 등록, 안전한 제거, 명시적 `repair`와 `unregister`, 공통 설치 상태 판정과 상태·진단 명령, 종합 `proofline status`, 등록 설치의 기본 업데이트 동기화이다. 정확한 신규 AC ID와 독립 Criterion 경계는 이 분류를 보존하여 REQ·AC가 소유하며 `satisfy` 대상은 없다.

## Out of Scope

- 기존 `~/.proofline/`의 자동 삭제·백업·이전·등록 또는 새 에이전트 대상의 원본으로 재사용
- 심볼릭 링크, 하드 링크, Windows 정션 또는 에이전트 설정의 외부 스킬 디렉터리 연결
- 에이전트 스킬 파일의 백그라운드 감시, 상주 프로세스, 암묵적 자동 동기화 또는 에이전트 실행 중 즉시 다시 읽기 보장
- 매니페스트가 없는 에이전트 프로필·범위의 자동 탐색·등록·삭제와 임의 파일시스템 탐색
- 사용자 수정 파일의 보존 병합 또는 광범위한 `--force` 덮어쓰기
- Hermes·Codex 이외 에이전트 어댑터, 시스템 전체·관리자 범위와 저장소 지역 에이전트 스킬 설치
- 모든 설치를 단일 전역 YAML 기록에 합치거나 에이전트 대상에 ProofLine 매니페스트를 두는 설계
- 에이전트 공급자의 플러그인 장터, 클라우드 배포, 원격 게시 또는 계정 인증
- 응용 프로젝트 `.proofline/`, 의존성·잠금 파일, Git 브랜치·워크트리와 원격 저장소 변경
- Line 0030과 기존 릴리스의 과거 산출물·태그·릴리스·이슈 이력 소급 수정
- REQ·AC 승인 생명주기 또는 검증기의 기준 Line·Discovery·REQ·AC 의미 변경
- 사용자의 실제 에이전트 대상에 대한 설치·기존 파일 등록·삭제 실행과 릴리스 버전·태그·파일 게시

## Risks and Unknowns

### Risks

- 현재 이전 버전 업데이터가 대상 홈 규약을 반드시 호출하므로 새 휠에서 규약을 단순 삭제하면 홈 폐기 릴리스에 도달하기 전에 업데이트가 실패할 수 있다. 공개 `v0.7.0` wheel에서 HOME 폐기 릴리스의 exact-tag installer `--force`·`-Force` 전환을 운영체제별로 검증하고, 대상 휠 staging·설치 후 provenance 재확인 또는 HOME·프로젝트·에이전트 상태 불변 검사가 실패하면 지원 전환이나 성공으로 표시하지 않아야 한다.
- 에이전트 공급자가 프로필 경로나 스킬 탐색 구조를 변경하면 저장된 대상의 파일이 패키지와 정확히 일치하더라도 현재 에이전트가 그 경로를 탐색하지 않을 수 있다. `healthy`는 복사 일치만 판정한다는 경계를 문서화하고, 모든 변경 명령은 어댑터가 논리 식별자를 다시 해석하여 매니페스트 대상과 다르면 중단해야 한다.
- 중앙 상태 매니페스트가 삭제되면 대상 파일이 남아 있어도 ProofLine 소유권을 입증할 수 없다. 이름만으로 삭제·덮어쓰지 않고 현재 패키지 파일과 정확히 일치할 때만 등록을 허용하여 데이터 손실보다 수동 복구를 우선한다.
- 여러 파일시스템에 걸친 패키지와 에이전트 대상 전체를 하나의 운영체제 기능으로 원자적으로 반영할 수 없다. 전체 사전 점검·대상별 준비·검증된 백업·순서 있는 반영·복구·최종 재확인으로 사용자 관점의 트랜잭션을 구성하고, 복구 실패를 숨기지 않는 기계 판독 상태가 필요하다.
- 기존 `~/.proofline`을 자동 삭제하지 않으면 사용자가 이를 현재 자원으로 오해할 수 있다. 명령행 안내와 이전·릴리스 문서는 해당 트리가 더 이상 읽히거나 갱신되지 않는 폐기된 기존 자료임을 명확히 알려야 한다.
- Hermes 묶음 구조와 Codex 평면 구조를 공통 경로 결합으로 처리하면 잘못된 깊이에 복사하거나 관련 없는 디렉터리를 삭제할 수 있다. 어댑터가 명시적인 배치 대응표와 예상 관리 루트를 소유하고, 공통 트랜잭션 계층에는 검증된 상대 파일 목록만 넘겨야 한다.
- Windows의 대소문자 무시 경로, 예약 이름, 재분석 지점, 열린 파일 교체 제약은 Unix 테스트만으로 드러나지 않는다. 운영체제별 테스트와 실제 지원 운영체제 점검을 릴리스 통과 조건에 포함하되, 심볼릭 링크 권한 분기를 기능 계약으로 다시 도입하지 않는다.
