# Specification Review Skill

## Objective

ProofLine에 `proofline-review-specification` 스킬을 추가한다. 이 스킬은 Discovery를 바탕으로 작성한 REQ와 AC를 사용자가 승인하기 전에 읽기 전용으로 검토한다. 검토자는 문제가 없으면 `PASS`, 승인 전에 고쳐야 할 문제가 있으면 `BLOCK`으로 보고한다. 검토 과정에서는 문서를 수정하거나 승인하지 않는다.

## Scope

- 스킬의 원본은 `skills/proofline-review-specification/SKILL.md`에 둔다. ProofLine wheel과 등록된 Hermes·Codex에도 원본과 같은 파일을 배포한다.
- 검토 대상 문서 집합은 다음과 같다.
  - 상태가 `confirmed`인 Discovery
  - 상태가 `draft`인 REQ
  - REQ의 `create`, `update`, `retire`, `satisfy`에 포함된 모든 AC
  - REQ에 적힌 모든 `Normative Design Documents`
- `Normative Design Documents` 목록이 없는 REQ도 정상적으로 검토할 수 있다. 반대로 일부 AC나 문서를 빠뜨린 채 전체 명세를 `PASS`로 판정해서는 안 된다.
- 참조된 설계 문서는 저장소 내부의 실제 Markdown 일반 파일이어야 한다. 파일이 없거나, 심볼릭 링크이거나, 저장소 밖을 가리키거나, Markdown 일반 파일이 아니면 `BLOCK`으로 판정한다.
- Discovery와 REQ 사이에서 다음을 확인한다.
  - Discovery의 문제, 근거, 범위와 제외 범위가 REQ에 빠짐없이 반영됐는가
  - REQ가 Discovery에서 정한 범위를 넘어가지 않는가
  - REQ의 목표, 범위, 제약과 제외 범위가 서로 모순되지 않는가
  - 자리표시자나 해결되지 않은 중요 질문이 남아 있지 않은가
- REQ와 AC 사이에서 다음을 확인한다.
  - REQ가 참조한 모든 AC가 존재하고 상태와 `create/update/retire/satisfy` 분류가 올바른가
  - 각 AC가 하나의 지속적인 요구사항을 독립적으로 표현하는가
  - 각 AC를 관찰 가능한 결과로 `PASS` 또는 `FAIL` 판정할 수 있는가
  - `Verification`이 `Criterion` 전체를 검사하는가
  - 필요한 정상, 실패, 경계 및 변경 없음 조건이 포함됐는가
  - AC 사이에 누락, 중복, 모순, 고립 또는 범위 초과가 없는가
  - 기존 활성 AC와 충돌하거나 불필요하게 중복되지 않는가
- REQ가 설계 문서를 참조하면 Discovery, REQ, 전체 AC와 설계 문서의 기술 내용이 서로 일치하는지 확인한다.
- 승인 전에 반드시 고쳐야 하는 문제와 참고 사항을 구분한다. 승인 차단 문제에는 다음 세 항목을 함께 적는다.
  1. 판단 근거가 되는 승인된 요구사항 또는 저장소 규칙
  2. 문제가 되는 구체적인 문구나 동작
  3. 문제를 해결하는 데 필요한 최소 수정
- 선택적 개선이나 새로운 정책 제안은 기존 승인 범위를 위반하지 않는 한 승인 차단 문제로 취급하지 않는다.
- 검토 결과에는 다음을 포함한다.
  - `Verdict: PASS` 또는 `Verdict: BLOCK`
  - `Mutation performed: false`
  - 실제로 검토한 문서의 경로와 식별정보
  - Discovery, REQ, AC와 설계 문서 사이의 요구사항 반영표
  - 승인 차단 문제
  - 승인 차단이 아닌 참고 사항
  - 문서 내용과 상태를 변경하지 않았다는 확인
- 승인 차단 문제가 하나라도 있으면 결과는 `BLOCK`이다. 문서를 수정하거나 검토 중 내용이 바뀌면 수정된 검토 대상 문서 집합 전체를 다시 읽고 검토해야 하며, 이전 `PASS`를 재사용하지 않는다.
- `PASS`는 사용자 승인을 대신하지 않는다. `PASS`가 나온 뒤에도 `proofline-approve-specification` 절차에서 사용자가 REQ와 AC를 명시적으로 승인해야 한다.
- 스킬의 필수 절차와 권한 경계를 테스트한다. 또한 원본, wheel, Hermes와 Codex에 배포된 파일의 내용이 같은지 확인한다.

## Constraints

- 현재 ProofLine의 상태 체계와 `proofline validate` 동작을 변경하지 않는다.
- `proofline validate` 통과는 검토를 시작하기 위한 구조 검사 결과일 뿐이며, 의미 검토의 `PASS`를 대신하지 않는다.
- 검토 결과는 실제로 검토한 문서와 내용에만 적용된다. 검토 대상 문서가 추가·삭제·수정되거나 검토 중 내용이 달라지면 전체 문서 집합을 다시 검토한다.
- 검토자는 Discovery, REQ, AC, 설계 문서, Git 상태를 변경하지 않는다.
- 검토자는 Discovery 확인, REQ·AC 승인, 상태 전환 또는 사용자에게 승인 결정을 대신 요청하는 일을 수행하지 않는다.
- 설계 문서에 별도의 상태, 승인 정보 또는 검토 증적 형식을 추가하지 않는다.
- 민감정보, 인증정보, 토큰 또는 연결 문자열은 출력하지 않고 `[REDACTED]`로 가린다.
- 사람이 작성하는 본문은 원칙적으로 한국어로 작성한다. H1 제목과 구조적 heading, ID, status, YAML key, CLI, 코드, path, 고유 기술 용어 및 영어가 의미를 더 정확하게 전달하는 내용은 영어로 유지할 수 있다. 이 원칙은 작성 지침이며 문서의 한국어 여부를 validator·QC·CI의 통과 조건으로 만들지 않는다.

## Non-Goals

- REQ, AC, Discovery 또는 설계 문서를 작성하거나 직접 수정하는 기능
- 사용자를 대신한 명세 승인이나 상태 전환
- `proofline validate`에 자연어 의미 검사를 추가하거나 새 CLI 명령을 만드는 작업
- Micro-SPEC, 구현, IQC, DQC, 전달, 릴리스 또는 공개 절차 검토
- 새로운 `.proofline/` 문서 종류, 검토 증적 파일, 상태 또는 설계 문서 상태 도입
- 특정 LLM, 제공자, 검토자 수, 위임 방식 또는 Git 이력을 필수 조건으로 지정
- 기존 작성 스킬이나 승인 스킬의 역할을 대신하거나 승인 절차를 자동으로 실행
