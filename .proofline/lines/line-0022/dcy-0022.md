# Legacy non-terminal Line history migration hotfix

## Problem

ProofLine 0.6.0은 repository-level history policy 도입 전에 implementation·IQC evidence를 이미 가진 fieldless non-terminal Line을 사실과 Git history를 보존한 채 `implementation_history: first_parent`로 migration할 수 없다. Field를 뒤늦게 추가한 commit이 per-Line adoption baseline `B`가 되면 validator가 모든 historical implementation cycle에 `B < I`를 소급 적용하여 과거 `I/Q`를 `history.ms.order` 또는 binding error로 거부한다. 반대로 field를 추가하지 않으면 `history.line.policy.missing`이 유지된다.

Terminal 전환, stale SHA 치환 또는 historical artifact 수정은 lifecycle 사실과 exact evidence identity를 왜곡한다. 따라서 migration 대상과 pre-migration evidence boundary를 canonical하게 선언하고 검증하되 migration 자체를 DQC PASS·integration·delivery로 승격하지 않으며, migration 뒤 fresh first-parent rework chronology를 시작할 수 있는 corrective patch가 필요하다.

## Evidence

- GitHub Issue [#20](https://github.com/genichin/proofline/issues/20)은 `proofline 0.6.0`에서 fieldless non-terminal Line이 `history.line.policy.missing`으로 실패하고, 현재 field 추가 후에는 기존 implementation/IQC가 새 baseline `B`보다 앞서 `history.ms.order` 또는 binding failure가 되는 재현과 acceptance matrix를 제공한다.
- `src/proofline/implementation_history.py:850-906`은 per-Line 최초 `implementation_history: first_parent` index를 baseline으로 선택하고 fieldless non-terminal을 `history.line.policy.missing`으로 거부한다. `:1048-1150`은 모든 persisted implementation cycle을 감사하며 `baseline < implementation`을 요구하므로 pre-`B` historical cycle을 migration provenance 없이 허용할 수 없다.
- `docs/contracts/line-delivery.md:173-184`는 fieldless terminal legacy와 prospective policy adoption만 정의한다. Existing non-terminal Line은 implementation/IQC 전에 adoption한다고 가정하므로 이미 evidence가 존재하는 pre-adoption case의 canonical migration artifact, evidence mapping 또는 post-migration chronology가 없다.
- Current public `v0.6.0` source tree의 history inventory에서 repository first policy activation은 commit `031c91dc6e21497bf814436e89730e3d5f5550c5`이다. Current canonical Lines에는 fieldless non-terminal이 0개, pre-activation fieldless terminal이 17개, policy-bearing Line이 3개였다. 따라서 #20은 ProofLine repository 자체의 현재 violation이 아니라 적용 project에서 발생하는 migration gap이며 synthetic Real-Git fixture로 재현해야 한다.
- `tests/test_implementation_history.py:854-958`과 후속 parity registry는 pre-adoption terminal legacy, fieldless non-terminal rejection, unpersisted policy, activation cutoff와 policy immutability를 검증하지만 pre-adoption implementation/IQC history를 가진 non-terminal migration positive path는 없다.
- Official wheel release contract는 exact candidate source/full regression, fresh wheel, isolated installed artifact, wheel+`SHA256SUMS` allowlist, explicit publication approval와 unauthenticated read-back을 요구하고 PyPI와 hosted release matrix를 제외한다. Existing stable `v0.6.0` tag·Release·assets는 immutable하다.

## Scope

- Pre-activation에 생성되고 fieldless `in_progress` 또는 `verifying` 상태이며 policy activation 전에 persisted implementation/IQC history가 존재하는 Line만 명시적 migration 대상으로 인정한다. `not_started`, terminal, policy activation 이후 생성, 이미 policy-bearing 또는 evidence가 없는 Line은 이 migration을 사용할 수 없다.
- Migration baseline `B`에서 대상 Line에 `implementation_history: first_parent`를 추가하고, 같은 commit에 `.proofline/lines/line-NNNN/legacy-migration-NNNN.md` frontmatter-only artifact를 정확히 하나 도입한다. Artifact의 path·`legacy-migration-NNNN` identity·target `line-NNNN`은 서로 일치해야 하며 다른 Line 또는 project-level manifest가 authority를 공유할 수 없다. Containing commit 자체가 `B`이고 artifact의 `pre_migration_parent`는 exact `B^1`이어야 한다. Git entry type·strict frontmatter·single-owner history를 검증하고 self-referential `migration_commit` field는 두지 않는다.
- Migration authority는 `B` 이전 대상 Line의 canonical Micro-SPEC, IQC 및 존재하는 DQC evidence를 exact path·identity·result·binding commit과 Git object provenance로 전수 inventory한다. 기존 artifact bytes/result/status를 변경하지 않고 stale·missing·duplicate·mismatched mapping, artifact 변경·제거와 duplicate migration을 거부한다.
- Mapped pre-`B` cycles에는 prospective `B < I` ordering을 소급 적용하지 않지만, exact Git object·artifact identity·IQC binding과 blocked/failed/passed result를 보존한다. Migration은 historical cycle을 새 policy PASS로 재분류하거나 implementation semantic quality를 승인하지 않는다.
- Migration 뒤 target Line은 기존 non-terminal 상태를 유지한다. Formal recovery는 `B` 뒤 별도 persisted `verifying|in_progress → in_progress` fresh rework start `P₂`, strict descendant non-governance implementation `I₂`, fresh implemented/IQC `Q₂`, integration `V₂`와 DQC를 요구하며 pre-`B` `P/I/Q`를 fresh evidence로 재사용하지 않는다.
- Empty commit, `.proofline/**`-only commit, tree-equivalent/stale SHA, blocked DQC와 terminal 우회를 implementation·DQC·delivery evidence로 인정하지 않는 기존 fail-closed behavior를 유지한다.
- Missing/shallow/malformed Git history, non-regular historical canonical entry, inherited Git routing/config와 unbounded subprocess 조건은 기존 `history.unavailable` 및 hardened read-only boundary로 실패한다.
- Validator schema·history reader·contract·artifact layout/template·user migration procedure와 source/isolated-wheel/packaged-resource Real-Git positive·negative parity를 동기화한다.
- Existing native `first_parent` Line, pre-adoption terminal legacy, current Line-0018~0020 history, DQC/integration/delivery와 no-mutation regression을 유지한다.
- Exact corrective candidate는 official release contract에 따라 package version과 release-facing installer/docs/tests를 `0.6.1`로 동기화하고, 별도 사용자 publication approval 뒤 annotated `v0.6.1` tag와 stable GitHub Release를 wheel+`SHA256SUMS` allowlist로 게시하여 unauthenticated public read-back을 수행한다.
- AC admission은 existing history lifecycle criterion `ac-0021`의 observable migration PASS/FAIL 집합을 `update`하고 mandatory hosted Line DQC criterion `ac-0010`을 의미 변경 없이 `satisfy`하는 것으로 제한한다. Version/tag/checksum은 AC가 아니라 Micro-SPEC·QC·publication evidence가 소유한다.

## Out of Scope

- Historical Git commit, existing IQC/DQC bytes·result 또는 terminal Line rewrite
- 모든 fieldless Line을 자동 허용하거나 history validation을 disable하는 opt-out/bypass
- Post-activation fieldless Line, native policy-bearing Line 또는 evidence 없는 `not_started` Line을 migration으로 구제
- Migration만으로 DQC PASS, integration candidate, delivery 또는 publication success를 주장
- Pre-`B` implementation/IQC를 post-migration fresh cycle로 재사용하거나 `P₂/I₂/Q₂`를 생략
- Full project migration 자동 실행, 여러 Line 일괄 migration 또는 cross-repository evidence import
- Production updater·installer transaction 의미 변경, PyPI publication, hosted release matrix 또는 기존 `v0.6.0` tag·Release·asset 변경
- 보존된 draft branch `draft/line-0021`의 specification 승인·구현·release 포함

## Risks and Unknowns

### Risks

- Migration authority가 historical evidence를 충분히 결속하지 않으면 임의 SHA 또는 누락 artifact가 legacy exemption으로 사용될 수 있다.
- Pre-`B` cycle을 새 lifecycle ordering에서 제외하는 경계를 넓게 구현하면 post-activation defect나 policy-bearing Line이 migration을 오용할 수 있다.
- Migration baseline과 first parent를 self-referential commit field로 표현하면 canonical bytes와 commit identity가 순환한다. Containing commit `B`와 explicit pre-migration parent binding을 분리해야 한다.
- Existing history validator는 모든 historical cycles를 감사하므로 migration-aware partition을 path·Line·baseline별로 정확히 제한하지 않으면 native Line regression 또는 old invalid cycle의 과도한 면제가 발생할 수 있다.
- 긴급 release라는 이유로 official release contract 밖 optional hosted release diagnostics를 blocker로 추가하면 publication scope가 다시 확대될 수 있다.

### Assumptions

- 적용 project는 migration 대상 Line의 complete first-parent history와 referenced Git objects를 보유한다.
- 대상 Line의 historical canonical artifacts는 exact regular blobs로 읽을 수 있으며 기존 bytes/result를 수정하지 않는다.
- Official `v0.6.1` publication 전 사용자는 exact release candidate와 artifact identity를 별도로 승인한다.
