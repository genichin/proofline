# 안전한 ProofLine project initialization

## Problem

ProofLine CLI와 user-level harness가 설치되어 있어도 fresh Git repository를 ProofLine project로 초기화하는 CLI가 없다. 현재 사용자는 `proofline.yaml`, `.proofline/lines/`, `.proofline/criteria/`를 수동으로 구성해야 하며, 이 과정에는 canonical schema, path, symlink, existing partial tree 및 no-mutation 정책을 일관되게 적용하는 writer가 없다. 그 결과 project bootstrap이 사용자별 수작업에 의존하고, 잘못되거나 Git clone에서 소실되는 scaffold가 이후 `proofline validate` 또는 `proofline line init` 단계에서 뒤늦게 실패할 수 있다.

## Evidence

- GitHub Issue [#12](https://github.com/genichin/proofline/issues/12)는 installed ProofLine CLI로 project scaffold를 초기화하는 기능, dry-run, conflict preflight, no-mutation failure, Line init 연계 및 installed-wheel E2E 검증을 요구한다.
- `src/proofline/cli.py`의 current command surface에는 `validate`, user-level `init`, `update`, `line init`만 있으며 `project` command가 없다. `PYTHONPATH=src proofline project --help`는 exit code 2와 `invalid choice: 'project'`를 반환했다.
- `src/proofline/cli.py:80-89`의 `proofline init`은 `initialize_home()`만 호출하여 `~/.proofline/`을 초기화한다. Project root를 쓰지 않는 이 책임은 `ac-0016`이 소유한다.
- `docs/contracts/storage-and-retention.md`는 project root의 `proofline.yaml`에 `schema_version: 1`과 `artifact_root: .proofline`을 필수로 선언하고, `docs/artifact-layout.md`는 project canonical root를 `.proofline/lines/`와 `.proofline/criteria/`로 정의한다.
- `src/proofline/validator.py:206-211`은 `.proofline/`이 directory가 아니면 artifact 검사를 오류 없이 건너뛴다. `tests/test_config_validation.py::test_valid_project_config_has_no_errors`도 `proofline.yaml`만 생성한 project를 valid로 고정한다.
- `src/proofline/line_writer.py:47-91`은 current working directory가 Git root이고 project validation이 통과하며 실제 `.proofline/lines/` directory가 존재해야 Line init을 허용한다. 따라서 config-only project는 validator를 통과해도 Line init precondition을 만족하지 못한다.
- `tests/test_line_init.py::make_project`는 test마다 `proofline.yaml`, `.proofline/lines/`, `.proofline/criteria/`를 수동 생성한 뒤 Git repository를 초기화한다. Project bootstrap 자체를 수행하는 production writer나 CLI E2E test는 없다.
- `tests/test_home_init.py`는 user-level harness init이 current project를 변경하지 않아야 한다고 검증한다. Project init도 반대 방향으로 `~/.proofline/`을 복사·수정하지 않는 별도 책임을 유지해야 한다.
- Repository package metadata는 `pyproject.toml`에서 `0.4.1`이지만 현재 shell의 installed command는 `proofline 0.2.1`을 보고했다. 이는 project-init 제품 계약과 분리하여 installed official wheel E2E evidence에서 exact candidate version으로 다시 검증해야 하는 release-specific 환경 신호다.
- Line 0014 scaffold dry-run은 `.proofline/lines/line-0014/line-0014.md`와 `dcy-0014.md` 두 path만 보고했고 실제 init 후 source validator가 PASS했다. 기존 Line bootstrap은 이미 초기화된 project에서는 정상 동작한다.

## Scope

- User-level harness init과 구분되는 `proofline project init [--dry-run]` command를 추가한다. Schema-v1 첫 interface는 current working directory가 정확한 Git repository root일 때만 동작하며 explicit path option과 parent-directory 자동 탐색은 제공하지 않는다.
- Fresh project root에 UTF-8 bytes `schema_version: 1\nartifact_root: .proofline\n`인 `proofline.yaml`과 zero-byte `.proofline/lines/.gitkeep`, `.proofline/criteria/.gitkeep`을 결정론적으로 생성한다. 두 `.gitkeep`은 empty directory를 Git clone 이후에도 보존하는 schema-owned marker이며 validator가 허용하는 project support file로 contract에 명시한다.
- `proofline.yaml`은 있지만 `.proofline/`, `.proofline/lines/` 또는 `.proofline/criteria/`가 없거나 directory가 아닌 project를 validation error로 전환한다.
- Dry-run과 실제 실행이 동일한 Git root 판정, rendering, schema validation, symlink, existing file·directory, permission 및 path conflict preflight를 공유하게 한다.
- Exact initialized state의 반복 실행만 successful no-op으로 허용한다. 일부 path만 존재하거나 expected bytes·file type과 다른 partial·mismatch state는 자동 보완·migration·overwrite하지 않고 conflict로 실패한다.
- Writer는 모든 required path를 사전에 검증하고 staging과 atomic commit 또는 검증 가능한 rollback 경계로 생성한다. 일반 실패에서는 project tree와 user home이 byte-for-byte 불변이어야 한다. Concurrent target appearance에서는 ProofLine invocation이 생성한 staging·partial state를 남기지 않고 경쟁 주체가 생성한 path를 수정·삭제하지 않으며, 외부 경쟁 mutation을 제외한 기존 project bytes와 user home을 보존해야 한다.
- 생성된 project에서 `proofline validate`와 `proofline line init line-0001 --title '<제목>'`을 순서대로 실행하는 source, exact installed wheel 및 checkout 밖 E2E test를 제공한다.
- Project init은 Git repository metadata를 읽어 project root boundary를 확인하지만 Git init, add, commit, branch 또는 remote mutation은 수행하지 않는다.
- Project scaffold는 installed package의 schema-owned resource를 source of truth로 사용한다. User-level `~/.proofline/`의 contracts, templates, skills와 agent context를 project `.proofline/`에 복제하지 않으며 home tree를 읽기 전용으로 유지하고 변경하지 않는다.
- User harness가 없거나 manifest mismatch여도 package-owned required resource가 온전하면 project init을 허용한다. Package required resource가 없거나 malformed이면 project와 home을 변경하지 않고 실패한다.
- AC admission은 독립적이고 장기 active 가치가 있는 project initialization 동작의 신규 AC 1개 `create`, project topology validation을 추가하는 `ac-0001` `update`, 기존 의미를 바꾸지 않는 Line init E2E 검증의 `ac-0004` `satisfy`로 확정한다. `retire` 대상은 없다.
- Package version, wheel filename, tag 또는 checksum은 release-specific IQC/DQC evidence로 기록하고 일반 project-init validator hard error로 만들지 않는다.

## Out of Scope

- 기존 `proofline init`의 user-level `~/.proofline/` 책임을 project init과 혼합하거나 `ac-0016`의 의미를 변경하는 작업
- Project initialization과 동시에 첫 Line, Discovery, REQ, AC, Micro-SPEC, IQC 또는 DQC를 자동 생성하는 작업
- Existing malformed project를 자동 migration, repair, merge 또는 overwrite하는 기능
- Explicit project path option, parent-directory 자동 탐색 또는 Git repository root 이외 directory 초기화
- Git repository 생성, file staging, commit, branch 생성, remote 설정 또는 push
- Issue #10의 산출물 template 전면 한국어화
- Installed `proofline 0.2.1`을 현재 source version으로 update하거나 release를 publish하는 작업

## Risks and Unknowns

### Risks

- 여러 path 생성 중 failure 또는 concurrent writer로 partial scaffold가 남지 않도록 staging과 atomic commit 또는 검증 가능한 rollback을 writer와 fault-injection test로 고정해야 한다.
- `.proofline`, `lines`, `criteria`, `.gitkeep` 또는 `proofline.yaml`의 symlink와 rename 경쟁은 repository 밖 write나 existing data 손상으로 이어질 수 있으므로 preflight와 commit 직전 path identity를 검증해야 한다.
- `.gitkeep`을 project support file로 허용하되 canonical lifecycle artifact로 해석하지 않도록 topology contract와 validator allowlist를 일치시켜야 한다.
- Config-only project를 valid로 허용한 historical 동작을 변경하므로 `ac-0001`의 PASS/FAIL 조건과 기존 fixture를 함께 갱신하고 compatibility impact를 regression test로 명시해야 한다.
- Installed executable metadata와 source checkout version이 다르면 잘못된 executable을 검증할 수 있으므로 wheel IQC는 checkout 밖 exact candidate command path와 version을 함께 기록해야 한다.
