# Restore updater operations resource support

## Problem

공식 `v0.6.1` archive-provenance installation에서 `proofline update`가 checksum-verified target wheel을 설치하기 전 home payload preflight에 실패한다. Wheel은 legacy non-terminal history migration 절차를 `proofline_home/operations/legacy-nonterminal-history-migration.md`로 포함하지만, 같은 release의 `home_writer`는 `contracts`, `templates`, `skills`만 managed root로 허용한다. 그 결과 지원되는 `0.6.0 → 0.6.1` updater 경로가 `unexpected resource path`로 중단되고 package와 existing `~/.proofline`은 이전 version에 남는다.

현재 source checkout도 같은 불일치를 유지한다. Packaged wheel parser는 wheel의 모든 `proofline_home/**` resource를 읽어 `operations`를 거부하는 반면 source fallback은 `_RESOURCE_GROUPS`에 `operations`가 없어 해당 procedure를 조용히 누락한다. 따라서 단순 allowlist 한 줄 변경이 아니라 managed group 정의, source/package payload parity, completeness, manifest, existing-home reconciliation과 transaction/rollback evidence를 함께 교정해야 한다.

이 작업은 open GitHub Issue [#22](https://github.com/genichin/proofline/issues/22)의 release-blocker를 해결하는 긴급 corrective Line이다.

## Scope

- `operations`를 unknown root 허용이 아닌 명시적 managed-resource group으로 정의하고 source package, installed wheel parser, manifest managed records, reported `~/.proofline/operations/` path와 completeness invariant를 일치시킨다.
- `docs/operations/*.md` 전체를 기존 contracts/templates/skills와 같은 managed group으로 소유한다. Source collection과 wheel build mapping은 directory-level group semantics를 공유하고, source fallback과 exact built wheel은 같은 relative paths와 bytes를 생성해야 한다. 향후 이 directory에 추가되는 Markdown operation도 같은 package/HOME surface에 포함되며 별도 single-file mapping을 만들지 않는다.
- Existing valid `0.6.0` home payload에서 corrective target payload로 `prepare → package install → home commit → verify → finalize`가 수렴하도록 유지하고 executable package version, manifest version, operation procedure bytes/hash가 같은 selected wheel target에 결속되도록 한다.
- Target payload preflight·package installation·home commit·post-verification failure에서 기존 tool과 exact old HOME을 보존하거나 rollback하는 기존 transaction 의미를 유지한다. Existing-home reconciliation도 old manifest에서 operations-bearing target으로만 안전하게 수렴해야 한다.
- Finalization cleanup 실패는 이미 committed된 coherent target package/HOME을 유지하면서 명시적 non-zero diagnostic을 반환하는 기존 의미를 보존하며 pre-update rollback으로 재정의하지 않는다.
- `operations` positive group, missing/empty/incomplete group, arbitrary unknown root, absolute/parent traversal, duplicate, symlink, malformed manifest, user-modified existing tree와 rollback/concurrency negatives를 focused test로 고정한다. Unknown·unsafe root는 계속 fail-closed여야 한다.
- Exact source payload와 fresh candidate wheel의 path/byte/manifest parity, isolated installed-wheel `payload_from_wheel()`와 home init/reconciliation, source/full regression을 검증한다. Fresh init의 operations-bearing topology·manifest·reported path와 no-op/failure semantics는 `ac-0016`의 독립 acceptance 책임으로 고정한다.
- Checksum-verified archive-provenance `0.6.0 → corrective release` integration은 isolated `HOME`, `UV_TOOL_DIR`, `UV_TOOL_BIN_DIR`에서 실제 executable/version, manifest/version, operation hash, rollback과 application project/Git no-mutation을 판정한다. Public old-to-new transaction은 immutable corrective Release publication에 대한 별도 사용자 승인 이후 read-back evidence로만 완료한다.
- User harness storage/retention, artifact-layout, `README.md`의 HOME topology, packaged `src/proofline_home/agent-context.md`, updater/release procedure와 package resource tests를 새 operations contract에 맞추고 source/wheel/installed-HOME에서 같은 operations path와 bytes를 검증한다.
- REQ criteria admission은 `ac-0012` `update`, `ac-0016` `update`, `ac-0010` `satisfy`, create/retire 없음으로 제한한다. Release identity와 wheel digest는 AC가 아니라 Micro-SPEC·IQC·DQC·publication evidence가 소유한다.
- Corrective candidate identity를 immutable `v0.6.1` 다음 stable patch `v0.6.2`로 고정하고 package version과 candidate artifact preparation을 이 Line에 포함한다. Tag push, GitHub Release 생성과 asset upload는 exact candidate의 IQC/DQC 이후 별도 사용자 approval 없이는 수행하지 않는다.

- Updater transaction architecture의 전면 재작성, Linux ownership/concurrency semantics 약화 또는 Windows existing-harness replacement 지원 확대
- Existing finalization-cleanup 의미의 rollback 재설계 또는 ancestor-safe descriptor traversal 같은 범용 filesystem hardening
- Legacy migration validator·artifact schema·migration lifecycle 의미 변경
- Automatic modification of application project `.proofline/`, dependency environment, lockfile 또는 Git state
- PyPI publication, additional hosted platform/version matrix, branch protection·repository rule 변경
- Issue #22 해결과 무관한 operation 문서 내용 개편
- Discovery/REQ 승인 전에 product source, tests, package version, tag 또는 Release 변경

## Risks and Unknowns

### Risks

- `operations`를 allowlist에만 추가하고 source collection 또는 wheel mapping을 동기화하지 않으면 반대 방향의 source/wheel parity defect가 남는다.
- Group completeness를 단순히 “operations 아래 파일 하나 이상”으로만 판정하면 source directory의 일부 operation이 누락된 wheel도 PASS할 수 있다. Source inventory와 wheel inventory의 exact path/byte parity를 completeness/test contract로 고정해야 한다.
- Existing `0.6.0` manifest에는 operations records가 없으므로 current payload 검증과 target payload staging을 혼동하면 정상 old HOME을 unexpected-entry 또는 incomplete 상태로 오판할 수 있다.
- Package install 후 home commit/verify 실패 시 operation directory가 부분적으로 남거나 old package rollback이 누락되면 package/HOME version coherence가 깨진다. 기존 transaction snapshot과 failure injection matrix를 operation-bearing payload로 확장해야 한다.
- Public integration test는 `v0.6.2`가 실제 게시되기 전에는 fixture/candidate evidence만 제공한다. Publication 전 local PASS를 public success로 표현해서는 안 된다.
- `docs/operations`에 internal-only 또는 민감한 procedure를 실수로 추가하면 user HOME payload와 public wheel surface도 자동 확장된다. 새 operation 문서 review는 이 publication/managed-resource 효과를 확인해야 한다.

### Assumptions

- GitHub Issue #22의 재현과 Acceptance Criteria는 이 Line의 urgent product authority로 사용하되 Discovery confirmation, REQ approval, Micro-SPEC approval, implementation/IQC/DQC와 publication authority는 기존 lifecycle대로 각각 분리한다.
- `v0.6.1`은 immutable public release이므로 overwrite할 수 없고 corrective candidate는 stable patch `v0.6.2`다. 이 identity는 package-version preparation을 승인하지만 tag·Release·asset publication authority는 부여하지 않는다.
- Linux archive-provenance existing-harness replacement가 public old-to-new mutation target이다. Existing Windows replacement는 현재 명시적 unsupported contract를 유지한다.
- Official Release publication 전에는 exact candidate wheel과 local fixture asset을 사용해 mutation/rollback을 검증하고, public URLs에 대한 성공 주장은 publication/read-back 이후에만 기록한다.
- `docs/operations/*.md`는 모두 user harness와 public wheel에 포함할 수 있는 managed procedure이며, single-file 예외 mapping 없이 source directory inventory 전체를 배포한다.
