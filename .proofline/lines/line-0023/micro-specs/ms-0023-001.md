# Operations-bearing user harness와 v0.6.2 corrective candidate

## Scope

### 담당 범위와 criteria 배정

- `ac-0012`를 독립 판정 책임으로 배정한다. `docs/operations/*.md` 전체를 required managed resource로 만들고 source payload, exact built wheel, installed HOME, existing-home reconciliation과 checksum-verified archive-provenance `0.6.0 → 0.6.2` candidate transaction이 동일한 operation relative path·bytes·manifest SHA-256과 selected wheel identity로 수렴하는지 판정한다.
- `ac-0016`을 독립 판정 책임으로 배정한다. Fresh `proofline init`이 operations-bearing managed HOME을 원자적으로 만들고 exact 재실행은 무변경이며, invalid payload·existing mismatch·concurrent target·fault failure에서 기존 HOME과 application project를 안전하게 보존하는지 판정한다.
- `ac-0010`을 의미 변경 없이 독립 판정 책임으로 배정한다. Exact candidate에 대해 repository-owned mandatory DQC policy의 동일 wheel 기반 Ubuntu full job과 Windows portable/focused job, exact run/job/artifact/provenance read-back, IQC coverage와 candidate 이후 source 불변을 요구한다.
- 세 criterion 결과는 `iqc-0023-001.md`의 `Criteria Results`에서 각각 독립적으로 기록한다. 이 Micro-SPEC의 criteria 집합은 approved `req-0023`의 `update`와 `satisfy` 합집합인 `[ac-0010, ac-0012, ac-0016]`과 정확히 일치한다.

### Operations inventory와 기술 경계

- Authoring 시점의 canonical inventory는 `docs/operations/legacy-nonterminal-history-migration.md`, `docs/operations/official-wheel-release.md`, `docs/operations/proofline-tool-environment.md` 세 파일이다. 구현은 특정 한 파일을 예외 mapping하지 않고 `docs/operations/*.md`의 전체 Markdown inventory를 source group 하나로 수집한다. 향후 같은 directory에 추가되는 Markdown도 동일한 public wheel/HOME surface가 된다.
- `src/proofline/home_writer.py`의 `_RESOURCE_GROUPS`, `_SOURCE_GROUPS`, source collection, wheel directory mapping, payload root allowlist, required-group completeness, manifest 생성, `payload_from_wheel()`, reported path와 reconciliation이 `operations`를 같은 단일 group으로 취급해야 한다. Source relative path `docs/operations/<name>.md`, wheel relative path `proofline_home/operations/<name>.md`, HOME relative path `operations/<name>.md`를 일대일로 결속한다.
- Source payload↔fresh wheel archive↔isolated installed `~/.proofline`의 operations inventory는 상대 경로 집합, 각 파일 bytes, manifest record path와 SHA-256이 모두 exact하게 같아야 한다. Missing·extra·byte drift 또는 manifest drift는 허용하지 않는다.
- Fresh init, exact second init, wheel parser와 existing-home reconciliation은 동일한 operations-bearing schema를 사용한다. Existing valid `0.6.0` HOME은 old manifest에 operations record가 없다는 이유로 invalid target처럼 오판하지 않고, verified target payload staging을 통해서만 operations-bearing candidate HOME으로 수렴한다.
- `src/proofline/updater.py`의 기존 순서 `target preflight → package install → HOME commit → post-verification → finalize`와 ownership/concurrency 경계를 보존한다. Executable package version, HOME manifest version, operations path/bytes/hash는 모두 하나의 selected exact wheel target에 결속한다.

### 제외 범위와 authority

- Windows existing-home replacement 지원 확대, updater transaction architecture 재작성, finalization cleanup을 old-state rollback으로 바꾸는 의미 변경, broad ancestor no-follow/descriptor traversal hardening은 범위 밖이다.

- Package와 candidate artifact identity만 stable patch `0.6.2`로 준비한다. 기존 `v0.6.1` tag·Release·wheel·`SHA256SUMS`는 불변이며, IQC/DQC 이후 별도 사용자 authority 전에는 tag 생성·push, GitHub Release 생성, asset upload, public read-back 또는 PyPI publication을 수행하지 않는다.
- Ubuntu 외 추가 full platform matrix, Windows broad full source suite, repository protection 변경과 Issue #22 해결에 필요하지 않은 optional hardening을 추가하지 않는다.

### 구현 순서

1. **RED — inventory와 package parity:** Current three-file operations inventory를 expected oracle로 고정하고 source payload가 operations를 누락하며 current wheel parser가 operations root를 거부하는 focused assertions를 먼저 실행한다. Directory mapping, exact relative paths/bytes/manifest SHA-256, reported `~/.proofline/operations/`와 source↔wheel↔installed HOME equality를 요구한다.
2. **RED — fresh init과 reconciliation:** Fresh HOME init topology, exact second-run snapshot equality와 valid `0.6.0` existing HOME→operations-bearing target reconciliation을 추가한다. Missing·empty·incomplete operations group, missing individual operation, extra/unknown root, unsafe absolute/parent path, duplicate archive entry, symlink, malformed manifest, modified/unknown existing tree를 각각 valid baseline에서 한 축씩 변조해 typed nonzero failure와 no partial state를 요구한다.
3. **RED — transaction matrix:** Archive provenance와 checksum을 실제로 검증한 `0.6.0 → 0.6.2 candidate` fixture에서 prepare, package install, HOME commit, post-verification, finalize 순서를 고정한다. Target preflight·install·commit·postverify fault, rollback fault, concurrent target과 finalization cleanup fault를 각각 주입하고 package/HOME coherence, old/target 상태, residue와 stable diagnostic을 검사한다.
4. **Minimal GREEN — managed group:** `_RESOURCE_GROUPS`/`_SOURCE_GROUPS`, source collector, wheel directory mapping, allowlist/completeness, manifest/reporting을 같은 `operations` inventory에 연결한다. Single-file special case나 arbitrary unknown-root fallback을 만들지 않는다.
5. **Minimal GREEN — init/update:** Existing home writer와 updater transaction primitives를 재사용해 fresh init과 reconciliation이 operations-bearing payload를 처리하게 한다. Current rollback·ownership·concurrency/finalization semantics를 약화하거나 새 transaction framework로 교체하지 않는다.
6. **Docs/package/version parity:** README, storage/artifact contracts, packaged agent context, release procedure, package/lock/installer identity를 `0.6.2` candidate와 operations-bearing schema로 동기화한다. Official release 문서는 exact candidate wheel 1회 build·검증과 publication approval 이후 절차를 구분한다.
7. **Command-level no-mutation containment:** 모든 local/hosted source command는 command마다 repository 밖 absolute `UV_PROJECT_ENVIRONMENT`, `UV_CACHE_DIR`, pytest basetemp와 `TMPDIR`/`TEMP`/`TMP` temporary root를 전달하고 `PYTHONDONTWRITEBYTECODE=1`을 설정한다. 모든 pytest invocation은 explicit `--basetemp <external-absolute-path> -p no:cacheprovider`를 사용하며 compileall invocation은 repository 밖 absolute `PYTHONPYCACHEPREFIX`를 추가한다. Build, source validation, import/provenance, registry/package helper와 Ubuntu/Windows command도 예외가 아니다. Command 전후 tracked+ignored inventory snapshot으로 repository `.venv`, `.pytest_cache`, `__pycache__`, `*.pyc`가 없음을 검사한다.
8. **Focused GREEN 후 full source regression:** 변경 영역 focused tests를 먼저 통과시킨 뒤 source-backed canonical validation, 전체 source test와 compile check를 위 command-level containment 아래 실행한다. Exact changed-path manifest가 위 inventory와 approved Issue #22 범위를 벗어나면 commit하지 않는다.
9. **Exact wheel 1회와 installed-wheel E2E:** Exact implementation candidate에서 fresh wheel을 한 번만 build하고 strict `SHA256SUMS`와 digest를 고정한다. Checkout 밖 isolated environment에 그 exact wheel을 non-editable install하고 application project cwd에서 `init --dry-run → init → exact init rerun → initialized update --check → validate`를 실행한다. Source/wheel/HOME operations path·bytes·manifest와 CLI/distribution version `0.6.2`를 대조하고 sequence 전후 project `.proofline`, dependency/lock files, `.venv`와 Git state가 의도하지 않게 변하지 않았음을 확인한다.
10. **Candidate gates와 single-wheel closure:** Candidate mode를 explicit `PROOFLINE_HOSTED_CANDIDATE_MODE=1`로 켜고, build job이 만든 동일 wheel의 absolute path `PROOFLINE_HOSTED_CANDIDATE_WHEEL`, lowercase expected SHA-256 `PROOFLINE_HOSTED_CANDIDATE_WHEEL_SHA256`, 그 wheel을 설치한 absolute `PROOFLINE_INSTALLED_EXECUTABLE`을 build-only, focused/full, source-installed parity, registry/package, Ubuntu와 Windows의 모든 capable test/helper에 전파한다. 각 consumer는 사용 전에 wheel bytes를 expected digest와 대조하고 executable의 installed provenance를 그 wheel에 결속한다. Candidate mode에서 세 값이 없거나 상대 path·digest mismatch·provenance mismatch이면 fail-closed하고, 위 inventory의 unconditional builder와 fallback fixture는 rebuild나 synthetic wheel 생성을 하지 않는다. `tests/test_candidate_verification_ci.py`가 workflow 전체의 `uv build --wheel` cardinality 1과 모든 consumer의 세 control 전달을 고정한다. Candidate wheel digest, exact candidate SHA, hosted run/job/artifact IDs는 implementation precommit test에 예상값으로 삽입하지 않고 IQC/DQC의 실제 evidence로 기록한다.

### Rollback과 containment

- 일반 preflight 또는 init failure에서는 HOME·package·application project의 before/after snapshot이 같고 ProofLine-owned staging·partial state가 없어야 한다. Existing HOME modified/unknown/symlink/manifest mismatch는 mutation 전에 거부한다.
- Package install 전 failure는 exact old package/HOME을 유지한다. Package install 뒤 HOME commit 또는 post-verification failure는 verified previous package와 exact old HOME을 복원하거나 이미 검증된 target으로 일관되게 끝내며 mixed version/manifest/operations state를 허용하지 않는다. Rollback 자체 실패는 stable nonzero diagnostic과 관찰된 coherent-state 판정을 남기고 실패를 성공으로 승격하지 않는다.
- Finalization cleanup만 실패하면 committed·post-verified target package/HOME과 operation bytes를 유지하고 old state로 되돌리지 않으며 nonzero finalization diagnostic과 invocation-owned residue 정보를 반환한다.
- Concurrent target fixture는 actor-owned target의 entry set·metadata·bytes를 보존하고 actor-owned delta를 제외한 HOME/project snapshot equality와 invocation-owned staging/partial residue 부재를 요구한다. Broad ancestor race/syscall-interposition hardening은 추가하지 않는다.

- 검사: `tests/test_home_init.py tests/test_home_update.py tests/test_updater_transaction.py tests/test_updater.py tests/test_cli_update.py tests/test_wheel_package.py`의 operations-focused cases를 RED로 먼저 실행하고 최소 구현 뒤 같은 node set을 GREEN으로 실행한다.

### Source, exact wheel과 isolated installed E2E

- 검사: 각 local/hosted command에 repository 밖 absolute `UV_PROJECT_ENVIRONMENT`, `UV_CACHE_DIR`, `TMPDIR`/`TEMP`/`TMP`와 `PYTHONDONTWRITEBYTECODE=1`을 command-level로 설정한다. 모든 pytest command는 `--basetemp <external-absolute-path> -p no:cacheprovider`를 explicit하게 포함하고, `python -m compileall -q src tests`는 추가로 repository 밖 absolute `PYTHONPYCACHEPREFIX`를 설정한다. 이 contract 아래 source-backed `proofline validate`, focused tests, 전체 source pytest와 compile check를 순서대로 실행하고 exact implementation candidate wheel을 unique external dist에 한 번만 build해 strict checksum, archive inventory, source↔wheel byte parity를 검사한다.
- 검사: 최초 build 직전과 모든 local/hosted source command가 끝난 뒤 `git status --short --untracked-files=all`과 `git status --short --ignored --untracked-files=all` 및 filesystem inventory를 비교해 tracked/ignored delta와 repository `.venv`, `.pytest_cache`, `__pycache__`, `*.pyc`가 모두 없음을 판정한다. `tests/test_candidate_verification_ci.py`는 build-candidate, Ubuntu와 Windows command 각각에 external absolute environment/cache/temp/basetemp, `PYTHONDONTWRITEBYTECODE=1`, pytest `-p no:cacheprovider`, compileall의 external `PYTHONPYCACHEPREFIX`가 빠지면 실패한다.
- 검사: 동일 exact wheel을 isolated environment에 설치해 `payload_from_wheel()` 및 application project cwd의 `init --dry-run → init → init rerun → update --check → validate`를 실행하고 HOME topology/manifest/version/operation digest와 application project·Git no-mutation snapshot을 확인한다. Valid `0.6.0` archive/package/HOME fixture에서 같은 candidate wheel을 사용한 full updater transaction과 failure matrix도 실행한다.
- 기대 결과: Source와 isolated installed wheel은 같은 operations inventory와 success/failure 판정을 내리고 candidate package/CLI/manifest는 `0.6.2`로 일치한다. Candidate mode의 모든 wheel-capable test/helper는 absolute `PROOFLINE_HOSTED_CANDIDATE_WHEEL`, `PROOFLINE_HOSTED_CANDIDATE_WHEEL_SHA256`, `PROOFLINE_INSTALLED_EXECUTABLE`을 요구하고 wheel digest와 executable provenance를 확인하며, 값 누락·mismatch 시 rebuild/fallback 없이 실패한다. Source-only developer build는 candidate mode 밖에서만 실행된다. Local candidate evidence를 public `v0.6.2` publication 성공으로 표현하지 않는다.
