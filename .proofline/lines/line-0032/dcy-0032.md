# Guided Worktree Creation

## Problem

ProofLine의 current simplified topology는 approved specification 이후 구현 작업 공간을 분리하는 workflow를 제공하지 않는다. 구현 에이전트가 main working tree에서 직접 source와 test를 변경하면 main이 dirty해져, 같은 repository에서 lead가 다음 기능의 Line/Discovery를 생성하고 evidence를 조사하기 어렵다. 구현을 linked worktree로 분리하도록 안내하여 main을 다음 governance 작업에 계속 사용할 수 있게 하되, 아직 충분히 사용해 보지 않은 worktree workflow를 CLI나 validator hard gate로 강제하면 과거 implementation lifecycle의 복잡성을 다시 도입할 수 있다.

## Evidence

- 사용자는 worktree handoff를 다시 채용하려는 목적이 구현 에이전트가 worktree에서 구현하는 동안 새로운 Line/Discovery 작업을 진행할 수 있게 하는 것이라고 명시했다.
- 사용자는 이번 범위를 worktree 생성으로만 제한하고, 현재는 ProofLine이 배포하는 skill에서만 제공하며 강한 강제보다 사용을 유도하는 형태로 운영한 뒤 실제 문제가 발생하면 공식 CLI 확장을 검토하기로 결정했다.
- GitHub Issue [#26](https://github.com/genichin/proofline/issues/26)은 approved specification에서 linked worktree를 만드는 방안을 제안하지만 CLI transaction, retry와 cleanup까지 포함한 초기 제안은 이번 결정에 따라 후속 검토 범위로 축소된다.
- `.proofline/lines/line-0026/req-0026.md`는 implementation history validator, Micro-SPEC·IQC·DQC·integration artifact와 관련 workflow를 current canonical 범위에서 제거하고 `ac-0007`, `ac-0021`, `ac-0022`를 retire했다.
- Retired `ac-0007`은 과거 exact-H worktree handoff를 Line execution status와 implementation chronology에 결합했으므로 current id-only Line topology에서 재활성화하기에 과도하다.
- Active `ac-0008`은 main과 모든 Line worktree가 application dependency·lockfile·`.venv`를 변경하지 않고 공용 ProofLine tool environment를 사용하도록 요구한다.
- Root `.gitignore`는 `/.worktrees/`를 제외하므로 이 repository 안의 guided worktree path가 main의 untracked 상태를 만들지 않는다.
- Current `skills/proofline-approve-specification/SKILL.md`는 승인 상태 전환과 validation 결과 보고에서 종료하며, 승인 뒤 worktree 생성을 optional next action으로 안내하거나 구현 agent 선택을 다루지 않는다.
- 과거 `skills/proofline-approve-specification/scripts/audit_transition.py` helper는 제거됐고 `tests/test_approve_specification_skill.py`가 그 제거를 고정하므로, 새 helper는 approval transition·chronology를 재판정하거나 기록하지 않아야 한다.
- Current ProofLine CLI에는 worktree command가 없고 `src/`에도 worktree·handoff 구현이 없다.

## Scope

- ProofLine source의 `skills/proofline-*` 아래에서 version control되고 official wheel의 `proofline_home/skills/`와 managed `~/.proofline/skills/`로 배포되는 implementation handoff skill을 제공한다.
- `proofline-approve-specification` skill은 사용자 승인에 따른 REQ `approved`와 대상 AC의 계약상 상태 전환 및 canonical validation이 완료된 뒤에만 worktree 생성을 optional next action으로 제시한다. Approval workflow가 worktree를 자동 생성하거나 사용을 승인 조건으로 만들지 않는다.
- 사용자가 optional next action을 선택하면 implementation handoff skill은 main을 직접 수정하지 않고 linked worktree를 사용하는 권장 workflow를 설명한다.
- Worktree skill은 supporting script `scripts/inspect_worktree_readiness.py`를 제공한다. Helper는 current canonical validation, confirmed Discovery, approved REQ·대상 AC 상태, current branch·HEAD, main cleanliness, deterministic branch·path availability, existing worktree registration과 `.worktrees/` ignore 상태를 read-only로 관찰한다.
- Helper는 `advisory: true`, `recommendation: create|review`, observations와 reasons를 machine-readable하게 반환한다. `create`와 `review`는 모두 정상 inspection exit `0`이며, non-zero는 invalid invocation, unreadable repository 또는 inspection 자체 실패에만 사용한다.
- Helper는 worktree 생성 허가·승인 authority가 아니며 artifact status, Git ref, worktree, filesystem과 canonical state를 변경하지 않는다. Helper 결과는 validator·QC·CI gate나 persistent handoff record로 사용하지 않는다.
- Skill은 helper 결과를 사용자·agent의 생성 결정 자료로 제시한다. `review`는 생성 금지 판정이 아니며 자동 override·repair·cleanup을 유발하지 않는다.
- 생성이 선택되면 Skill은 deterministic branch와 repository-relative `.worktrees/line-NNNN` path를 사용해 표준 Git worktree creation command를 실행하고 `--force`, 자동 suffix, existing branch reset과 path 삭제를 사용하지 않는다.
- Skill은 생성된 worktree path, attached branch와 시작 commit을 read-back한 뒤 구현 작업 주체를 강제하지 않고 두 선택을 제시한다. 현재 agent가 working directory를 생성된 worktree로 전환해 계속하거나, 다른 agent·subagent에게 exact path·branch·starting commit과 approved REQ·AC 범위를 전달해 구현을 진행할 수 있다.
- 다른 agent·subagent에게 인계할 때는 main이 아니라 생성된 worktree만 implementation working directory로 사용하고 approved specification 의미를 변경하지 않는다는 경계를 handoff context에 포함한다.
- Handoff 뒤 main에서는 lead 또는 현재 governance agent가 별도 신규 `proofline line init`, Discovery evidence 조사와 specification 작업을 계속할 수 있음을 명시한다.
- Agent 선택과 delegation은 현재 session의 orchestration 결정이며 canonical artifact, ProofLine CLI 또는 validator state로 기록하거나 강제하지 않는다.
- Skill은 worktree 사용을 권장하고 생성 절차를 제공하지만, ProofLine CLI나 validator가 main 직접 구현을 거부하거나 worktree 사용을 필수 lifecycle gate로 만들지 않는다.
- Skill은 Git worktree creation 한 번만 소유하며 구현 진행·완료, retry·repair, cleanup, merge와 integration을 관리하지 않는다.
- Skill source와 official wheel·initialized HOME의 managed copy가 같은 path와 bytes를 제공하는지 기존 package resource parity 방식으로 검증한다.
- Temporary Git fixture는 skill이 제시하는 기본 command sequence로 linked worktree가 지정된 branch와 commit에서 생성되고 main에서 별도 Line/Discovery 작업을 시작할 수 있는지 확인한다. 복잡한 failure injection·rollback matrix는 요구하지 않는다.
- AC admission은 version-independent guided worktree creation을 소유하는 신규 AC 하나의 `create`와 공용 tool environment를 의미 변경 없이 유지하는 `ac-0008`의 `satisfy` 후보로 분류한다. Retired `ac-0007`, `ac-0021`, `ac-0022`는 재활성화하지 않는다.

## Out of Scope

- 공식 `proofline worktree` CLI 또는 별도 executable 구현
- Worktree 사용을 validator·QC·CI의 필수 gate로 적용
- Helper 결과를 worktree 생성 permission, approval authority, PASS/FAIL gate 또는 canonical lifecycle 상태로 해석
- Helper가 artifact status, Git ref·registration, branch·path 또는 filesystem을 변경하는 기능
- Main에서 직접 구현하는 작업의 금지 또는 invalid 판정
- Canonical handoff artifact, Line execution status 또는 `implementation_history` field 도입
- Automatic retry, partial-state repair, rollback transaction과 alternate branch·path 생성
- Worktree·branch cleanup, resume, rebase, merge와 integration 자동화
- Current agent 또는 다른 agent·subagent 중 하나를 자동 선택하거나 agent process를 ProofLine CLI·validator가 생성·관리하는 기능
- Agent identity, delegation 상태와 session 진행 상황을 canonical artifact에 기록하는 기능
- Implementation commit history, 완료, 검증, delivery 또는 release 품질 인증
- Micro-SPEC, IQC·DQC와 integration manifest 복원
- 기존 canonical artifact와 Git history의 소급 변환·재작성
- Retired AC의 직접 재활성화
- 실제 사용에서 확인되지 않은 adversarial concurrency·filesystem threat hardening

## Risks and Unknowns

### Risks

- Skill은 권장 workflow이므로 에이전트나 사용자가 main에서 직접 구현하는 것을 기술적으로 차단하지 않는다.
- Helper가 지나치게 많은 lifecycle 의미를 재구현하면 제거된 approval audit helper와 같은 secondary validator가 될 수 있으므로 관찰 필드와 recommendation vocabulary를 제한해야 한다.
- Helper의 `review`가 shell failure나 CI failure로 취급되면 사실상 gate가 되므로 정상 inspection exit-code 계약을 검증해야 한다.
- Git worktree creation 중 충돌이나 부분 실패가 발생하면 이번 범위에는 자동 repair·rollback이 없으므로 사용자가 현재 Git 상태를 확인해야 할 수 있다.
- Deterministic branch 또는 path가 이미 존재하는 경우 skill은 자동 suffix·reset·삭제 없이 중단하고 충돌을 보고해야 한다.
- 다른 agent·subagent에게 인계할 때 exact worktree path, starting commit과 approved scope가 누락되면 main 또는 잘못된 baseline에서 구현할 수 있으므로 handoff context의 최소 항목을 명시해야 한다.
- 실제 사용에서 반복되는 충돌, partial state 또는 platform 차이가 확인되면 그 evidence를 근거로 별도 Discovery에서 공식 CLI와 필요한 transaction 경계를 검토해야 한다.
