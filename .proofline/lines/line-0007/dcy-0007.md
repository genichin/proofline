# 공식 ProofLine wheel release

## Problem

ProofLine은 `pyproject.toml`에 build backend, package version과 console script를 정의하고 wheel resource 검증도 보유하지만 사용자가 내려받을 수 있는 공식 release가 없다. 현재 공용 `uv tool` 설치는 사용자가 선택한 local source checkout을 요구하므로 source repository가 없는 환경에서 immutable version을 설치하거나 배포 artifact의 provenance와 checksum을 확인할 수 없다.

## Evidence

- Exact baseline `b7e1bc4e8d9efdaff63341d6f6d4b57a1a2eadc1`의 `pyproject.toml`은 package name `proofline`, version `0.1.0`, Python `>=3.11`, Hatchling wheel build와 console script `proofline = proofline.cli:main`을 선언한다.
- 같은 baseline의 wheel 설정은 `src/proofline`과 `templates/schema-v1` package data를 포함하며 `tests/test_wheel_package.py`가 built wheel의 template resource와 installed `_read_template()` 동작을 검사한다.
- Main과 `origin/main`은 baseline에서 일치하고 working tree는 clean이며 `proofline validate`와 전체 pytest `73 passed`가 통과했다.
- `git tag --list`와 `gh release list` 결과는 모두 0건이다. 공개 저장소 `https://github.com/genichin/proofline`에는 공식 Git tag와 GitHub Release가 없다.
- `gh auth status`는 release publication에 필요한 현재 GitHub 인증이 유효함을 확인했다. Credential 값은 기록하지 않는다.
- `docs/operations/proofline-tool-environment.md`는 공식 release channel이 없는 동안 clean source checkout의 non-editable `uv tool install`만 허용하고, release source·update·rollback을 별도 결정으로 남긴다.
- 현재 user-level tool은 `~/.local/share/uv/tools/proofline/`의 non-editable package `proofline 0.1.0`이며 source checkout 밖에서 console script가 실행된다.
- 저장소는 public이지만 repository license metadata와 root `LICENSE`, release workflow를 갖고 있지 않다. 이번 release는 license를 추정하거나 hosted CI 정책을 새로 만들지 않아야 한다.

## Scope

- ProofLine 최초 공식 package version을 현재 manifest version과 일치하는 `0.1.0`으로 고정하고 Git tag와 GitHub Release 이름을 `v0.1.0`으로 사용한다.
- Final delivered main commit을 exact release source로 사용하고 annotated tag `v0.1.0`이 그 commit만 가리키게 한다.
- Clean exact source에서 `uv build --wheel`로 `proofline-0.1.0-py3-none-any.whl`을 생성한다.
- Release asset은 wheel과 그 exact SHA-256을 담은 `SHA256SUMS`로 한정한다.
- Wheel을 source checkout 밖의 fresh isolated environment에 non-editable로 설치하여 다음을 검증한다.
  - Distribution metadata name·version과 module provenance가 installed environment의 `site-packages`를 가리킴
  - Console script help와 representative `proofline validate` 성공·실패 동작
  - Repository template와 installed package resource의 byte parity
  - Application project의 dependency metadata, `.venv`와 canonical artifact를 설치 과정이 변경하지 않음
- GitHub Release notes에 release version, exact source commit, Python requirement, wheel filename과 SHA-256을 기록한다.
- Publication 직전에 local/remote main exact synchronization, tag·release·asset 이름 충돌, GitHub 권한과 final artifact checksum을 preflight한다.
- Tag와 Release가 이미 존재하면 exact commit·metadata·asset checksum이 모두 일치할 때만 verified existing state로 재사용하고, 하나라도 충돌하면 force-update나 overwrite 없이 중단한다.
- Tag push 후 Release 또는 asset upload가 실패하면 원격 tag를 자동 삭제하지 않는다. 재실행은 exact identity를 검증한 뒤 누락 단계만 완료한다.
- Publication 후 GitHub에서 wheel과 `SHA256SUMS`를 다시 내려받아 asset checksum, wheel metadata와 isolated installation을 재검증한다.
- 기존 clean source checkout 설치 경로와 user-level `uv tool` environment는 유지하며 현재 installation을 자동 변경하지 않는다.

## Out of Scope

- PyPI publication 또는 package namespace claim
- `curl ... | bash` installer
- `proofline update`, 자동 update, rollback command 또는 version pinning UI
- Source distribution(`sdist`), container image, standalone executable 또는 OS package
- GitHub Actions, hosted CI, Python version matrix, branch protection 또는 required remote status check
- Artifact signing, Sigstore, SBOM 또는 별도 transparency log
- Repository license 선택·추정 또는 기존 source의 license 정책 변경
- `proofline.yaml` schema나 canonical artifact migration
- 기존 user-level ProofLine installation의 삭제·덮어쓰기·upgrade
- Release publication을 application deployment나 governance artifact delivery로 표현하는 것

## Risks and Unknowns

### Risks

- Repository에 명시적인 package license가 없어 공개 wheel 사용자가 재배포·수정 권한을 판단할 수 없다. 이번 Line은 license를 임의 선언하지 않고 현재 상태를 Release notes에 숨기지 않으며, license 결정은 별도 사용자 결정으로 남긴다.
- GitHub Release와 tag는 repository 관리자에 의해 삭제될 수 있어 cryptographic immutability를 제공하지 않는다. Exact source commit과 SHA-256 read-back evidence로 이번 최소 release의 identity를 고정한다.
- Local build가 통과해도 upload 중 asset이 바뀌거나 잘못된 파일이 연결될 수 있다. Publication 후 remote download bytes와 metadata를 독립적으로 재검증해야 한다.
- Tag push 이후 Release 생성 실패는 로컬 rollback으로 해결할 수 없다. Existing remote object를 삭제하거나 force-update하지 않고 exact identity 기반 retry만 허용해야 한다.

### Assumptions

- 사용자의 “공식 wheel release” 지시는 공개 GitHub repository의 첫 stable GitHub Release `v0.1.0`을 만들 권한을 포함한다.
- PyPI, installer와 `proofline update`는 공식 wheel release가 존재한 뒤 각각 별도 Line에서 다룬다.
- Package version `0.1.0`은 아직 tag·release로 사용되지 않았으므로 최초 official release identity로 사용할 수 있다.
