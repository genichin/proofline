# Implementation lifecycle history validation

## Problem

ProofLine은 Micro-SPEC의 implementation lifecycle을 `not_started → in_progress → implemented`로 정의하지만, 현재 validator는 working tree의 `implementation_status` vocabulary와 artifact 관계만 검사하고 persisted Git history에서 허용된 transition이 실제로 존재하는지는 검사하지 않는다. 그 결과 구현 착수 기록 없이 `not_started`에서 `implemented`로 직접 바뀐 Micro-SPEC과 그 IQC가 canonical validation을 통과할 수 있고, exact implementation binding과 작업 chronology의 진위를 independent reviewer가 수동으로 재구성해야 한다.

기대 상태는 IQC admission에 영향을 주는 implementation lifecycle history를 validator가 read-only로 검사하여, 적용 대상 Micro-SPEC의 필수 intermediate transition과 IQC commit ancestry가 없거나 모순되면 stable diagnostic으로 fail-closed하는 것이다.

## Evidence

- `docs/contracts/micro-spec-and-iqc.md`는 implementation transition을 `not_started → in_progress → implemented`와 재작업의 `implemented → in_progress → implemented`로 제한하고, IQC가 exact Micro-SPEC commit과 실제 검증한 implementation commit을 함께 bind하도록 요구한다.
- `src/proofline/validator.py`의 현재 구현은 `implementation_status`의 허용 값과 IQC frontmatter field를 선언하지만, Micro-SPEC의 과거 tree bytes나 transition commit ancestry를 검사하는 implementation-history rule은 없다.
- Line 0017에서는 실제 구현 commit `e4be646f737e903dec67982d934b814e3391b7f5`부터 최종 IQC-bound implementation `531432f9b8f5d367c3c2c2f2033eda9797029110`까지 세 Micro-SPEC이 `not_started`로 남아 있었다. 직접 `implemented`로 바꾼 IQC candidate가 canonical validation을 통과한 뒤 independent IQC review에서 위반이 발견되어, IQC를 분리하고 `in_progress` commit `80c64ae208c630e0ffbf0536187d5757619a7282`을 먼저 영속화한 후 IQC commit `c818496c67c509ade9126ed804c9c6951492e6b2`으로 복원해야 했다.
- 2026-08-04의 canonical main `05e59af53f8bdf65b97b4f6ac0e5994950181ac1` 전수 조사에서 현재 `implemented`인 Micro-SPEC 35개 중 18개(Line 0011~0016)가 persisted `in_progress` 상태 없이 `not_started → implemented`로 기록되어 있다. 모든 historical artifact에 새 strict rule을 즉시 소급하면 현재 delivered main이 invalid해진다.
- `src/proofline/identity_ledger.py`와 관련 Real-Git tests는 ProofLine validator가 Git tree와 first-parent history를 fail-closed·read-only로 검사할 수 있다는 기존 구현 선례를 제공하지만, Micro-SPEC lifecycle history를 대신 검증하지는 않는다.
- GitHub Issue #14 `IQC admission에서 persisted implementation lifecycle history를 검증한다`가 재현 이력, 최소 불변조건과 positive/negative acceptance matrix를 추적한다.

## Scope

- `create`: topology·direct-reference 검증과 독립적으로 장기 유지되는 implementation lifecycle history acceptance criterion을 새로 정의한다.
- Prospective enforcement를 사용한다. 명시적이고 감사 가능한 adoption baseline 이전에 이미 delivered된 history는 legacy로 보존하고, baseline 이후 implementation transition부터 strict history validation을 적용한다. Baseline 이후 위반을 legacy로 분류하거나 warning-only migration window를 두지 않는다.
- 적용 대상으로 결정된 Micro-SPEC에 대해 persisted `in_progress` transition, 후속 implementation commit과 `implemented`/IQC 상태의 순서 및 ancestry를 history-aware하게 검증한다.
- `implementation_commit`은 승인된 specification과 persisted `in_progress` transition 모두의 descendant여야 한다. Lifecycle chronology는 exact implementation/IQC candidate의 first-parent chain만 canonical path로 인정하며, 다른 parent에서만 reachable한 transition은 predecessor로 인정하지 않는다. `not_started → implemented`, `in_progress`와 `implemented`의 same-commit 기록, 필수 predecessor보다 앞서거나 lifecycle-only transition에 잘못 bind된 IQC implementation commit을 fail-closed하는 판정 경계를 정의한다.
- 여러 Micro-SPEC 중 위반 artifact ID, 누락 또는 모순된 transition과 관련 commit boundary를 식별하는 stable diagnostic을 제공한다.
- Git history가 없거나 필요한 commit·tree를 해석할 수 없는 환경의 fail-closed 동작과 source CLI·isolated installed-wheel CLI parity를 검증한다.
- Validation 전후 canonical bytes, index, worktree, symbolic HEAD와 refs가 동일한 read-only 성질을 Real-Git fixture로 검증한다.
- 기존 Micro-SPEC/IQC contract, validator, package assets, user harness 및 implementation-start/IQC 절차를 같은 결정과 일치시키되 자동 mutation 기능은 도입하지 않는다.

## Out of Scope

- Historical Git commit 또는 delivered Line artifact를 다시 쓰거나 과거 작업 chronology를 사후 생성하는 기능
- Validator가 status 변경이나 Git commit을 자동 생성하는 기능
- 모든 Micro-SPEC을 동시에 `in_progress`로 전환하도록 강제하는 정책
- Discovery, REQ, AC, DQC 또는 Line delivery 전체 lifecycle을 한 번에 history-aware하게 재설계하는 작업
- Implementation 내용의 품질 또는 승인 범위 충족 여부를 Git path 종류만으로 추론하는 기능
- Line 0017 구현·IQC·DQC를 재개하거나 변경하는 작업
- Windows controlled verification, release, tag, publication 또는 public asset read-back

## Risks and Unknowns

### Risks

- Prospective baseline은 legacy delivered history를 보존하지만, baseline identity가 모호하거나 변경 가능하면 새 위반까지 exemption할 수 있다. REQ는 baseline을 stable하고 검증 가능한 canonical 사실로 만들고 baseline 이후 strict 적용을 우회할 수 없게 해야 한다.
- Merge topology에서는 exact implementation/IQC candidate의 first-parent chain만 canonical chronology로 인정한다. 다른 parent에서만 reachable한 `in_progress` transition은 현재 candidate의 predecessor가 아니며, merge parent ordering이 canonical chain을 바꾸면 판정도 달라진다.
- `implementation_commit`이 실제 구현을 담았는지는 일반적인 path allowlist만으로 완전하게 증명할 수 없다. History validator는 검증 가능한 transition·ancestry 조건과 reviewer가 소유하는 semantic implementation 판정을 혼동하지 않아야 한다.
- Shallow clone, missing object와 Git command failure를 valid history로 오인하면 fail-open이 된다. 반대로 모든 제한 환경을 malformed history와 같은 진단으로 표현하면 복구 가능성이 낮아진다.
- Repository 규모에 비례한 commit-by-commit 검사로 일반 `proofline validate` 성능이 과도하게 저하될 수 있다.
