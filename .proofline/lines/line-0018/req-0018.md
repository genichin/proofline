# Implementation lifecycle history validation

## Objective

ProofLine project가 Line별 first-parent adoption baseline을 명시하면 `proofline validate`가 그 baseline 이후 Micro-SPEC implementation cycle과 IQC exact binding의 persisted chronology를 fail-closed·read-only로 검증하여, `not_started → implemented` 직접 전이와 side-branch 또는 lifecycle-only commit을 이용한 잘못된 binding을 IQC admission 전에 차단하게 한다.

## Scope

- Line artifact에 `implementation_history: first_parent` policy field를 도입한다. 이 field가 해당 Line의 first-parent history에 처음 persisted된 commit `B`가 그 Line의 adoption baseline이며, 한 번 도입한 field의 제거·변경이나 first-parent history로 입증할 수 없는 baseline은 오류다.
- Repository first-parent history에서 어떤 Line이든 policy field를 처음 persisted한 commit `A`를 fieldless-legacy activation cutoff로 사용한다. 별도 global artifact나 Line ID allowlist를 만들지 않으며 `A`는 canonical Line field history에서만 파생한다.
- `proofline line init`과 schema-v1 Line template은 새 Line에 policy field를 기본 기록한다. Existing non-terminal Line은 implementation 완료/IQC admission 전에 field를 명시적으로 추가하여 adoption하며, validator가 자동으로 artifact나 commit을 생성하지 않는다.
- `A`가 아직 없는 pre-adoption repository의 fieldless terminal Line과 terminal transition commit `T`(`delivered` 또는 `cancelled`)가 `A`의 strict first-parent ancestor인 fieldless Line만 legacy로 보존한다. `T = A`, `T`가 `A` 이후이거나 first-parent ordering을 입증할 수 없는 fieldless terminal 전이, fieldless non-terminal Line, field 제거 이력에는 legacy exemption이나 warning-only migration을 적용하지 않는다.
- Strict 대상의 각 최초 implementation cycle은 approved `micro_spec_commit`보다 뒤의 별도 persisted `in_progress` commit `P`와 그보다 뒤의 exact `implementation_commit` `I`, 후속 `implemented`/IQC candidate `Q`를 가져야 한다. Line adoption baseline `B`는 `I`보다 먼저 persisted되어야 한다. 즉 `micro_spec_commit < P < I < Q`와 `B < I < Q`를 모두 요구하되, policy 지원 전에 올바르게 시작한 existing non-terminal Line의 `P < B < I < Q`와 policy 도입 후 시작한 새 Line의 `B < P < I < Q`를 모두 인정한다.
- `I < B`, `P = I`, `I = Q`, `P`가 approved specification보다 앞선 ordering은 실패한다. Baseline을 가로지르는 cycle을 legacy로 면제하지 않으며, baseline 이전 `P`도 exact candidate first-parent chain의 유효 predecessor로 검사한다.
- Rework cycle은 이전 `implemented` 상태 이후 별도 `in_progress` transition과 후속 implementation commit 및 갱신된 `implemented`/IQC evidence를 같은 순서로 다시 가져야 한다.
- Lifecycle chronology는 exact implementation/IQC candidate의 first-parent chain만 사용한다. 다른 parent에서만 reachable한 transition이나 implementation commit은 predecessor 또는 binding으로 인정하지 않는다.
- `not_started → implemented`, `implemented → implemented` rework without `in_progress`, `in_progress`와 implementation의 same-commit 결합, lifecycle-only `in_progress` commit을 `implementation_commit`으로 사용, approved specification 또는 `in_progress`보다 앞선 implementation binding을 artifact ID·관련 boundary와 함께 stable diagnostic으로 거부한다.
- `implementation_commit`의 semantic 품질이나 승인 범위 충족 여부를 path allowlist로 추론하지 않는다. Validator가 기계적으로 보장하는 것은 exact commit resolution, strict first-parent ordering과 lifecycle transition이며 실제 검사 결과는 IQC가 소유한다.
- Missing object, shallow history, unresolved commit, malformed historical artifact, first-parent traversal 또는 Git execution 실패로 strict history를 입증하지 못하면 permissive fallback 없이 history-unavailable 계열 stable diagnostic으로 실패한다.
- Contract, template, validator, Line writer, packaged user harness와 implementation-start/IQC workflow를 같은 policy와 일치시키고 source CLI와 isolated installed-wheel CLI에서 동일한 판정과 read-only 동작을 제공한다.
- Real-Git fixture로 valid 최초 cycle·valid rework, direct transition, same-commit, second-parent-only marker, lifecycle-only binding, pre-baseline `delivered`·`cancelled` terminal legacy, fieldless non-terminal, cutoff 이후 fieldless terminal 전이, field removal, missing history와 여러 Micro-SPEC 중 단일 위반을 검증한다.

## Constraints

- Validation은 canonical bytes, index, worktree, symbolic HEAD, refs와 Git object database를 변경하지 않아야 한다.
- Baseline과 transition 판정은 commit timestamp가 아니라 exact Git commit graph와 first-parent ordering을 사용한다.
- Existing terminal(`delivered`·`cancelled`) Line의 bytes나 Git history를 migration 목적으로 수정하지 않는다.
- History policy 도입은 current lifecycle vocabulary, IQC result vocabulary, fast-forward main integration contract 또는 reviewer의 semantic implementation 판정을 변경하지 않는다.
- Stable diagnostic은 위반 Micro-SPEC 또는 Line path와 원인을 식별하되 credential, token, password, remote URL secret 또는 environment connection string을 기록하지 않는다.

## Non-Goals

- Historical commit rewrite, synthetic transition commit 또는 terminal artifact migration
- Validator나 Line writer의 자동 Git commit·branch·merge·ref mutation
- 모든 Micro-SPEC의 동시 `in_progress` 전환
- Discovery, REQ, AC, DQC 또는 delivery lifecycle 전체의 history validation
- Source path 종류만으로 implementation 내용·품질·승인 범위 충족을 판정하는 기능
- Warning-only migration period 또는 baseline 이후 opt-out
- Windows controlled verification, release, tag, publication 또는 public asset read-back
