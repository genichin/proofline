# Windows official fresh install과 user harness initialization

## Problem

ProofLine의 official wheel은 Windows 11 일반 사용자 환경의 user-level `uv tool`에 설치할 수 있지만, 현재 versioned installer와 `proofline init` transaction은 Windows에서 공식 install → user harness initialization → validation 흐름을 완료하지 못한다. Git Bash의 POSIX temporary path를 native Windows `curl`이 기록하지 못할 수 있고, user harness의 fresh commit이 Linux `renameat2(RENAME_NOREPLACE)`를 직접 호출하여 Windows에서 실제 mutation 전에 실패한다. 따라서 관리자 권한 없이 official artifact를 검증·설치하고 isolated user home에 canonical harness를 원자적으로 초기화한 뒤 project를 검증하는 최소 Windows 지원 경계가 필요하다.

## Evidence

- GitHub Issue [#13](https://github.com/genichin/proofline/issues/13)은 Windows 11, Python 3.11.15, uv 0.11.31, Git for Windows 2.55.0 및 official `v0.4.1` wheel에서 두 실패를 기록한다. Git Bash의 `TMPDIR=/tmp` 상태에서는 native Windows `curl`이 `curl: (23) client returned ERROR on write`로 실패했고, Windows native temporary path를 명시하면 wheel 설치는 성공했다.
- 같은 Issue에서 `proofline init --dry-run`은 성공하지만 actual init은 `home_writer._commit_directory()`의 `ctypes.CDLL(None, use_errno=True)` 경계에서 실패했다. 우회하여 packaged payload를 Windows directory rename으로 fresh target에 commit한 뒤 official `proofline init`을 재실행하면 `already-initialized`가 확인됐다.
- `install.sh:35-56`은 `curl`, `sha256sum`, `uv`, `mktemp`와 POSIX shell을 요구하고 `mktemp -d "${TMPDIR:-/tmp}/proofline-install.XXXXXX"` 결과를 native `curl -o`에 직접 전달한다. 현재 tracked `install.ps1` 또는 다른 native Windows installer는 없으며 `README.md:19-25`의 official install interface도 versioned `install.sh`만 제공한다.
- `src/proofline/home_writer.py:217-245`의 `_commit_directory()`와 `_exchange_directories()`는 플랫폼 capability 분리 없이 `ctypes.CDLL(None)`에서 libc `renameat2`를 조회하고 각각 `RENAME_NOREPLACE`와 `RENAME_EXCHANGE`를 사용한다. Fresh create와 existing replacement가 같은 Linux 전용 backend에 결합돼 Windows에서는 fresh init까지 차단된다.
- `src/proofline/home_writer.py:186-214`는 existing tree의 exact entry set·symlink·bytes를 검증하고 staging payload를 결정론적으로 작성하는 플랫폼 독립 로직을 이미 제공한다. `HomeUpdateTransaction.commit()`은 create와 replace mode를 구분하므로 Windows 최소 범위를 fresh create backend로 제한할 구조적 경계가 존재한다.
- `tests/test_home_init.py`는 isolated HOME의 fresh init, dry-run no-mutation, repeated `already-initialized`, conflict·symlink·write failure·concurrent target 보존을 검사하지만 현재 repository에는 tracked PowerShell test나 `.github/**` hosted CI workflow가 없고 Windows에서 exact installed wheel을 실행하는 gate도 없다.
- Public v0.5.0 release read-back에서 isolated fresh HOME에 official installer로 package를 설치한 직후 `proofline update --check`는 package가 current/target `0.5.0`이어도 harness 부재 때문에 `status: update-available`을 반환했다. `proofline init` 후 동일 check는 `status: already-current`를 반환했다. 이는 `src/proofline/updater.py:252-256`의 명시적 absent-home 분기와 일치하지만 README 설치 확인 순서는 이 선행 조건을 분명히 제시하지 않는다.
- Active `ac-0014`는 immutable exact tag의 `install.sh`만 official one-line installer로 규정한다. Windows-native official interface를 도입하면 이 지속 계약의 observable interface와 검증 의미를 갱신해야 한다. `ac-0008`, `ac-0012`, `ac-0016`은 각각 user-level uv tool, verified update/check와 project 무변경, safe user harness init을 이미 지속 조건으로 소유한다.

## Scope

- Windows 11 일반 사용자의 official fresh-install 정본 interface로 native PowerShell `install.ps1`을 제공하고 기존 `install.sh`는 현재 POSIX 정본으로 유지한다. `install.ps1`은 exact immutable version tag에서 official wheel과 `SHA256SUMS`만 다운로드하고 mutation 전에 SHA-256을 strict 검증하며 user-level `uv tool install --no-config`를 실행한 뒤 exact executable과 selected version을 검증한다.
- Windows installer의 temporary directory와 download destination은 같은 native Windows path namespace에서 해석돼야 하며 Git Bash의 `/tmp`와 native executable의 path interpretation 차이에 의존하지 않아야 한다.
- `home_writer`의 staging·payload verification과 commit primitive를 플랫폼별 capability boundary로 분리하고, Windows fresh mode에서 user home 아래 private staging tree를 완성·검증한 뒤 absent `~/.proofline` target에 no-overwrite commit한다. Concurrent target이 먼저 나타나면 외부 target을 보존하고 ProofLine-owned staging만 제거하며 partial harness를 남기지 않는다.
- Windows fresh `proofline init --dry-run`은 actual과 동일한 package resource·HOME·target·capability preflight를 수행하되 mutation하지 않는다. Actual init 후 manifest와 모든 managed-file checksum을 재검증하고 exact repeated init은 `already-initialized` no-op이어야 한다.
- Repository-owned tracked PowerShell verification script를 GitHub Actions `windows-latest`의 Python 3.11 mandatory Line gate와 controlled Windows 11 일반 사용자 IQC에서 동일하게 실행한다. Checkout 밖의 exact candidate wheel을 isolated user-level tool directory에 직접 설치하고 distribution metadata·`site-packages` origin·version, init dry-run, fresh init, repeated init, manifest·managed checksum, initialized 상태의 `update --check`, fixture project `validate`와 application `.venv`·`pyproject.toml`·lockfile·Git state·project `.proofline/` 불변을 판정한다. Installer 자체는 local fixture asset과 checksum으로 download·verification·installation·post-verification 순서를 재현한다.
- GitHub Actions `ubuntu-latest`의 Python 3.11 mandatory Line gate는 전체 regression과 Linux `renameat2` fresh-create·exchange transaction 회귀를 실행한다. Mandatory는 REQ·IQC·DQC가 두 hosted job의 PASS evidence를 요구한다는 의미이며 GitHub branch protection 설정 변경을 뜻하지 않는다.
- Publication 후 release evidence는 approved exact release commit과 annotated tag가 public remote에 존재한 뒤에만 수집한다. Exact-tag Windows installer bytes, release asset allowlist, remote wheel·`SHA256SUMS`, checksum·local candidate byte identity, isolated user-scoped installation과 첫 init·validate 흐름을 public URL에서 read-back하고 IQC/DQC 또는 publication evidence에 기록한다. 미공개 candidate gate를 immutable public tag evidence로 대신하지 않는다.
- Linux의 `renameat2` fresh-create 및 exchange transaction 계약과 기존 home-init·updater regression을 유지하고 Windows backend 도입이 Linux rollback·concurrency 의미를 약화하지 않는지 검증한다.
- Fresh package install 후 문서와 E2E는 `proofline init`을 먼저 수행한 다음 initialized harness에서 `proofline update --check`의 `already-current`와 zero mutation을 검증한다. Harness absent 상태의 현재 `update-available` 의미는 변경하지 않으며 package-only 새 status를 추가하지 않는다.
- AC admission은 `install.sh` 전용 official installer 계약을 platform별 exact-tag `install.sh`·`install.ps1` interface로 확장하는 `ac-0014` `update`, 기존 의미를 Windows에서 충족·회귀 검증하는 `ac-0008`, `ac-0012`, `ac-0016` `satisfy`로 분류한다. 새 AC 생성이나 retirement는 계획하지 않으며 exact release version·tag·wheel·checksum은 IQC/DQC publication evidence로만 기록한다.

## Out of Scope

- Windows에서 existing `~/.proofline` harness를 새 payload로 transactional replacement하거나 Linux `RENAME_EXCHANGE`와 동등한 directory exchange를 제공하는 기능
- Windows updater mutation, package·harness rollback, interruption·crash recovery 또는 old-to-new public update transaction을 지원 완료로 선언하는 작업
- Harness absent 상태의 `proofline update --check` status를 변경하거나 package-only 상태를 새 public status로 추가하는 작업
- `proofline project init`과 `proofline line init`의 Linux-specific commit primitive를 Windows용으로 전면 이식하는 작업
- 모든 Windows version, filesystem, shell, architecture와 Python minor의 지원을 한 번에 보장하는 작업
- Python 3.12 이상 또는 추가 Windows image·architecture를 initial hosted matrix에 포함하는 작업
- GitHub branch protection이나 repository rule을 생성·변경하여 workflow를 remote merge gate로 강제하는 작업
- Windows installer가 Git, Python, uv 또는 PATH를 자동 설치·영구 수정하거나 관리자 권한을 요구하는 동작
- Git Bash용 Windows-aware `install.sh` fallback을 official Windows interface로 추가하거나 지원 완료로 선언하는 작업
- Existing malformed harness를 repair·merge·overwrite하거나 user-managed unknown entry를 삭제하는 동작
- Issue #3의 `line-0000` numbering policy, Issue #10의 artifact template 한국어화 및 다른 open backlog
- v0.5.0 immutable tag·asset을 수정·교체하거나 특정 corrective release identity를 active AC로 만드는 작업

## Risks and Unknowns

### Risks

- POSIX shell과 PowerShell installer를 별도로 유지하면 version, asset filename, checksum sequence, replacement guard와 post-verification이 drift할 수 있다. Shared release-facing invariant test와 exact-tag public read-back으로 두 interface의 결과 동등성을 검증해야 한다.
- Windows directory rename의 no-overwrite·same-volume·symlink/junction·sharing violation 의미가 Linux `renameat2`와 다르므로 API 이름이 아니라 observable no-overwrite, external-winner preservation와 cleanup 결과를 계약으로 고정해야 한다.
- Fresh create backend를 replacement에도 재사용하면 verified previous harness의 atomicity와 rollback을 약화할 수 있다. Platform dispatch는 mode별 capability를 분리하고 unsupported replacement를 mutation 전에 fail-closed해야 한다.
- Hosted Windows test가 source checkout import나 developer environment를 우연히 사용하면 official wheel 검증을 가장할 수 있다. Checkout 밖 exact executable, distribution metadata, `site-packages` origin과 isolated HOME·tool directories를 기록해야 한다.
- Windows-specific path normalization이 symlink·junction 또는 drive boundary를 잘못 허용하면 user home 밖 mutation이나 staging residue로 이어질 수 있다. Native path identity와 target ownership을 failure matrix에 포함해야 한다.

### Assumptions

- 첫 Windows vertical slice는 Windows 11, CPython 3.11, official pure-Python wheel 및 user-level uv tool을 최소 지원 기준으로 삼으며 확대 여부는 후속 evidence로 결정한다.
- Hosted Windows runner의 단순 성공은 실제 non-admin 증거가 아니므로 elevation 요청 부재와 machine-scoped path·setting 무변경을 자동 gate에서 판정하고, 실제 Windows 일반 사용자 계정에서 같은 tracked script를 실행한 결과를 IQC evidence로 기록한다.
- User home과 staging 및 target이 같은 volume에 있다는 조건은 atomic directory commit 후보의 전제다. 이 전제를 요구할지와 위반 시 diagnostic은 REQ에서 Windows capability evidence에 근거해 고정한다.

### Open Questions

- `OQ-001`
  - Type: `DECIDE`
  - Status: answered
  - Question: Windows official fresh install의 정본 user-facing interface를 native PowerShell `install.ps1`로 추가할 것인가, 기존 `install.sh`가 Git Bash와 native Windows path를 함께 처리하도록 확장할 것인가?
  - Options: Native `install.ps1`은 Windows 기본 shell·native temporary path·download·hash API를 사용하여 Git Bash와 `cygpath` 의존성을 제거하지만 POSIX installer와 release invariant가 drift하지 않도록 parity test가 필요하다. Windows-aware `install.sh`는 script 수를 늘리지 않지만 Git Bash 설치를 전제로 하고 POSIX path를 native `curl`·`uv`에 전달할 때 shell/tool 조합별 path conversion을 계속 소유해야 한다.
  - Recommendation: Native `install.ps1`을 Windows 정본 interface로 추가하고 기존 `install.sh`는 현재 POSIX 정본으로 유지한다. 별도 사용자 요구가 없는 한 Windows-aware `install.sh` fallback은 이 Line에 포함하지 않는다.
  - Decision Basis: Issue #13의 직접 실패 원인이 wheel이나 uv가 아니라 Git Bash의 `/tmp`와 native Windows executable의 path namespace 결합이므로, path conversion을 보강하는 것보다 Windows 기본 실행 경로로 분리하는 편이 fresh-only 범위를 작게 유지하고 재현 가능한 official interface를 제공한다.
  - Owner: 제품 owner
  - Exit Condition: 사용자가 native `install.ps1`을 Windows 정본 interface로 승인했고 Windows-aware `install.sh` fallback은 제외했다. 결과를 Scope·Out of Scope와 `ac-0014` update 방향에 반영했다.
