# Windows fresh user harness commit backend

## Scope

### 담당 범위

- `HomeUpdateTransaction`의 staging·payload verification과 commit primitive를 platform capability boundary로 분리하고 Windows fresh `proofline init`의 absent-target no-overwrite commit을 구현한다.
- Dry-run capability parity, successful post-verification, repeated no-op, concurrent target preservation과 owned cleanup을 구현·검증한다.

### 제외 범위

- Native Windows installer와 hosted workflow는 다른 Micro-SPEC이 담당한다.
- Windows existing harness replacement, updater mutation, exchange·rollback·recovery는 담당하지 않는다.
- Same-user staging 탈취, syscall interposition과 abrupt process·kernel termination을 보장하지 않는다.

### 기준과 의존성

- Confirmed `dcy-0017`, draft `req-0017`과 `ac-0016`의 fresh managed-tree atomicity·no-overwrite·project no-mutation 계약을 기준으로 한다.
- Existing manifest rendering, managed entry verification과 Linux `renameat2` backend의 observable behavior는 유지한다.

## Implementation

### 변경 대상

- `src/proofline/home_writer.py`의 platform capability dispatch와 Windows fresh directory commit
- `src/proofline/home_init.py`의 dry-run/actual capability preflight 및 post-verification 연결
- `tests/test_home_init.py`, installed-wheel home-init fixture와 Windows-specific failure matrix

### 구현 작업

1. Fresh create와 existing replacement mode가 서로 다른 platform capability를 선택하게 하며 Windows fresh create가 Linux libc symbol lookup을 실행하지 않도록 한다.
2. Windows fresh create는 user home과 같은 volume의 private staging tree를 완성하고 exact managed entry set·manifest·checksum을 검증한 뒤 absent target에 no-overwrite directory commit한다.
3. Commit 직전에 target이 나타나거나 native primitive가 sharing·permission·cross-volume·unsupported failure를 반환하면 external target을 수정·삭제하지 않고 invocation-owned staging·partial state만 identity 확인 후 정리한다.
4. Windows replacement mode는 verified existing harness를 displaced하거나 변경하기 전에 stable unsupported diagnostic으로 중단한다. Linux fresh-create·exchange paths는 기존 behavior와 failure semantics를 유지한다.
5. Dry-run은 package payload, HOME topology, target absence와 selected fresh-commit capability를 actual과 동일하게 확인하되 staging·target을 만들지 않는다.
6. Successful actual은 committed tree를 다시 읽어 manifest와 모든 managed checksums를 검증하고, exact repeated init은 bytes·metadata·project snapshot이 변하지 않는 `already-initialized` 결과를 반환한다.
7. Real Windows와 Linux tests에서 fresh·dry-run·repeat·symlink or junction·concurrent target·write·commit·post-verification failure 및 project no-mutation을 검증한다.

### Rollback과 containment

- Cleanup은 이번 invocation이 생성한 staging identity와 partial target만 대상으로 하며 pre-existing 또는 concurrent external target의 path·bytes를 변경하지 않는다.
- Fresh target commit 성공 후 post-verification failure에서 target ownership을 증명할 수 있는 경우에만 invocation-owned target을 제거하고, 증명할 수 없으면 외부 상태를 보존한 채 primary diagnostic과 cleanup failure를 함께 보고한다.

## Verification

- 검사: Platform dispatch unit tests, Windows native filesystem subprocess, Linux home-init regression, dry-run parity, exact no-op, concurrent target event choreography, injected write·commit·post-verification failure와 checkout 밖 exact wheel E2E를 실행한다.
- 기대 결과: Windows fresh init은 libc 의존 없이 complete verified harness만 commit하고 모든 in-scope failure에서 external state를 보존하며 owned residue를 남기지 않는다. Windows replacement는 mutation 전 실패하고 Linux transaction behavior는 회귀하지 않는다.
- Evidence: `.proofline/lines/line-0017/micro-specs/iqc-0017-001.md`에 exact specification·implementation commit, OS·filesystem fixture와 test 결과를 기록한다.
