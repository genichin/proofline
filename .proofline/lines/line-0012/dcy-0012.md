# AC 카탈로그 병합 및 정리

## Problem

현재 active AC 카탈로그에는 동일한 제품 동작의 성공 조건과 실패·안전 조건을 별도 identity로 분리하거나, 기존 AC가 소유해야 할 경계 조건을 새 AC로 생성한 항목이 있다. 이 구조는 AC를 독립적이고 지속적인 제품 사양보다 Line별 작업 기록에 가깝게 만들고, 현재 요구사항 목록의 중복과 장기 유지 비용을 증가시킨다.

이번 정리는 기존 구현을 제거하거나 과거 delivery를 무효화하는 작업이 아니다. 같은 사양 축의 조건을 stable survivor AC에 통합하고, 중복 AC를 canonical path에 보존한 채 retire하여 현재 active 카탈로그와 역사적 traceability를 동시에 유지해야 한다.

## Evidence

- GitHub Issue #11 `새 AC 생성 전에 사양 가치와 기존 AC 소유권을 판정한다`는 `Issue → Line → REQ → 새 AC`의 기계적 변환과 AC admission 부재를 근본 원인으로 기록한다: `https://github.com/genichin/proofline/issues/11`.
- `docs/contracts/requirements-and-criteria.md`는 같은 사양 축의 조건 변경은 stable AC를 update하고, active AC는 지속적으로 만족해야 하는 version-independent product behavior 또는 constraint여야 한다고 규정한다.
- `ac-0004`와 `ac-0005`는 모두 `proofline line init`을 소유하며 각각 정상 생성과 preflight·dry-run·원자적 실패 조건을 분리한다.
- `ac-0007`은 exact approval commit 기반 implementation worktree를 소유하고, `ac-0009`는 prior draft transition 이력이 없는 exact approved baseline도 허용한다는 동일 preflight 축의 경계 조건을 소유한다.
- `ac-0012`, `ac-0018`, `ac-0019`는 모두 `proofline update`를 소유하며 각각 verified release 선택·package 교체, package와 user harness 수렴, preflight·rollback·failure coherence를 분리한다.
- `ac-0016`과 `ac-0017`은 모두 명시적 `proofline init`을 소유하며 각각 user harness 생성과 idempotency·fail-closed·atomicity를 분리한다.
- `line-0005`의 REQ·Micro-SPEC·IQC·DQC는 `ac-0009`를 직접 참조하므로 AC 파일 삭제나 ID 변경은 dangling reference와 historical binding 훼손을 만든다.
- `docs/contracts/storage-and-retention.md`는 retired AC를 고정 canonical path에서 무기한 보존하고 active AC만 현재 `docs/requirements.md`에 포함하도록 규정한다.
- 현재 `proofline validate`는 retired release AC인 `ac-0011`, `ac-0013`, `ac-0015`와 이들을 참조하는 과거 Line을 함께 보존한 상태에서 통과한다.

## Scope

- `ac-0004`를 update하여 결정론적 Line bootstrap과 preflight·dry-run·no-overwrite·atomic failure 조건을 하나의 `proofline line init` 계약으로 통합한다.
- `ac-0005`를 `ac-0004`에 흡수된 중복 사양으로 retire한다.
- `ac-0007`을 update하여 prior draft transition 이력 유무와 관계없이 exact approved baseline을 허용하는 조건을 통합한다.
- `ac-0009`를 `ac-0007`에 흡수된 경계 조건으로 retire한다.
- `ac-0012`를 update하여 verified official release 선택, CLI/package와 managed user harness의 동일 target 수렴, read-only check, preflight, atomic commit·rollback과 failure coherence를 하나의 `proofline update` 계약으로 통합한다.
- `ac-0018`과 `ac-0019`를 `ac-0012`에 흡수된 update 성공·실패 조건으로 retire한다.
- `ac-0016`을 update하여 명시적 user harness 초기화와 idempotency·fail-closed·atomicity를 하나의 `proofline init` 계약으로 통합한다.
- `ac-0017`을 `ac-0016`에 흡수된 초기화 안전 조건으로 retire한다.
- 새 REQ의 AC 변경 집합은 `create: []`, `update: [ac-0004, ac-0007, ac-0012, ac-0016]`, `retire: [ac-0005, ac-0009, ac-0017, ac-0018, ac-0019]`로 제한한다.
- Survivor AC의 Verification은 흡수된 AC의 성공·실패·경계 조건과 기존 구현 evidence를 잃지 않아야 한다.
- Retired AC는 기존 ID와 canonical path를 유지하고 survivor AC, retirement Line 및 역사적 evidence 관계를 본문에 명시한다.
- 기존 Line의 REQ·Micro-SPEC·IQC·DQC를 수정하지 않고 각 승인·candidate commit의 historical evidence로 보존한다.
- 정리 후 active AC만 사용하는 현재 요구사항 view와 canonical reference validation이 일관되는지 검증한다.

## Out of Scope

- 새로운 AC identity 생성
- `ac-0001`, `ac-0002`, `ac-0003`, `ac-0006`, `ac-0008`, `ac-0010`, `ac-0014`의 의미 변경 또는 retirement
- 이미 retired된 `ac-0011`, `ac-0013`, `ac-0015`의 삭제·재활성화 또는 history rewrite
- ProofLine CLI, validator, installer, updater, home writer 또는 Line writer의 제품 동작 변경
- 과거 Line·REQ·Micro-SPEC·IQC·DQC의 소급 수정
- AC ID 변경, 재번호 부여, 파일 삭제 또는 archive 이동
- Issue #11의 AC admission template·skill·validator 개선 전체 구현
- 고객용 설명 문서의 별도 문체·번역 작업

## Risks and Unknowns

### Risks

- Survivor AC가 지나치게 넓어지면 독립적인 변경·검증 경계가 약해질 수 있으므로 동일 command와 동일 사양 축의 성공·실패 조건만 통합해야 한다.
- Retired AC의 현재 본문과 과거 Line의 exact baseline을 혼동하면 역사적 검증 결과를 잘못 해석할 수 있으므로 retirement 사유와 survivor mapping을 명시해야 한다.
- Survivor AC update 과정에서 기존 Verification 항목을 누락하면 이미 검증된 안전 조건의 canonical coverage가 줄어들 수 있으므로 흡수 전후 criterion matrix를 확인해야 한다.
- 현재 설치된 공용 `proofline` CLI version과 repository source version이 다를 수 있으므로 정본 검증은 repository가 요구하는 schema와 실제 CLI 결과를 함께 확인해야 한다.

### Assumptions

- 이번 변경은 현재 구현이 이미 만족하는 조건의 canonical ownership을 재배치하는 사양 정리이며 새로운 제품 구현을 요구하지 않는다. REQ와 Micro-SPEC 작성 전에 survivor AC별 기존 구현·test evidence로 이 전제를 확인한다.
- Retired AC를 참조하는 과거 Line은 해당 Line의 exact approval·candidate commit에서 해석하며, 현재 tree의 retired 상태는 후속 lifecycle transition으로 해석한다.
- Issue #11의 재발 방지 구현은 별도 범위로 남기되, 이번 Line의 create/update/retire 결정은 해당 이슈에 기록된 admission 기준을 적용한다.
