# Provider-free DQC core

## Problem

ProofLine의 공식 DQC 계약은 exact candidate의 로컬 Line-level 검증을 넘어 GitHub Actions workflow, candidate remote ref, 고정 job 이름, Python wheel artifact와 provider API read-back을 mandatory gate로 소유한다. 이 결합은 DQC의 지속적인 core 의미를 특정 CI provider와 ProofLine 저장소의 package 형식에 종속시키며, GitLab·사내 runner·air-gapped 환경 또는 firmware처럼 wheel을 만들지 않는 프로젝트가 같은 core 계약을 사용하기 어렵게 한다.

Open Issue #21은 이를 GitHub Actions와 GitLab CI adapter 및 artifact verification profile로 일반화하려 하지만, 그 구조도 provider API, token, run attempt, artifact expiry와 provider별 failure semantics를 ProofLine core가 계속 소유하게 한다. 제품 owner는 GitHub Actions와 GitLab CI를 모두 ProofLine 공식 gate에서 제거하고, 필요한 CI는 각 적용 프로젝트가 별도 정책으로 운영하는 provider-free core를 선택했다. 따라서 이번 변경은 provider adapter를 추가하지 않고 공식 DQC를 deterministic candidate·IQC·local regression·canonical validation·integration readiness에 한정해야 한다.

## Scope

- ProofLine 공식 DQC를 provider-free core로 정의한다. Core mandatory Line-level checks는 exact IQC coverage/binding, candidate 전체 regression, canonical validation, cross-spec integration·REQ scope, main integration readiness와 candidate 이후 제품 source 불변을 유지한다.
- GitHub Actions, GitLab CI, remote candidate ref, workflow/pipeline/run/attempt/job, hosted artifact expiry, provider API, wheel 전용 provenance 및 checksum read-back을 공식 DQC admission과 authority에서 제거한다.
- 외부 CI가 필요한 프로젝트는 repository-owned workflow, script, skill 또는 운영 정책으로 별도 gate를 소유한다. 외부 CI PASS/FAIL은 해당 프로젝트의 delivery를 추가로 차단할 수 있지만 ProofLine core DQC PASS를 생성·대체·승격하거나 main 통합 authority를 부여하지 않는다.
- 기존 `.github/workflows/candidate-verification.yml`과 관련 `.github/scripts/`는 ProofLine 저장소가 선택적으로 사용하는 project-local cross-platform CI로 유지한다. 이 자산은 DQC admission이나 packaged core 자산이 아니며, 현재 `skills/proofline-run-dqc/resources/candidate-clean-runner-plan-v1.json`을 참조하는 project-local helper/resource는 필요하면 `.github/**` ownership으로 이동해 workflow를 독립시킨다.
- `docs/contracts/line-delivery.md`, `skills/proofline-run-dqc/SKILL.md`, packaged skill resources와 `templates/schema-v1/artifacts/dqc.md`에서 mandatory hosted gate와 provider-specific 필드를 제거하고 source↔wheel↔installed HOME의 updated skill/template byte parity를 유지한다.
- DQC template의 `Checks`는 provider-neutral mandatory Line-level checks와 approved REQ/AC가 명시한 project-local 검사 결과만 기록한다. 외부 CI용 canonical schema, normalized evidence 또는 provider extension field를 새로 추가하지 않는다.
- `ac-0010`을 `update`한다. 기존 trigger-based IQC reuse와 여섯 Line-level check는 유지하되 repository-owned hosted policy를 공식 DQC-ready 조건으로 승격하는 criterion·verification을 제거하고 provider-free authority boundary를 명시한다.
- `ac-0023`을 `retire`한다. Mandatory hosted workflow가 공식 DQC에서 사라지므로 그 workflow를 전제로 하는 clean-runner preflight는 지속적인 독립 acceptance condition이 아니다. Historical criterion과 과거 Line/DQC evidence는 Git history와 canonical artifact로 보존한다.
- REQ admission은 `create: []`, `update: [ac-0010]`, `retire: [ac-0023]`, `satisfy: []`를 권장한다. Version, tag, release, publication evidence는 이 분류에 포함하지 않는다.
- Issue #21은 Discovery confirmation 이후 provider adapter 구현 요구를 폐기하고 이 Line의 provider-free scope로 대체됐음을 기록한다.
- Contract, skill, template, package parity와 관련 tests를 provider-free 의미에 맞게 수정한다. Historical canonical Line·REQ·Micro-SPEC·IQC·DQC bytes는 소급 수정하지 않는다.

## Out of Scope

- GitHub Actions adapter, GitLab CI adapter 또는 다른 CI provider adapter 구현
- `proofline hosted-evidence collect/verify` CLI, normalized hosted-evidence schema, provider/profile 설정 또는 `proofline.yaml` schema v2 도입
- `generic`, `python-wheel`, `zephyr-firmware` 같은 core verification profile 구현
- 프로젝트별 CI workflow가 수행할 build·test·firmware provenance 정책의 표준화
- 외부 CI 결과를 canonical DQC authority field로 수용하는 extension schema
- 과거 Line·DQC 결과, GitHub workflow run 또는 release evidence의 재판정·재작성
- Updater bootstrap과 재설치 경계를 다루는 GitHub Issue #24 및 후속 release 구현
- 기존 `.github` optional project-local CI의 삭제 또는 cross-platform build/test 동작 재설계. 이번 Line은 core authority 분리와 필요한 ownership relocation만 수행한다.
- Version bump, tag, GitHub Release, asset upload, PyPI publication 또는 remote candidate ref mutation
- DQC와 무관한 validator, Line lifecycle, IQC binding 또는 integration topology 변경

## Risks and Unknowns

### Risks

- Mandatory hosted gate 제거로 ProofLine core DQC 자체는 cross-platform hosted execution을 보증하지 않는다. 이는 provider-free 경계의 의도된 결과이며, cross-platform 보증이 필요한 프로젝트는 자체 CI gate를 delivery policy에 별도로 둬야 한다.
- Project-local CI 결과를 DQC Checks에 권위 있는 ProofLine PASS처럼 기록하면 경계가 다시 결합될 수 있다. Core contract와 skill은 external CI가 ProofLine authority를 생성하지 않는다고 명시해야 한다.
- `ac-0010`의 hosted 문구와 `ac-0023`을 그대로 둔 채 contract만 변경하면 active AC와 제품 동작이 충돌한다. AC update/retire transition과 REQ owner를 같은 specification baseline에 결속해야 한다.
- Hosted gate 관련 tests와 packaged resources가 여러 historical feature 영역에 연결되어 있어 단순 문자열 삭제로 source/wheel/package regression을 만들 수 있다. 구현은 current authority-bearing contract·skill·template와 optional project-local 자산을 구분하고 historical fixture 의미를 보존해야 한다.
- 기존 `.github` workflow를 유지하면 공식 DQC gate로 오인될 수 있다. Workflow, helper path, tests와 문서에서 `optional project-local CI` ownership을 명시하고 DQC result/authority를 생성하지 않도록 분리해야 한다.

### Assumptions

- Exact candidate, IQC coverage/binding, full regression, canonical validation, cross-spec scope, main integration readiness와 post-candidate source immutability는 provider와 무관한 공식 DQC core로 유지한다.
- 각 적용 프로젝트는 ProofLine 밖의 repository policy로 CI를 추가 요구할 수 있으며, 그 gate의 provider API·token·artifact·retry·retention과 운영 실패를 자체 소유한다.
- Existing schema v1 canonical artifact와 historical DQC 문서는 계속 read/validate할 수 있어야 하며 과거 hosted evidence가 있었다는 이유로 수정하거나 무효화하지 않는다.
- Provider-free 전환에는 `proofline.yaml` schema 변경이나 새 public CLI가 필요하지 않다.
- 이 Line은 source/specification candidate를 준비하며 release/publication authority를 포함하지 않는다.
