# 최소 validator를 통한 ProofLine 절차 검증

## Problem

> 해결할 문제

ProofLine 스키마 버전 1의 정본 디렉터리 구조, 문서 형식, 상태 및 자리표시자 계약은 문서로만 정의되어 있어 잘못된 산출 문서를 기계적으로 거부할 수 없다. 반면 계약 전체를 첫 구현에 반영하면 validator 자체가 커져 ProofLine 절차를 실제로 시험하기 전에 구현이 지연될 위험이 있다. 따라서 ProofLine 절차를 직접 적용하면서 후속 기능의 기반이 되는 최소 실행 가능 validator를 만들어야 한다.

## Evidence

> 확인 근거

- `docs/artifact-layout.md`와 `docs/contracts/`는 writer와 validator가 따라야 할 스키마 버전 1 계약을 정의한다.
- `templates/schema-v1/`에는 Line부터 DQC까지의 정본 산출 문서와 파생 요구사항 문서의 생성 입력이 존재한다.
- 현재 `cbe1f2c` 개정에는 ProofLine 실행 코드, 패키지 설정 파일 및 검증용 예제가 없다.
- 루트 `proofline.yaml`은 `schema_version: 1`과 `artifact_root: .proofline`을 선언한다.

## Scope

> 포함 범위

- 이 Line 자체를 Discovery → REQ·AC → Micro-SPEC → IQC → DQC 순서로 진행하여 ProofLine 절차와 템플릿을 실제로 사용한다.
- `proofline validate` 단일 명령으로 스키마 버전 1의 프로젝트 설정과 정본 산출 문서의 최소 구조를 검사한다.
- 필수 YAML 머리말 항목, 허용 상태값, 파일명과 ID, H1·H2 구조 및 자리표시자 규칙을 검사한다.
- `discovery`, `parent_req`, `criteria`, `micro_spec`, `line`이 직접 참조하는 정본 파일이 규칙으로 정해진 경로에 존재하는지 검사한다. 참조의 의미와 집합 불변식 검사는 포함하지 않는다.
- 최소 정상 예제와 대표 오류 예제로 일관된 종료 코드 및 오류 위치를 검증한다.
- 첫 구현은 하나의 Micro-SPEC 안에서 완료할 수 있는 범위로 제한한다.

## Out of Scope

- 산출 문서 writer와 자동 ID 할당
- `docs/requirements.md` 생성기
- 상태 전이 자동화와 승인 권한 관리
- Git 커밋 계보, fast-forward 가능 여부 및 과거 상태 전이 전체 분석
- IQC·DQC 커밋 결합의 자동 검증
- 플러그인 구조와 원격 서비스
- Hermes Agent skill 설치·배포
- 자동 수정 기능

## Risks and Unknowns

> 위험 및 미확정 사항

### 위험

- Validator가 완성되기 전에는 이 Line의 산출 문서를 스스로 검증할 수 없다. 초기 산출 문서는 계약 대조, 형식 검사와 검증용 예제의 실행 결과를 IQC·DQC 검증 근거로 기록해 확인한다.
- 구현 중 계약 전체를 한 번에 포함하려는 범위 팽창이 발생할 수 있다. 승인된 AC와 하나의 Micro-SPEC 범위를 넘는 검사는 후속 Line으로 분리한다.
- 문서 계약과 템플릿 사이의 불일치가 발견될 수 있다. 구현 편의를 위해 임의 해석하지 않고 정본 계약 또는 템플릿의 결함으로 분류해 먼저 수정한다.
