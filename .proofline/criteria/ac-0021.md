# Main spine과 Line spine의 exact implementation lifecycle 검증

## Criterion

Line이 `implementation_history: first_parent`를 adoption하면 validator는 각 Micro-SPEC implementation cycle의 approved specification commit `S`, 별도 persisted `in_progress` transition `P`, strict first-parent descendant implementation commit `I`, 후속 `implemented` 상태와 exact-bound IQC `Q`를 read-only로 검증해야 한다. Policy의 최초 persisted commit `B`는 해당 Line의 prospective baseline이며 `I`보다 먼저 있어야 한다. Approved specification 뒤 code change 전에 persisted된 `P`는 `B`보다 앞서도 유효하므로 `P < B < I < Q`와 `B < P < I < Q`를 모두 인정하되 `I < B`, `P = I`, `I = Q`와 baseline-crossing cycle 전체 면제는 허용하지 않는다. 어떤 Line이든 policy를 처음 persisted한 repository first-parent commit `A0`를 fieldless-legacy cutoff로 파생하고, fieldless Line의 terminal transition `T`가 없거나 `T`가 `A0`의 strict ancestor가 아니면 실패해야 한다. 아직 `A0`가 없는 pre-adoption repository의 fieldless terminal Line과 `T < A0`인 Line만 legacy로 보존한다. Field 없는 non-terminal Line, `T = A0`·`T > A0`·second-parent-only `T`, policy 제거·변경, direct transition, rework predecessor 누락, lifecycle-only implementation binding과 입증할 수 없는 Git history는 fail-closed해야 한다.

Main-owned handoff를 사용하는 pre-integration Line spine은 exact specification baseline과 handoff에서 `Q`까지 strict first-parent여야 한다. Line 0020 bootstrap은 Micro-SPEC approval `S`가 combined approval baseline `A`와 같으므로 `S=A < H < P < I < Q`를 사용하고 post-H `S0/S`를 요구하지 않는다. Updated workflow를 사용하는 후속 Line은 `A < H < S0 < S < P < I < Q`를 사용한다. Main이 `H` 뒤 진행한 exact integration candidate `V`는 exactly two parents를 가지고 `parent[0]=M` latest main, `parent[1]=Q` exact single-Line head여야 한다. `V`가 새로 포함하는 유일한 canonical `.proofline/lines/line-NNNN/integration-NNNN.md` manifest의 schema·path·`line_id`·`main_parent`·`line_head`는 containing commit의 target Line과 actual parents에 정확히 결속돼야 한다. Manifest missing·duplicate·path/identity/parent mismatch, parent reversal, octopus·multi-Line·ambiguous second parent, second-parent-only lifecycle evidence와 manifest 외 merge-only 제품 변경은 거부해야 한다. Candidate/DQC admission 전에는 current main과 Line head가 각각 `M`과 `Q`인지 검사하고 drift에는 fresh `V`와 fresh evidence를 요구해야 한다. DQC PASS descendant가 main에 fast-forward된 뒤 historical validation은 mutable refs가 아니라 DQC `candidate_commit: V`, manifest, actual parents, main first-parent의 `M → V → DQC PASS → delivery`와 designated Line first-parent chronology를 검증해야 한다.

## Verification

- 성공 조건: 새 Line과 명시적으로 adoption한 existing non-terminal Line의 최초 cycle 및 `implemented → in_progress → implemented` rework가 approved specification, persisted `P`, strict-descendant `I`와 후속 IQC 순서를 가지면 PASS해야 한다. 최초 cycle은 `P < B < I < Q`와 `B < P < I < Q`를 모두 허용한다. Policy marker `A0`가 없는 pre-adoption repository의 fieldless terminal Line과 `T < A0` Line을 보존해야 한다. Line 0020 `S=A < H < P < I < Q`, 후속 Line `A < H < S0 < S < P < I < Q`, linear Line과 diverged `V(parent[0]=M,parent[1]=Q)`·matching manifest·DQC/delivery chronology가 source와 installed-wheel에서 PASS해야 한다. DQC fast-forward, 후속 unrelated main commit과 Line branch cleanup 뒤에도 immutable historical validation이 PASS해야 한다.
- 실패·경계 조건: `I < B`, `P = I`, `I = Q`, approved specification보다 앞선 `P`, baseline-crossing 면제, field 없는 non-terminal Line, `T = A0`·`T > A0`·second-parent-only/missing terminal transition, policy 제거·변경, `not_started → implemented`, rework `P` 누락, lifecycle-only 또는 second-parent-only marker·implementation, Line 0020의 post-H extra `S`, 후속 Line의 missing/stale/body-changing `S`, stale `M`·`Q`, wrong parent order, missing·duplicate·mismatched manifest, arbitrary/multiple Line parent, octopus merge, merge-only 제품 수정, malformed/missing/shallow/unresolved Git history와 ambiguous DQC binding은 Line·Micro-SPEC·manifest path와 stable diagnostic으로 fail-closed해야 한다.
- 검사 방법: Existing legacy cutoff·field policy·first/rework/baseline matrix와 main governance/Line implementation을 독립 진행한 Real-Git candidate matrix를 함께 실행한다. Candidate 전 ref drift, deterministic two-parent merge, manifest authority, DQC descendant·fast-forward·delivery, post-cleanup historical scan과 Line 0018·0019 regression을 source 및 isolated installed-wheel CLI에서 검증하고 canonical bytes, index/worktree, symbolic HEAD, refs와 object database snapshot을 전후 비교한다.
