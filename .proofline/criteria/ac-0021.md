# First-parent implementation lifecycle history 검증

## Criterion

Line이 `implementation_history: first_parent`를 adoption하면 `proofline validate`는 exact Git first-parent chronology에서 각 Micro-SPEC implementation cycle이 approved specification commit, 별도 persisted `in_progress` transition, 그보다 뒤의 exact implementation commit, 후속 `implemented` 상태와 대응 IQC evidence 순서로 존재하는지 read-only로 검증해야 한다. Policy의 최초 persisted commit `B`는 해당 Line의 prospective baseline이며 implementation commit보다 먼저 있어야 한다. Approved specification 뒤에 코드 변경보다 먼저 persisted된 `in_progress`는 `B`보다 앞서도 유효하므로 `P < B < I < Q`와 `B < P < I < Q`를 모두 인정하되, `I < B`, `P = I`, `I = Q` 또는 baseline-crossing cycle 전체 면제는 허용하지 않는다. 어떤 Line이든 policy를 처음 persisted한 repository first-parent commit `A`를 fieldless-legacy cutoff로 파생하고, fieldless Line의 delivered transition `D`가 없거나 `D`가 `A`의 strict ancestor가 아니면 실패해야 한다. 아직 `A`가 없는 pre-adoption repository의 fieldless delivered Line과 `D < A`인 Line만 legacy로 보존한다. Field 없는 non-delivered Line, policy 제거·변경, direct transition, rework predecessor 누락, second-parent-only evidence, lifecycle-only implementation binding과 입증할 수 없는 Git history는 artifact와 원인을 식별하는 stable diagnostic으로 fail-closed해야 한다.

## Verification

- 성공 조건: 새 Line과 명시적으로 adoption한 existing non-delivered Line의 최초 cycle 및 `implemented → in_progress → implemented` rework가 approved Micro-SPEC, persisted `in_progress`, strict-descendant implementation commit과 후속 IQC 순서를 first-parent chain에 가지면 source와 installed-wheel `proofline validate`가 종료 코드 0을 반환해야 한다. 최초 cycle은 `P < B < I < Q`와 `B < P < I < Q`를 모두 PASS한다. Policy marker `A`가 없는 pre-adoption repository의 fieldless delivered Line과 fieldless delivered transition `D`가 `A`의 strict ancestor인 Line도 소급 transition 오류 없이 통과해야 한다.
- 실패·경계 조건: `I < B`, `P = I`, `I = Q`, approved specification보다 앞선 `P`, baseline-crossing cycle 면제, field 없는 non-delivered Line, `D = A`·`D > A`·second-parent-only `D` 또는 delivered transition을 입증할 수 없는 fieldless Line, 도입된 field의 제거·변경, `not_started → implemented`, rework `in_progress` 누락, lifecycle-only transition commit binding, second parent에만 존재하는 marker·implementation, missing object·shallow history·unresolved commit·malformed historical artifact와 여러 Micro-SPEC 중 하나의 위반에서 해당 Line 또는 Micro-SPEC path, stable error code와 원인을 반환해야 한다.
- 검사 방법: Merge graph와 최초·rework cycle을 생성하는 Real-Git positive/negative fixture에서 exact commit ordering과 diagnostic을 검사하고, validation 전후 canonical recursive bytes, index/worktree status, symbolic HEAD, refs와 object database snapshot을 비교한다. 같은 fixture를 source CLI와 isolated installed-wheel CLI로 실행하여 판정 parity와 기존 valid lifecycle regression을 확인한다.
