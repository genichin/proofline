# Main spine과 Line spine의 exact implementation lifecycle 검증

## Criterion

Line이 `implementation_history: first_parent`를 adoption하면 validator는 각 Micro-SPEC implementation cycle의 approved specification commit `S`, 별도 persisted `in_progress` transition `P`, strict first-parent descendant implementation commit `I`, 후속 `implemented` 상태와 exact-bound IQC를 해당 Line implementation spine에서 read-only로 검증해야 한다. Line worktree의 pre-integration spine은 main-owned handoff `H`에서 exact Line verification head `Q`까지 first-parent여야 하며 second-parent-only `S`·`P`·`I`·`Q`, lifecycle-only implementation binding, direct transition과 rework predecessor 누락을 거부해야 한다. Main이 `H` 뒤 진행한 경우 exact integration candidate `V`는 exactly two parents를 가지고 `parent[0]`을 latest main `M`, `parent[1]`을 exact single-Line `Q`로 사용해야 한다. `V`가 새로 포함하는 canonical `integration-NNNN.md` manifest의 path·`line_id`·`main_parent`·`line_head`는 containing commit의 target Line과 actual parents에 정확히 결속돼야 하며, manifest missing·duplicate·mismatch, parent reversal, octopus·multi-Line·ambiguous second parent와 manifest 외 merge-only 제품 변경을 거부해야 한다. Candidate/DQC admission 전에는 current main과 Line head가 각각 `M`과 `Q`인지 검사하고 drift에는 fresh `V`를 요구해야 한다. DQC PASS descendant가 main에 fast-forward된 뒤 historical validation은 mutable refs가 아니라 DQC `candidate_commit: V`, manifest, actual parents, main first-parent의 `M → V → DQC PASS → delivery`와 designated Line first-parent의 `H → S → P → I → Q`를 검증해야 한다. Existing linear delivered Lines와 prospective policy baseline, legacy cutoff 및 valid `P < B < I < Q`·`B < P < I < Q` 의미는 보존해야 한다.

## Verification

- 성공 조건: Linear Line과 diverged main/Line Real-Git graph에서 approved `S`, separate `P`, strict descendant `I`·`Q`, exact IQC, `V(parent[0]=M,parent[1]=Q)`, matching manifest, hosted/DQC descendant와 delivery chronology가 source와 installed-wheel validation에서 PASS해야 한다. DQC fast-forward 직후, 후속 unrelated main commit 뒤와 clean Line branch cleanup 뒤에도 immutable historical validation이 PASS해야 한다.
- 실패·경계 조건: `I < policy baseline`, `P = I`, `I = Q`, approved specification보다 앞선 `P`, direct/rework transition 누락, second-parent-only Line lifecycle, stale `M`·`Q`, wrong parent order, missing·duplicate·mismatched manifest, arbitrary/multiple Line parent, octopus merge, merge-only 제품 수정, malformed/missing/shallow Git object와 ambiguous DQC binding은 Line·Micro-SPEC·manifest path와 stable diagnostic으로 fail-closed해야 한다.
- 검사 방법: Main governance와 Line implementation을 독립 진행한 Real-Git fixtures에서 candidate 생성 전 ref drift, deterministic two-parent merge, manifest authority, DQC descendant·fast-forward·delivery와 post-cleanup historical scan을 실행한다. Existing Line 0018·0019 linear fixtures, 최초/rework cycle, fieldless legacy cutoff를 source 및 isolated installed-wheel CLI에서 검증하고 전후 canonical bytes, index/worktree, symbolic HEAD, refs와 object database snapshot을 비교한다.
