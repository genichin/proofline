# 직접 참조와 lifecycle-aware criteria coverage 검증

## Criterion

Validator는 `discovery`, `parent_req`, `criteria`, `micro_spec`, `line`에 기록된 각 canonical reference를 계약된 repository-relative path로 해석하고 대상 canonical artifact가 존재하지 않거나 path와 stable identity가 불일치하면 참조를 소유한 파일을 오류로 판정해야 한다. REQ의 `criteria.satisfy`는 현재 `active` AC를 참조해야 한다. 단, 기존 active AC가 정확히 하나의 non-withdrawn draft REQ에서 `criteria.update` 대상으로 전환 중이고 canonical main의 draft transition 직전 revision에서 그 AC가 active이며 satisfy를 소유한 approved REQ가 현재와 동일한 bytes로 이미 존재하면, 그 binding은 last active approval baseline을 계속 참조하는 것으로 판정해야 한다. Transition 이후 추가·변경된 binding, 새 draft·withdrawn REQ의 draft AC satisfy, prior active revision을 증명할 수 없는 draft AC, 둘 이상의 update owner와 retired AC satisfy는 거부해야 한다. Legacy 3-field REQ와 4-field REQ를 모두 지원하며, 각 non-withdrawn Micro-SPEC의 criteria는 parent REQ target의 non-empty 부분집합이어야 한다. Line이 `not_started` 또는 `in_progress`이고 동시에 모든 non-withdrawn Micro-SPEC의 `implementation_status`가 `not_started`인 경우에만 Micro-SPEC이 없거나 REQ target을 부분 coverage하는 drafting state를 허용한다. 어떤 non-withdrawn Micro-SPEC이라도 `in_progress` 또는 `implemented`이면 Line 상태와 무관하게, 또는 Line이 `verifying`·`delivered`이면, 같은 REQ의 non-withdrawn Micro-SPEC criteria 합집합은 REQ target 전체와 정확히 같아야 한다. Validator는 이 direct-reference·lifecycle-aware coverage 불변식만 판정하고 AC 문장의 의미적 독립성, admission 선택, integration manifest 또는 ancestry를 판정하지 않아야 한다.

## Verification

- 성공 조건: 모든 직접 참조가 존재하고 active satisfy target 또는 단일 update draft의 transition 직전 main revision에 exact approved binding bytes와 active target이 함께 존재하는 historical satisfy를 사용하며, legacy 3-field와 4-field REQ가 유효해야 한다. Micro-SPEC 없는 `not_started` Line, 모든 Micro-SPEC이 `not_started`인 zero/partial `in_progress` drafting Line, first implementation transition 전 full exact coverage와 verifying/delivered exact coverage project는 source와 installed-wheel validation에서 PASS해야 한다.
- 실패·경계 조건: 직접 참조 누락·path/identity mismatch, retired target, transition 이후 생성·변경된 approved binding, 새 draft·withdrawn REQ의 draft target satisfy, prior active revision이 없거나 update owner가 0개·2개 이상인 draft target satisfy, empty/out-of-scope Micro-SPEC criteria, Line 상태와 무관하게 하나라도 `in_progress`·`implemented`인 시점의 uncovered target, verifying/delivered coverage gap과 withdrawn Micro-SPEC에만 의존한 coverage는 소유 artifact·target ID·coverage 차이를 stable diagnostic으로 반환하고 입력 tree를 변경하지 않아야 한다.
- 검사 방법: Active AC의 `active → draft → active`, 과거 approved satisfy REQ, update-owner·activation-evidence cardinality, legacy 3/4-field REQ, Line `not_started → in_progress → verifying → delivered`, Micro-SPEC 없음·partial·exact coverage와 invalid `Line=not_started, MS=in_progress`를 조합한 Real-Git matrix를 source 및 isolated installed-wheel CLI로 실행하고 canonical bytes, index/worktree, HEAD, refs와 object database의 전후 snapshot을 비교한다.
