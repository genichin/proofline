# 사용자 승인 기반 단일 Specification 승인 절차

## Criterion

ProofLine의 Specification 승인은 agent가 confirmed Discovery에 연결된 exact REQ, 전체 criteria 변경 집합의 AC와 REQ가 `Normative Design Documents`로 열거한 exact project design-document 내용을 사용자에게 함께 제시하고 명시적 approval을 받은 뒤에만 계약상 REQ/AC status를 전환하며, current canonical `proofline validate` 결과로 baseline을 확인하는 단일 절차여야 한다. Design documents는 별도 lifecycle status나 approval metadata를 갖지 않으며, 승인된 기술 의미를 변경하려면 관련 REQ와 영향받는 AC를 draft로 되돌려 변경 문서와 함께 재검토·재승인해야 한다. 별도 status-only approval commit, prior draft와 immediate parent 비교, `recorded`·`not recorded` transition audit 또는 exact approval commit 보고를 승인 조건이나 권장 경로로 정의하지 않아야 한다. Source skill과 installed wheel은 같은 managed relative path와 exact bytes를 제공해야 하며, 등록된 에이전트 설치가 있으면 지원 어댑터의 대상에도 같은 bytes가 배치되어야 한다. 어느 배포 위치에도 transition audit helper가 없어야 하고 historical canonical artifacts는 변경하지 않아야 한다.

## Verification

- 성공 조건: Skill과 contract가 exact REQ·AC·Normative Design Documents 제시, 사용자 approval, REQ/AC status 전환, current validation, 결과 보고를 하나의 workflow로 안내하고, design documents가 별도 approval status 없이 current approved baseline의 기술 계약으로 검토되며 source·wheel·등록 대상 어디에도 `audit_transition.py`와 optional transition audit 절차가 없어야 한다.
- 실패·경계 조건: 사용자 approval 전 REQ/AC status 전환, design-document 누락 또는 agent self-approval, 승인된 design 의미의 REQ/AC draft 회귀 없는 변경, audit 제거를 approval gate 제거로 해석하는 문구, source·wheel·등록 대상의 불일치 또는 historical REQ·retired AC 수정은 허용하지 않아야 한다. Normative Design Documents 목록이 없는 REQ와 등록 설치가 없는 상태는 실패가 아니어야 한다.
- 검사 방법: Design-document 목록 유무를 포함한 approval skill·contract fixture, source와 built wheel member 및 격리된 Hermes·Codex 등록 대상의 managed-relative-path byte parity, helper 경로 부재를 확인한 뒤 전체 test와 `proofline validate`를 실행한다.
