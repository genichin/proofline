# DQC는 필수 Line-level 신호와 trigger 기반 재검사를 구분한다

## Criterion

Exact integration candidate의 DQC는 모든 non-withdrawn Micro-SPEC과 passed IQC의 coverage·exact binding, 전체 regression, canonical validation, Micro-SPEC 간 충돌·Line 범위, main fast-forward 가능성과 candidate 이후 제품 source 불변을 항상 판정해야 한다. Component-specific IQC 검사는 passed evidence가 exact-bound이고 candidate가 그 evidence를 stale하게 만들지 않으면 재실행하지 않아도 되며, DQC는 사용한 IQC binding과 skip rationale을 기록해야 한다. 반대로 IQC 이후 관련 source 변경, uncovered integration risk, 누락·stale·non-passed IQC evidence 또는 REQ·AC의 명시적 Line-level 요구가 있으면 관련 검사를 조건부로 요구하고 결과 없이 DQC를 passed로 판정해서는 안 된다. Repository-owned DQC policy가 mandatory hosted candidate gate를 선언하면 exact candidate의 terminal hosted PASS, required jobs, 동일 build artifact의 platform별 검증, immutable run-attempt·artifact·wheel identity read-back과 hosted evidence 이후 제품 source·test·build/runtime configuration 불변도 필수 Line-level 신호이며, 누락·실패·identity drift·artifact ambiguity·mismatch·stale evidence에서는 DQC를 passed로 판정해서는 안 된다.

## Verification

- Exact-bound passed IQC와 필수 Line-level 검사만 있는 representative candidate는 component-specific 검사를 반복하지 않고 DQC-ready로 판정된다.
- Source-after-IQC, uncovered integration risk, invalid IQC evidence와 explicit Line-level requirement fixture는 각각 관련 조건부 검사를 요구한다.
- 필수 Line-level 검사 또는 required conditional 결과가 누락된 fixture는 DQC-ready가 아니다.
- Repository-owned DQC policy에 mandatory hosted candidate gate가 없으면 hosted check를 임의로 요구하거나 실행했다고 기록하지 않는다. 해당 policy가 gate를 선언하면 그 policy가 고정한 workflow identity, required job 집합, artifact naming·provenance schema와 read-back helper를 사용하고, exact candidate SHA·run ID·run attempt에 속한 terminal required job PASS와 정확히 하나의 non-expired artifact, strict 단일 wheel checksum 및 hosted evidence 이후 불변성이 모두 입증될 때만 DQC-ready다.
- Candidate bytes가 바뀌지 않고 repository-owned DQC policy의 narrow interruption predicate가 exact failed run ID·attempt, complete jobs/steps API snapshot과 UTC timestamps, required jobs의 모든 declared step `started_at` 부재 및 선택한 단일 external cause record로 충족된 경우에만 실패 attempt를 보존한 채 같은 exact candidate의 새 run/attempt를 검증할 수 있으며 terminal PASS evidence 전에는 blocked다. Accepted cause는 run conclusion `startup_failure|stale`, authority actor·basis·reason·exact run/attempt·UTC request timestamp가 기록된 external cancellation, 또는 stable GitHub Status incident ID·URL·`GitHub Actions` component와 run interval에 inclusive overlap하는 incident interval뿐이다. Candidate-controlled step은 각 required job의 첫 checkout부터 마지막 declared step까지다. 원인 불명·timeout·started step·불완전·ambiguous evidence, candidate 결함 수정 또는 product source·test·build/runtime configuration 변경은 same-candidate retry admission이 아니며, 변경 correction에는 fresh `P → I → Q → V` 및 새 hosted evidence가 필요하다.
- Contract·canonical DQC template·repository-owned workflow와 DQC policy가 같은 필수·조건부 분류, hosted identity와 기록 방법을 제공한다.
- `proofline validate`는 DQC command list, hosted policy 또는 transition history를 새 schema gate로 검사하지 않는다.
