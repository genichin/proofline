# DQC는 provider-free 필수 Line-level 신호와 trigger 기반 재검사를 구분한다

## Criterion

Exact integration candidate의 DQC는 모든 non-withdrawn Micro-SPEC과 passed IQC의 coverage·exact binding, 전체 regression, canonical validation, Micro-SPEC 간 충돌·Line 범위, main integration readiness와 candidate 이후 제품 source 불변을 항상 판정해야 한다. Component-specific IQC 검사는 passed evidence가 exact-bound이고 candidate가 그 evidence를 stale하게 만들지 않으면 재실행하지 않아도 되며, DQC는 사용한 IQC binding과 skip rationale을 기록해야 한다. 반대로 IQC 이후 관련 source 변경, uncovered integration risk, 누락·stale·non-passed IQC evidence 또는 REQ·AC의 명시적 Line-level 요구가 있으면 관련 검사를 조건부로 요구하고 결과 없이 DQC를 passed로 판정해서는 안 된다.

ProofLine core DQC는 GitHub Actions, GitLab CI 또는 다른 CI provider의 workflow·pipeline·remote ref·run·attempt·job·artifact·API·token·retention을 필수 또는 조건부 DQC 신호로 요구·실행·조회·정규화·판정해서는 안 된다. Project-local CI는 해당 프로젝트 delivery policy의 독립 gate가 될 수 있지만 ProofLine DQC PASS를 생성·대체·승격하거나 main integration authority를 부여해서는 안 된다.

## Verification

- Exact-bound passed IQC와 provider-free 필수 Line-level 검사만 있는 representative candidate는 component-specific 검사를 반복하거나 hosted CI evidence를 요구하지 않고 DQC-ready로 판정된다.
- Source-after-IQC, uncovered integration risk, invalid IQC evidence와 explicit REQ·AC Line-level requirement fixture는 각각 관련 조건부 검사를 요구한다.
- 필수 Line-level 검사 또는 required conditional 결과가 누락된 fixture는 DQC-ready가 아니다.
- Repository에 GitHub Actions, GitLab CI 또는 다른 project-local workflow가 존재하거나 부재해도 ProofLine core DQC의 필수·조건부 check 집합과 PASS 의미는 변하지 않는다.
- Project-local CI의 PASS·FAIL·missing·stale·retry·artifact 상태는 프로젝트 delivery policy에서 별도로 판정하며, 이를 ProofLine DQC result 또는 integration authority로 기록하는 fixture는 거부된다.
- Contract, canonical DQC template와 packaged `proofline-run-dqc` skill은 provider·workflow·run/job/artifact identity 없이 동일한 항상 필수·조건부 분류, IQC reuse와 skip rationale 기록 방법을 제공한다.
- Source checkout, built wheel과 isolated installed HOME의 updated contract·template·skill bytes와 provider-free positive/negative outcome이 exact parity를 이룬다.
- Existing schema v1 historical DQC와 terminal Line은 재작성 없이 계속 검증되며 `proofline validate`는 provider config, external evidence 또는 새 schema field를 요구하지 않는다.
