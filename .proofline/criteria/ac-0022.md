# 독립 Micro-SPEC review와 사용자 승인 ownership

## Criterion

Micro-SPEC approval은 draft author, independent specification reviewer, 사용자 approval authority와 governance recorder를 서로 배타적인 phase로 분리해야 한다. Draft author는 exact `H` 뒤 target Micro-SPEC의 최초 persisted `spec_status: draft`, `implementation_status: not_started` commit `S0`를 만들고, review correction이 필요하면 같은 canonical path만 substantive하게 변경하면서 두 status를 유지한 `R1..Rn`을 순서대로 persist할 수 있다. Independent reviewer는 현재 final draft(`R`이 없으면 `S0`, 있으면 `Rn`)의 substantive bytes, parent REQ·AC scope와 coverage를 read-only로 검토하여 PASS 또는 correction recommendation만 소유해야 하며, correction 뒤에는 final target에 대한 fresh review가 필요하다.

Exact main first-parent에서 `req-0025`가 `draft → approved`이고 `ac-0021`·`ac-0022`가 `draft → active`인 status-only approval commit을 revised baseline `A25`로 파생한다. `A25`와 그 이후 cycle에서 review와 user approval은 closed JSON v2 evidence로 동일한 exact final target을 결속해야 한다. Independent-review v2의 exact key는 `schema`, `target_commit`, `target_tree`, `target_path`, `target_sha256`, `result`, `reviewer_actor_id`, `mutation_performed`이고, user-approval v2의 exact key는 `schema`, `target_commit`, `target_tree`, `target_path`, `target_sha256`, `decision`, `user_actor_id`, `actor_role`, `review_evidence_sha256`이다. Schema 값은 각각 `proofline.independent-review/v2`, `proofline.user-approval/v2`이며 `target_path`는 repository-relative canonical Micro-SPEC path, `target_sha256`은 target commit에서 읽은 그 regular-blob bytes의 lowercase SHA-256이어야 한다. 두 evidence의 commit·tree·path·target digest가 서로 및 supplied target과 같아야 하고, user evidence는 exact review JSON file bytes의 lowercase SHA-256도 결속해야 한다.

Review PASS 뒤 사용자만 exact reviewed target을 승인할 수 있으며 governance lead는 사용자 승인을 대신하지 않고 clean exact final draft 위에 target Micro-SPEC의 `spec_status: draft → approved`만 포함한 direct non-merge child `S`를 기록해야 한다. Substantive bytes 불변과 status-only diff를 read-back한 뒤에만 exact `S` worktree를 구현 에이전트에게 다시 인계해야 한다. 여러 Micro-SPEC은 각 `S0 → R* → S → P` chain을 직렬화하며 한 target chain 안에 다른 target lifecycle을 interleave하거나 batch approval하지 않는다. Self-approval, reviewer mutation, stale intermediate approval, review 중 concurrent mutation, path·digest mismatch, v1/v2 혼합, governance lead 단독 approval과 approval commit의 substantive 변경을 허용하지 않아야 한다.

Pre-`A25` normal flow와 Line 0020 bootstrap은 기존 evidence v1과 기존 chronology 의미를 보존한다. Confirmed Discovery가 current-validator migration bootstrap을 명시한 Line에서는 동일한 independent review와 user-only approval을 REQ·AC·Micro-SPEC combined exact draft에 적용하고 governance lead가 main에 status-only combined approval `S=A`를 기록할 수 있으며, 이 경우 post-handoff `S0/S`를 다시 만들지 않아야 한다. Existing v1 evidence를 post-`A25` authority로 승격하거나 historical evidence를 v2로 rewrite하지 않는다.

## Verification

- 성공 조건: Pre-`A25` existing-valid normal flow와 Line 0020 bootstrap이 기존 의미로 PASS해야 한다. Post-`A25`에서는 `R*=0`, 단일 `R`, 복수 `R` 각각의 exact final draft read-only review, matching v2 evidence, explicit user approval, direct-child status-only `S`와 exclusive handback이 PASS해야 한다.
- 실패·경계 조건: Draft author의 self-approval, reviewer 또는 구현 에이전트 mutation, stale/non-final target, correction 후 old review reuse, user approval 부재, governance lead 단독 decision, dirty worktree, malformed·extra·missing v2 key, v1/v2 schema 혼합, target commit·tree·path·bytes digest 또는 review-file digest mismatch, actor separation 위반, `S.parent`가 final draft가 아닌 경우, merge/body-changing `S`, 다른 target과 interleaved chain, declared bootstrap 외 combined approval과 bootstrap의 post-H duplicate `S`는 stable diagnostic으로 거부해야 한다.
- 검사 방법: Separate actor/phase markers와 temporary Real-Git commits를 사용해 pre-activation compatibility, post-activation `S0 → R* → S` positive path와 stale intermediate·concurrent·schema·path·digest·body-changing·missing-user-approval negative path를 검사한다. Source validator, isolated installed-wheel CLI와 wheel-extracted standalone helper가 같은 scenario ID·diagnostic을 제공해야 하며 helper 전후 canonical bytes, index/worktree, HEAD, refs와 object database가 불변인지 확인한다.
